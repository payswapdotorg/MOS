## What was implemented

**The Agency Command Center as a SECOND route family over the EXISTING
/reporting authority** (the MKT-030 precedent, exactly as the tree
documents it: "the agency-scoped Command Center family (MKT-029) will
register its own family against the same module"; the jobs-visits-routes
pattern — one authority, multiple route families). No new module, no
second reporting/aggregation authority, no UI state of its own: a PURE
LIVE AGGREGATION, READ-ONLY by construction. NO migration (the MKT-030
pattern needed none; nothing was added to persist — verified by the
architecture test).

- `src/modules/reporting/public.ts` — the module's public contract,
  extended ADDITIVELY: the Command Center VIEW types (portfolio-goal
  recaps with client attribution + agency-wide and per-client tallies;
  workflow-state recaps; the agency evidence-quality posture with the
  low-grade D/E/F signal; the risk posture; the pending-approval
  presentations), the second read method
  (`getAgencyCommandCenter` — read-only by construction, zero mutating
  verbs), and the widened `ReportingModuleDeps`: MKT-029 composes the
  /executions direction of the SAME frozen matrix line
  (`/reporting ──→ /goals, /workflows, /executions, /evidence,
  /experiments, /metrics, /learnings`) — the exact direction the
  composition-root comment documented as reserved for "the MKT-029
  agency-scoped family"; /metrics remains the one unused allowed
  direction.
- `src/modules/reporting/internal/command-center-read-model.ts` — the PURE
  composition functions (unit-tested): portfolio goals (full-key
  tallies), workflow state (per-workflow/agency-wide/per-client §5
  tallies), the agency evidence-quality posture (grade distribution by
  class across the portfolio + per-client low-grade counts), the risk
  derivation (goal-DECLARED risk constraints verbatim + FAILED executions
  + UNRESOLVED 'unknown'/'reconciling' executions + blocked/paused
  instance and low-grade evidence counts — durable state ONLY, no
  score/severity/priority field exists anywhere in the vocabulary: a
  tally of authoritative rows, never a risk engine), and the
  pending-approval derivation (the MKT-030 semantics client-attributed).
- `src/modules/reporting/internal/reporting-module.ts` — the module
  wiring: fetches the agency's authorized portfolio state through the
  composed authorities' PUBLIC CONTRACTS ONLY and composes the view live
  on every call (no cache, no projection, no staleness shortcuts). No
  db, no ids, no write path.

**The route family** `src/api/reporting-command-center-routes.ts`:

- `GET /api/reporting/command-center/:agencyId` — the ONLY route: the
  live-aggregated command-center view. Registered in `routes.ts`; the
  module is wired ONCE in `composition-root.ts` (with the /executions
  dependency added to the matrix-allowed set) and exposed through
  `application.ts`.
- AGENCY-SCOPED, SERVER-DERIVED SCOPE, authorized BEFORE any traversal:
  the route resolves the durable agency row and the caller's membership
  in THAT agency from durable state (users + agency memberships — never
  headers/claims). The work-item requirement "cross-agency data must 404
  (not 403-leak existence)" is implemented as the UNIFORM 404: a
  malformed, unknown or FOREIGN agency identifier is indistinguishable
  (the requireAgentAccess posture for agency-scoped records; asserted
  structurally AND behaviorally). Only a SUSPENDED membership or disabled
  identity is a 403 (intra-tenant, post-existence — asserted distinct);
  anonymous calls are 401 (fail closed). Any ACTIVE member may read.
- READ-ONLY BY CONSTRUCTION: exactly one GET route; no mutating verb is
  registered in the file (the router 405s POST/PUT/PATCH/DELETE); the
  route reads NO request body, validates NO DTO and reads NO query
  parameter — authority fields are STRUCTURALLY unreachable, not merely
  rejected (UI-AC-02).
- The aggregation scope (the agency's LIVE clients + each client's
  Workspaces) is SERVER-DERIVED at the route layer (/clients + /workspaces
  public contracts — matrix directions /reporting does not hold; the
  decision-room scope-as-data posture) and handed to the /reporting module
  as aggregation input. A client or workspace identifier is never accepted
  from the caller, so cross-agency data is structurally unreachable inside
  the composed view.
- Honest disclosures encoded in the response: the evidence-quality window
  bound (`evidence-authority-bounded-newest-first-listing-per-client`) and
  the risk basis string (declared goal risk constraints + operational +
  evidence-quality signals — never a synthesized assessment).

## Authority boundaries honored

- No new module; no second reporting engine; no write authority: the
  /reporting public contract exposes exactly TWO methods, both reads
  (asserted by the static architecture tests — no
  create/update/set/append/record/transition/delete/approve/reject/decide
  verb exists).
- Frozen matrix honored: /reporting ──→ /goals, /workflows, /executions,
  /evidence, /experiments, /metrics, /learnings (six-contract subset used;
  /metrics unused allowed; verified by tools/arch-check — 0 violations —
  and the boundary tests).
- PostgreSQL is authoritative persistence; the command center owns NO
  state (pure live aggregation; no projection migration exists — asserted
  by the architecture test).
- Caller-supplied identifiers are never authorization; agency/client
  isolation enforced server-side BEFORE dependent traversal; no secrets in
  domain records; no provider SDKs.
- "Risks" is a PRESENTATION of risk-relevant signals the composed
  authorities already expose in durable state (goal-declared risk
  constraints per architecture.md §7; failed/unresolved executions per the
  frozen v1.2 runtime rule "UNKNOWN execution outcome is unresolved, never
  success, and requires reconciliation"; blocked/paused instances; low-grade
  evidence). No risk engine, no re-assessment, no synthesized scores — the
  vocabulary has no score/severity/priority field (asserted by unit AND
  integration tests).

## Known limitations

- The evidence-quality posture is computed over the /evidence authority's
  bounded public listings (newest-first window per client) — a read-side
  presentation choice disclosed in the response (`window` field), not an
  authoritative recount of the unbounded append-only ledger.
- "Risks" surfaces exactly the risk-relevant signals the frozen matrix
  allows /reporting to compose (goal-declared risk constraints, failed and
  unresolved executions, blocked/paused instance counts, low-grade
  evidence counts). There is no separate risk-assessment authority on
  main, and /reporting's frozen matrix line holds no /policies or /audit
  direction — so policy-decision posture is NOT part of this surface (the
  /policies decision ledger remains reachable through its own
  agency-scoped route family). This is the frozen-architecture-consistent
  reading of "risks"; no risk engine was invented.
- Pending approvals derive from the two authority-exposed pending families
  the MKT-030 precedent established (experiments awaiting decision +
  workflow instances awaiting continuation). Creator-gate approvals and
  extension permission reviews live in authorities the frozen matrix does
  not allow /reporting to compose; they stay on their own surfaces.
- The aggregation iterates clients × workspaces sequentially (await per
  listing) — the same live-read posture the accepted MKT-030 aggregation
  uses; no pagination on the agency family yet (per-client drill-down
  tallies are included in the single response).
- The 9 environmental MinIO failures above (pre-existing, fails on
  pristine base, unrelated).
