## What was implemented

### 1. One auditable, explicit configuration surface (DEPLOY-AC-01)

`src/platform/config/config.ts`:

- **`describeConfig(config)`** — the REDACTED effective-configuration
  report. The shared bootstrap logs it ONCE per process as the structured
  `config.effective` record (`platform.startup` module) BEFORE any
  serving, so both entrypoints — control plane (`src/entrypoints/api.ts`)
  and workers (`src/entrypoints/worker.ts`) — put the exact effective
  capability topology on record: env, HTTP listener, database (system of
  record), object store, Redis (advisory-only role + endpoint, never the
  password), secret backend dir, auth/session/bootstrap-admin presence,
  worker tuning, queue (authority + retry/stale-claim windows) and the AI
  Runtime provider wiring. Secret-bearing settings are reduced to BOOLEAN
  presence flags whose names deliberately survive the observability
  layer's own secret-shaped-key scrubbing (`logger.ts` `redactSecrets`)
  — the auditable record still answers "was it configured?" for every
  capability instead of being double-redacted to noise. Unit-tested: no
  secret value (database URL credentials, internal token, bootstrap admin
  password, S3 signing key, Redis password, AI provider key) ever appears.
- **AI Runtime provider-adapter configuration (`aiRuntime` field)** —
  complete-or-absent EXACTLY like MKT-005's S3 surface: the documented
  default `MOS_AI_PROVIDER=none` wires no provider adapter; choosing
  `openrouter` requires `MOS_AI_OPENROUTER_ENDPOINT` (an http(s) URL) and
  `MOS_AI_OPENROUTER_API_KEY` together, with an optional
  `MOS_AI_OPENROUTER_TIMEOUT_MS` (default 30000, bounds 100..600000).
  Half-configured or malformed provider config aborts startup with a
  `CONFIG_INVALID` `ConfigError` — never a silent fallback to 'none'.

`src/composition-root.ts`:

- The **OpenRouterAdapter is wired** (the sanctioned composition-root
  adapter home the AI-AC-03 boundary tests reserve for exactly this
  wiring) from the explicit `MOS_AI_*` configuration, riding the platform
  `HttpCallPort` (fetch — zero provider SDKs, verified by the existing
  static boundary tests). It is surfaced on the bootstrap result as
  `runtime.aiProvider` (`RuntimeWiring`) behind the `/ai-runtime`
  `ProviderAdapter` CONTRACT — the module boundary is untouched, and
  callers supply it to `routeTask` exactly as the MKT-018 route contract
  documents ("the composition root wires the OpenRouter adapter; the
  integration test supplies a fake").
- **Startup ordering is now explicit and logged**
  (`bootstrapApplication`, shared by BOTH entrypoints):
  1. `loadConfig` — the explicit validated config (fail-fast;
     missing/ambiguous config never guesses);
  2. `buildCore` — every capability constructed from that config
     (db, queue, object store, sandbox driver, AI provider adapter,
     secrets, advisory Redis cache/locks, outbound HTTP);
  3. `config.effective` logged once (the auditable surface);
  4. `runMigrations` — startup VERIFIES the migration state (applies
     missing migrations, hard-fails on checksum drift of applied ones),
     then logs `platform.migrations.verified` with the applied count and
     latest migration name;
  5. `ensureBootstrapAdministrator` (optional, idempotent).

Graceful shutdown ordering (pre-existing, now TESTED): SIGTERM on the
worker stops claiming, DRAINS in-flight jobs to completion, closes the
database and exits 0 (`job.succeeded` precedes `worker.stopped` in the
structured record stream — asserted by the integration test); SIGTERM on
the control plane logs `api.stopping`, closes the listener and the
database pool, exits 0.

### 2. Queue recovery without Redis as authority (DEPLOY-AC-02)

`tests/integration/queue-recovery-no-redis.test.ts` — the recovery test,
run with REDIS ABSENT ENTIRELY (`MOS_REDIS_URL=''` — the documented
degenerate advisory adapters; no redis-server process exists anywhere):

1. a continuous worker (explicit worker id, batch 1, explicit 60s
   stale-claim window) claims a long job; a second job stays pending
   behind it (mid-queue);
2. the worker is SIGKILLED mid-execution;
3. the authoritative PostgreSQL rows show RECONCILABLE state: the job is
   durably `running`, claimed by the dead worker, with its attempt
   recorded as an UNRESOLVED `running` attempt row (never fabricated
   success, never silent loss — the v1.2/v1.3 posture);
4. a fresh worker INSIDE the live-claim window completes the pending
   work and does NOT blindly replay the crashed claim (identical
   authoritative state, still owned by the dead worker);
5. after the claim ages past an explicit 1200ms window (the test waits
   deterministically on the authoritative `claimed_at` age), a fresh
   worker with that window RECOVERS the job from PostgreSQL alone:
   stale-claim reclaim → re-execute → complete, at-least-once (attempts
   1 → 2), with the append-only attempt ledger recording BOTH the crash
   window (attempt 1, `running`, unfinished) and the recovery execution
   (attempt 2, `succeeded`);
6. exactly ONE job row per idempotency key with ONE terminal state, and
   resubmitting the same key + payload converges on the SAME durable job
   identity (no duplicated final state).

PostgreSQL (`platform_jobs` / `platform_job_attempts`) is the authority
at every point — all assertions read the authoritative rows directly.
(Complementary coverage that already existed and is unchanged: the
MKT-005 `queue-authority.test.ts` Redis-down/no-Redis flows, and the
MKT-011 `pooled-executions.test.ts` frozen UNKNOWN semantics — an
execution in `unknown`/`reconciling` is never blindly resolved by stale
redelivery; only explicit reconciliation resolves it.)

### 3. Deployment topology integration test (DEPLOY-AC-01)

`tests/integration/deployment-topology.test.ts` — boots the control plane
and workers as REAL OS subprocesses against the REAL embedded PostgreSQL
with an EXPLICIT configuration (fs object store, secret backend dir,
internal API token, bootstrap admin, worker id, queue windows, the
OpenRouter provider adapter, NO Redis) and proves:

- POSITIVE: `api.started` + the single `config.effective` record with the
  redaction contract; startup migration verification cross-checked
  against `platform_schema_migrations` in the authoritative store; the
  `/api/platform/health` liveness answer; the worker boots from the SAME
  config surface (its own `config.effective` + migration verification
  records) and drains cleanly; the composed topology moves real work
  (submit → durable queue → worker → object-store artifact, asserted in
  PostgreSQL); the sandbox capability answers on its Workspace-scoped
  surface and the AI Runtime model registry answers; graceful SIGTERM
  ordering for both entrypoints (worker drains in-flight work first).
- NEGATIVE (explicit-config contract — fail loudly, never guess):
  missing `MOS_DATABASE_URL` aborts BOTH entrypoints (structured
  `*.startup.failed` record, non-zero exit — and the harness spawns with
  an exact env so a missing value is genuinely missing, not rescued by
  ambient environment); invalid enum/integer values abort startup;
  half-configured S3 and half-configured AI provider abort startup
  (complete-or-absent); an unreachable database aborts startup (no
  silent degraded boot).

### 4. Test-harness extensions (backward compatible)

`tests/integration/helpers/harness.ts`:

- `spawnWorker` gains an options parameter (`{ drain?: boolean }`, default
  `drain: true` — the unchanged legacy behavior). Continuous mode spawns
  the production claim/execute loop, resolves only once `worker.started`
  is logged, and attaches the stdout collector BEFORE waiting so no early
  startup record is lost (crash-recovery tests kill it mid-job
  deterministically).
- `spawnApi` now attaches its stdout collector before waiting for
  `api.started`, so startup records (`config.effective`,
  `platform.migrations.verified`, `api.started`) are all captured.
- `spawnEntrypointExpectFailure(entry, env)` — spawns an entrypoint with
  the EXACT env given (absent values are not inherited from the parent
  process) and resolves on exit; the negative tests assert non-zero exit
  codes and the structured `*.startup.failed` stderr records.

## Runbook — the frozen topology, exactly how it starts

### Prerequisites

- Node ≥ 24 (or Bun) with TypeScript-style ESM `.ts` imports (the repo
  runs on plain `node` with type stripping);
- PostgreSQL (any instance; the test harness uses `embedded-postgres`
  18.4 binaries — it downloads libicu60 once into `.test-deps/` when the
  host lacks it);
- a directory for the file secret backend, containing `<handle>.secret`
  files for every credential the deployment must resolve.

### Commands (exact)

```bash
bun install

# control plane (explicit config; picks an ephemeral-free port 8080 by default)
MOS_ENV=prod \
MOS_DATABASE_URL='postgres://user:pass@host:5432/mos' \

# workers (SAME explicit config surface + worker tuning)
MOS_ENV=prod \
MOS_DATABASE_URL='postgres://user:pass@host:5432/mos' \
MOS_INTERNAL_API_TOKEN='<service token>' \
MOS_OBJECT_STORE=fs MOS_OBJECT_STORE_DIR=/var/lib/mos/objects \
```

adapters only — correctness NEVER depends on it (DEPLOY-AC-02; the queue
authority, locking fallback and all recovery paths are PostgreSQL).
Operational drain: run the worker entrypoint with `--drain` (relayed
outbox → queue → recovery fixpoint → exit 0).

### Sandbox + AI Runtime wiring notes

- The **sandbox service** starts as part of every bootstrap: the
  `InProcessSandboxDriver` is wired at the composition root into the
  `/executions` sandbox lifecycle (MKT-012). No runtime knob exists for
  it because no alternative substrate adapter exists yet (real isolation
  substrates are later composition-root adapters, per the frozen runtime
  rules). Persistent sandboxes stay Workspace-scoped and leased to
  Executions — `execution_id` is never sandbox identity.
- The **AI Runtime** starts with the merged routing/registry (MKT-018)
  and the explicit provider-adapter wiring above. The adapter stays
  behind the module boundary (the `ProviderAdapter` contract); no
  provider SDK exists anywhere in `src/` (static boundary tests).

### Recovery operations

- A worker killed mid-job leaves the job durably `running` (claimed,
  attempt recorded). Inside `MOS_QUEUE_STALE_CLAIM_MS` nothing replays
  it; after the window, any worker reclaims it at-least-once or deads it
  when attempts are exhausted. Redis plays no role in any of this.
- The worker drain fixpoint also runs the pooled recovery sweep
  (dead-job execution terminalization, deferred-paused re-arm, stale
  sandbox-lease release). Executions in `unknown` are NEVER auto-resolved
  — only explicit reconciliation moves them (frozen rule).

## Honest limitations

- **The 9 pre-existing s3-object-store integration failures** (upstream
  MinIO archive shutdown, `HTTP 410 Gone` from `dl.min.io` for every
  release) are disclosed above with pristine-base reproduction evidence;
  they are environmental, pre-date this branch, and are unrelated to
  MKT-033's scope. All 16 new MKT-033 integration tests pass.
- **The wired OpenRouterAdapter has no production route-time caller yet.**
  MKT-018's route layer deliberately does not expose `routeTask` as an
  HTTP route ("the adapter is supplied by the caller at route time"); the
  composition-root wiring here makes the adapter available on the
  bootstrap result (`runtime.aiProvider`) for exactly those callers, and
  the deployment test proves the wiring decision (provider, endpoint,
  timeout, key presence) on the auditable startup surface plus the
  fail-fast posture for half-configured providers. First end-to-end AI
  invocation through the cascade is the MKT-034 E2E work item's concern.
- **The sandbox substrate remains the in-process simulated driver**
  (MKT-012's frozen default). This Work Item proves it starts and its
  surface answers; real isolation substrates are future composition-root
  adapters behind the SAME `SandboxDriver` port.
- **The recovery test's "no blind replay" proof is time-bounded by the
  explicit claim window**, exactly as the frozen queue contract defines
  reclaim eligibility; a deployment that sets `MOS_QUEUE_STALE_CLAIM_MS=0`
  opts out of automatic reclaim (MKT-001 behavior) and requires operator
  action for crashed claims — documented, not hidden.
- Startup does not (and per OBS-AC-02 must not) persist boot records into
  a queryable table; the auditable startup evidence is the structured
  record stream plus the authoritative migration table.
