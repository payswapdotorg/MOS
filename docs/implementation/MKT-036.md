# MKT-036 — Versioned Domain Pack framework

Work Item: MKT-036 (spec/work-item-v1.3-overrides.md: "implement the
versioned Domain Pack composition contract, installation scope, immutable
versions, dependency/compatibility checks, and authority restrictions";
dependencies: MKT-007, MKT-008, MKT-022 — all merged at base b46b903).

Requirements: PACK-001 — "Provide versioned Domain Packs that specialize
MarketingOS without creating alternate platform authorities."

Acceptance:

- PACK-AC-01 — Domain Pack version is immutable after publication and
  installed version is recorded against the authorized Workspace/Client
  context — DB/integration test.
- PACK-AC-02 — Domain Pack workflows use existing Workflow, Execution,
  Evidence, AI Router, Credential, Policy and Audit authorities — static
  architecture test.
- PACK-AC-03 — pack-owned Client data cannot cross Client boundaries;
  Agency-scoped reusable pack artifacts are explicitly distinguished —
  security/static test.

## What was implemented

Migration `030_domain_packs.sql` (the only new tables; number 030 was
free on the base — 028 is the last applied):

- `domain_packs` — the immutable versioned PACK REGISTRY: one row per
  (publisher, pack_key, version), DB-UNIQUE-fenced; UPDATE and DELETE
  rejected outright by triggers (published pack versions are immutable —
  domain-pack-v1.3.md §4; the playbook-versioning and extension-registry
  precedent). Columns: identity (pack_key/publisher/version),
  display_name/description, the platform compatibility range
  (compat_min/compat_max — catalog data), `required_packs` (exact
  published (publisher, packKey, version) dependency references),
  `artifacts` (the §2 artifact declarations, each carrying the §5
  explicit scope), idempotency/fingerprint/provenance. NO tenant
  columns: a pack version is global catalog state, exactly like an
  extension version.
- `domain_pack_installs` — the INSTALLED-VERSION RECORDS (PACK-AC-01):
  one row per (workspace, pack version), DB-UNIQUE-fenced; the canonical
  agency→client→workspace scope chain re-fenced by triggers; scope,
  pinned pack version, idempotency identity and provenance IMMUTABLE;
  frozen lifecycle `installed ⇄ disabled + terminal uninstall` (born
  'installed', 'uninstalled' is a tombstone); CAS `version`.
- `domain_pack_artifacts` — the ARTIFACT SCOPE RECORDS (PACK-AC-03):
  one row per declared artifact materialized AT INSTALL TIME against the
  installing context. THE structural §5 distinction: `scope='client'`
  requires `client_id NOT NULL` (pack-owned Client data confined to the
  installing Client boundary); `scope='agency-reusable'` requires
  `client_id NULL` (the explicitly-declared Agency-scoped reusable
  artifact — e.g. a playbook template). APPEND-ONLY (UPDATE/DELETE
  rejected — cross-client re-parenting is impossible at the storage
  layer); consistency fence (the artifact's install must pin the same
  pack in the same workspace/agency; a client-scoped artifact's client
  must equal its install's client).
- Closed-vocabulary CHECKs: the 14 artifact kinds (domain-pack-v1.3.md
  §2 bullets) and the 2 artifact scopes (§5) are DB CHECKs; the §21
  material-key validator (`domain_packs_payload_has_no_material_keys`)
  fences every jsonb payload. NO column capable of holding secret
  material anywhere. NO workflow/execution/evidence/credential/audit/Job
  table, column or trigger (PACK-AC-02 at the storage layer).

Module `/domain-packs` (`public.ts` + `internal/module.ts` +
`internal/store.ts`, replacing the MKT-001 boundary stub):

- the MANIFEST CONTRACT: identity + display metadata + compatibility
  range + `requiredPacks` + `artifacts` (each artifact: closed §2 kind,
  bounded name unique within its kind, description, closed §5 scope,
  bounded JSON payload);
- §4 WORKFLOW-TEMPLATE CONFORMANCE: every `workflow-template` payload is
  validated at publication through the /workflows authority's OWN
  `validateWorkflowDefinitionContent` (imported from the /workflows
  PUBLIC contract — the ONLY cross-module import; matrix-allowed). The
  framework has NO workflow engine; pack workflow templates are DATA
  that materializes and executes only through /workflows + /executions;
- PUBLICATION: manifest guard (shape + vocabularies + duplicate identity
  + material keys + self-dependency rejection) → insert with
  (publisher, pack_key, version) fence → re-publication is a 409, a new
  version is a new row;
- INSTALLATION (PACK-AC-01): scope-as-data (the SERVER-SUPPLIED
  canonical workspace ownership — the /extensions posture; the module
  has no /clients//workspaces dependency), dependency checks (every
  declared required pack must be PUBLISHED — fail-closed
  InvalidRequestError), then ONE transaction inserting the install AND
  materializing the artifact scope records with the §5 distinction
  resolved against the installing context; idempotent replay
  convergence on the (workspace, pack version) fence;
- LIFECYCLE: CAS transitions on the frozen
  installed ⇄ disabled + terminal-uninstall table;
- ARTIFACT READS: by-id (content served from the IMMUTABLE registry row
  through the scope record), the workspace listing (the workspace's OWN
  install artifacts), and the agency listing (ONLY
  `scope='agency-reusable'` records — the §5 explicit distinction as a
  query; Client-scoped pack-owned data never aggregates at agency
  scope; cross-client aggregation without explicit governance is not
  implemented and not expressible in the scope vocabulary).

Dependency posture (frozen matrix: /domain-packs ──→ /agencies, /clients,
/workspaces, /goals, /playbooks, /workflows, /executions, /agents, /jobs,
/evidence, /metrics, /experiments, /learnings, /extensions, /policies,
/audit): the framework composes ONLY `/workflows` public (its pure §4
validator) at module level — every other allowance stays deliberately
unused (the /agents precedent). Runtime composition with the Execution,
Evidence, AI Router, Credential, Policy and Audit authorities happens
when pack workflows EXECUTE through /workflows + /executions; the
install scope is resolved at the ROUTE layer from canonical
/workspaces ownership. No /policies gate on install: the frozen POL-001
dimension set has no pack dimension (inventing one would modify frozen
vocabulary; borrowing the 'extension' dimension would misapply it) —
authorization is the /agencies membership authority at the route layer,
exactly the /playbooks precedent.

API routes (`src/api/domain-packs-routes.ts`, wired into `routes.ts` +
`composition-root.ts` + `application.ts`): 12 routes —

- `POST /api/domain-packs` (publish: platform admin OR agency
  owner/admin — the /extensions publisher posture), `GET /api/domain-packs`
  (list; any active member), `GET /api/domain-packs/:packId` (read);
- `POST /api/workspaces/:workspaceId/domain-pack-installs` (install:
  owner/admin; scope SERVER-DERIVED from the canonical workspace
  ownership), `GET .../domain-pack-installs` (list, every state),
  `GET .../domain-pack-installs/:installId` (uniform 404 for foreign),
  `POST .../disable`, `POST .../enable`, `POST .../uninstall` (CAS edges);
- `GET /api/workspaces/:workspaceId/domain-pack-artifacts` (the
  workspace's own install artifacts, both scopes, explicit scope field),
  `GET /api/agencies/:agencyId/domain-pack-artifacts` (agency-reusable
  ONLY), `GET /api/domain-pack-artifacts/:artifactId` (boundary-checked
  by-id read: client-scoped needs the owning client's boundary through
  requireClientAccess; agency-reusable needs the owning agency; uniform
  404 for foreign — no cross-tenant oracle).

Every mutation resolves the canonical owner BEFORE authorize (§23),
authorizes through the SAME /agencies membership authority, rejects
identity/scope/lifecycle/provenance authority fields and material-shaped
keys in the DTOs, and emits `recordMutationAudit`
(`domain_packs.version.published`, `domain_packs.installed`,
`domain_packs.install.disabled|enabled|uninstalled` — the
underscore-segment audit-action vocabulary).

## Security/concurrency posture

- Server-side Client isolation BEFORE dependent traversal (uniform 404
  for foreign/unknown; install scope always the canonical workspace
  owner).
- Caller-supplied identifiers/authority fields never authorization
  (DTO rejection lists; §3).
- Negative regressions: republish 409; forged authority fields 422;
  terminal-uninstall transitions 409; direct-SQL immutability, scope,
  scope-shape and append-only rejections; foreign 404 uniform with
  unknown; role gating (collaborator cannot publish/install); anonymous
  401.
- No secrets in pack records (§21 module guard + DB CHECKs; CRED-001).
- No provider SDKs in the module (static test).

## Known limitations (honest disclosure)

- No pack CONFIGURATION surface (no configure/authorize install subset):
  extension bindings resolve through the /extensions install lifecycle
  which owns configuration; the frozen domain-pack contract defines
  none for the framework.
- Agency-reusable artifacts materialize per install (two installs of the
  same pack in one agency produce two reusable records of the same
  (pack, kind, name) — each carrying its materializing install as
  provenance; listings return both, bounded).
- PACK-AC-02 is proven statically/structurally: the framework routes
  pack workflow materialization+execution through /workflows +
  /executions and imports no runtime authority; the full runtime
  composition (a pack workflow actually executing with AI
  routing/credentials/evidence) belongs to MKT-037+ work items.
- The compatibility range is validated as catalog data (shape) only —
  like the extension registry; resolution against a platform version
  belongs to the Deployment authority (marketing-cloud-deployment-v1.4).
