  `policy_reference_id` (the consulted /policies version of the last
  successful gate; fenced to move only on validation/gate edges), the
  `runtime_requirements` (EXACTLY the closed one-key runtimeClass shape
  with the infrastructure-identity denylist CHECK — DEPLOY-AC-09 at the
  storage layer), the `trigger_config` (closed trigger shapes; schedule
  triggers require a config), the lifecycle `status` (closed 9-state
  CHECK) and the CAS `version`.
- `deployment_events` — the APPEND-ONLY deployment history ledger
  (lifecycle transitions, validation reports, full version-selection
  revisions, execution-request references): UPDATE and DELETE rejected
  by triggers (the migration 015/018/025 pattern — DEPLOY-AC-06's
  storage half); the `(deployment_id, idempotency_key)` UNIQUE fence
  makes duplicate delivery of the same logical command converge
  (§8-style); server-derived provenance columns on every row
  (implementation-contract §3); §21 material-key CHECKs on every jsonb
  payload.
- Frozen-machine storage backstops: the transition trigger encodes
  EXACTLY the contract's drawn edges (draft→validating→ready→active;
  ready→blocked; active→paused/disabled/redeploying/rolling_back;
  paused/redeploying/rolling_back→active; blocked/disabled terminal);
  the version-selection fence permits selection-column mutation ONLY on
  the (redeploying|rolling_back)→active completion edges — redeploy/
  rollback change FUTURE version selection only.

Module `/deployments` (`public.ts` + `internal/module.ts` +
`internal/store.ts` + `internal/resolution.ts`, replacing the MKT-001
boundary stub):

- **Dependency posture (the headline architectural decision):** the
  frozen module-dependency-matrix has NO `/deployments` line, so
  /deployments holds an EMPTY allowance list in the static checker.
  EVERY consumed public contract therefore arrives through DECLARED
  STRUCTURAL PORTS (the /integrations MKT-023 precedent for /clients +
  /evidence, extended to the whole dependency surface): narrow typed
  views of /workspaces, /playbooks, /workflows (read-only),
  /domain-packs, /extensions, /integrations, /policies, /credentials
  (reference-only) and /executions (createExecution — the
  request-execution surface only), satisfied structurally by the real
  instances and wired at the composition root. There is NO import of
  another module anywhere under src/modules/deployments — not even
  type-only (verified by tools/arch-check and
  tests/architecture/deployments-boundary.test.ts).
- **The frozen lifecycle** exactly as drawn; `validating` is the atomic
  in-flight leg the compound `validateDeployment` passes through (never
  externally targetable); `blocked`/`disabled` are terminal (the frozen
  contract lists no exit edge — the operator's path forward is a NEW
  deployment, never a resurrected row).
- **`validateDeployment`** (Configure→Validate): the compound
  draft→validating→ready leg in ONE transaction, gated by the full
  resolution contract; ANY failed check rejects the operation BEFORE any
  state change (the deployment stays draft) and the failed checks are
  the error's details — no partially validated deployment becomes READY,
  let alone ACTIVE.
- **`transitionDeployment`** — the single authorized lifecycle mutation
  port (the transitionWorkflowInstance/transitionExecution house
  pattern): one frozen edge per call, CAS-guarded, idempotency-fenced.
  Every entry into ACTIVE (deploy from ready, resume from paused,
  redeploy/rollback completion) re-runs the FULL gate FRESH — the
  strictest reading of the frozen resolution contract. The five
  frozen policy operations (deployment.deploy/pause/resume/redeploy/
  rollback) are fail-closed gated through the /policies
  deployment-dimension evaluation (only an explicit recorded allow
  proceeds); disable and block are ungated control edges (disclosed
  below).
- **Redeploy/rollback:** `active→redeploying` records the PENDING new
  selection on the ledger (the row stays pinned); the completion edge
  runs the full gate against the pending selection and applies it
  atomically (future version selection changes HERE — DEPLOY-AC-06).
  `active→rolling_back` targets a prior selection-bearing ledger
  revision; the completion edge applies the target the same way.
- **`requestDeploymentExecution`** — the request-execution surface:
  createExecution through the /executions public contract (taskLink
  external-request referencing the deployment + trigger, executionKind
  'deterministic', runtimeClass = the deployment's DECLARED class),
  recorded on the append-only ledger. There is deliberately NO
  dispatch, NO retry, NO workflow-instance materialization and NO
  sandbox/lease surface (DEPLOY-AC-07/09).
- **The pure resolution evaluator** (`internal/resolution.ts`): the
  nine named checks (authorization, playbook-version, workflow-versions,
  domain-packs, capabilities, credentials, policy, runtime, triggers)
  over already-resolved port snapshots — pure, deterministic, unit
  tested for every dependency failure; the version-constraint matcher
  (null / '*' / exact / '^major' — anything else fails closed); the §21
  material-key guard; the closed runtime-class guard.

API surface (`src/api/deployments-routes.ts`, registered in routes.ts;
`deployments` wired into application.ts and the composition root):
thirteen frozen routes under `/api/workspaces/:workspaceId/deployments`
— configure (create), list, read, history ledger, validate, activate,
pause, resume, disable, block, redeploy, rollback, request-execution.
No delete route; no dispatch/retry surface. Every mutation route
resolves the canonical owner from durable state BEFORE
authorize/validate/execute, authorizes against the SAME /agencies
membership authority (mutations owner|admin; reads any active member),
yields UNIFORM 404s for unknown/foreign identifiers, and rejects
authority/provenance/material-shaped fields on every DTO.

## Honest limitations / disclosures

1. **The frozen matrix grants /deployments no direct module imports.**
   Every consumed contract is a structural port wired at the
   composition root — the sanctioned /integrations precedent, not a
   redesign. The trade-off: the ports are re-declared narrow types
   (drift between a port and the real public contract surfaces at the
   composition-root type check, which is exactly where they are wired).
2. **`validating` is an atomic in-flight state, never a durable
   resting state.** The compound validate operation passes the row
   THROUGH it in one transaction; a failed validation leaves the
   deployment in DRAFT (the operation is rejected — "invalid
   transitions are rejected" analog). The frozen machine's edge set is
   implemented EXACTLY as drawn; nothing was added.
3. **Every entry into ACTIVE re-runs the full gate** (deploy, resume,
   redeploy/rollback completion) — the strictest reading of the frozen
   resolution contract ("Activation/redeployment must validate … before
   activation"). Cost: redundant external reads on resume; benefit:
   dependency drift can never ride a paused deployment back into
   ACTIVE.
4. **Fail-closed policy posture:** the five frozen deployment actions
   (deploy/pause/resume/redeploy/rollback) require an EXPLICIT
   deployment-dimension policy allow (deny/unknown → 403 POLICY_DENIED
   before any transition) — the POL-001 posture the /integrations and
   /extensions modules established. Environments without a declared
   deployment policy cannot deploy (fail closed, by design).
   `disable` and `block` are ungated control edges (the frozen
   dimension vocabulary lists exactly deploy/pause/resume/redeploy/
   rollback); a deployment-dimension 'execute' operation was NOT added
   for request-execution (not in the frozen vocabulary — boundary
   checks only).
5. **Integration capability version constraints:** the integration
   adapter REGISTRY carries no per-capability versions (the frozen §20
   contract has no versioned adapters), so an integration requirement
   with a versionConstraint is validated for REGISTRATION + a CONNECTED
   Client connection; the constraint value is persisted but has no
   registry version to match against (the extension and domain-pack
   capabilities ARE version-matched through their registries).
6. **Schedule/event triggers are declarative only** in this Work Item:
   requestDeploymentExecution serves MANUAL triggers; the scheduler/
   event wiring belongs to the runtime authority (a later Work Item) —
   the frozen contract says deployment requests execution, it does not
   build a trigger engine.
7. **A failed redeploy/rollback completion leaves the deployment in
   redeploying/rolling_back** (retryable after fixing the dependency):
   the frozen table has no exit edge except → active, and taking that
   edge without a green gate would violate the resolution contract.
   The operator's recourse is retry or a new deployment.
8. **The request-execution surface creates the Execution identity**
   (external-request task link, deterministic kind, the declared
   runtime class) through /executions' public contract. It does NOT
   materialize workflow instances or dispatch work — that belongs to
   /workflows and the runtime (DEPLOY-AC-07's authority boundary).
9. Deployment configuration is **immutable from creation** (the Vercel
   model): a mis-configured draft is superseded by a new deployment;
   the selection columns move only through redeploy/rollback completion
   (the DB fence enforces this even against direct SQL).
