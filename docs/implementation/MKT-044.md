## What was implemented

**Migration choice — DISCLOSED: NO MIGRATION (live derivation).** The
module owns NO durable state: there are no `client_memory_*` tables, no
snapshot store, no retrieval index and no recompute/converge operation —
nothing to rebuild, because nothing is stored (the REQUIRED no-migration
preference; the /reporting live-aggregation precedent of MKT-029/030 and
the exact /profit-intelligence house precedent of MKT-043). The
expected-migration list is UNCHANGED and this delivery takes no migration
number at all. Every memory view is COMPOSED at read time from the
authorities' own rows through their public contracts.

**Retrieval technology — DISCLOSED: NONE EXISTS.** §6 makes
retrieval/index technology non-authoritative; this delivery adds NO index
and NO cache at all (the disclosed choice): the retrieval surface (the
kind-filtered route) is a pure filter over the DERIVED memory items —
search over derived data, never a second query authority. Had an index
been added it would be a rebuildable derived artifact with a disclosed
recompute path; the no-migration live derivation makes the question moot.

Module `/client-memory` (`public.ts` + `internal/` only — the
reporting/profit-intelligence house shape):

- `src/modules/client-memory/public.ts` — the frozen contract:
  `CLIENT_MEMORY_PROJECTION_VERSION = 'cm-proj-v1'` (the frozen projection
  vocabulary; views are versioned, never silently restated — the same
  discipline as `pi-calc-v1`), the closed `CLIENT_MEMORY_RECORD_KINDS`
  vocabulary (client, goal, playbook, playbook-version, deployment,
  evidence, experiment, outcome, decision, learning — exactly the §6
  record-kind set, with the playbook-version refinement of the playbook
  kind), the exported `CLIENT_MEMORY_SOURCE_AUTHORITIES` authority map
  (policy-visible data lineage), the exported
  `CLIENT_MEMORY_SELECTION_RULES` record (which records enter the memory
  surface under which freshness/selection rules — structured, explicit,
  no hidden rules; every entry ships verbatim in every response), the
  `ClientMemoryItem` shape (canonical citation `kind`+`id`, bounded
  `summary` under the frozen 280-char bound, the authority's own
  lifecycle `status` surfaced verbatim, the authority's own
  `workspaceId` scope and `recordedAt` timestamp, `links` citing
  canonical records of the composed kinds), the three view shapes
  (client / workspace / kind-slice) and `ClientMemoryModuleApi` —
  EXACTLY THREE read methods, zero mutation verbs.
- `src/modules/client-memory/internal/memory-projection.ts` — the PURE
  projections (no I/O): per-kind item builders (each citing the canonical
  record; decision items cite the ledger's evidence/experiment/
  predecessor/successor/deployment/learning references; evidence items
  surface the quality grade and the supersession link; outcome items cite
  the decision id and map the as-expected flag honestly), the frozen
  selection rules applied (superseded evidence predecessors counted
  `supersededEvidenceCount` and never presented — the metrics
  latest-wins discipline applied to the evidence ledger; the client's OWN
  client-scoped playbooks only — agency-scoped reusable IP is the
  disclosed exclusion; observed outcomes on ACCEPTED decisions — the
  exactly-once outcome surface; every goal/experiment/decision/learning
  lifecycle state retained — history is memory), the deterministic
  ordering (kind vocabulary order, then recordedAt DESC, then id ASC),
  the workspace covering rule (client-wide + own workspace), the kind
  slice (a pure filter over the derived items) and the projection
  disclosure composition.
- `src/modules/client-memory/internal/client-memory-module.ts` — the
  live read model: gathers one Client's authority rows through the nine
  composed authorities' PUBLIC CONTRACTS (clients, workspaces, goals,
  playbooks, deployments, evidence, experiments, decisions, learnings —
  the frozen dependency-matrix line), hands the plain snapshot to the
  pure projections and composes the view. Canonical Client/Workspace
  ownership resolves FIRST (unknown/tombstoned Client, or unknown/
  tombstoned/foreign Workspace → the uniform 404 upstream, before any
  dependent traversal; the workspace must be among the Client's LIVE
  enumeration). Zero mutation methods; zero owned state.

Routes (`src/api/client-memory-routes.ts`, registered additively in
`src/api/routes.ts`; module exposed additively in
`src/api/application.ts` and `src/composition-root.ts`) — EXACTLY THREE
GETs, read-only by construction:

- `GET /api/client-memory/:agencyId/clients/:clientId` — the Client's
  operating memory (the full governed projection).
- `GET /api/client-memory/:agencyId/clients/:clientId/workspaces/:workspaceId`
  — the Workspace's memory slice (the covering rule: client-wide items +
  the workspace's own items).
- `GET /api/client-memory/:agencyId/clients/:clientId/records/:kind` —
  the kind-filtered retrieval over the PROJECTED records (a path selector
  over the frozen record-kind vocabulary; an unknown kind is the uniform
  404 — fail-closed, no vocabulary oracle). Search over DERIVED data:
  the full memory composes first through the same live derivation, then
  ONE vocabulary kind's items are presented — never a second query
  authority.

The scope is SERVER-DERIVED on every read: the authenticated identity +
the durable agency membership (suspended member 403, anonymous 401
fail-closed) + live-client/workspace state; authorization is re-resolved
FRESH in the execute step of every route. Tenant identity can never
arrive via DTO — no request body, no DTO validation, no query parameters
(the platform router strips the query string before handlers run; proven
statically). The uniform 404 covers foreign ≡ unknown ≡ malformed
agencies, clients, workspaces AND record-kinds (no cross-tenant
existence oracle).

**Outcome composition — DISCLOSED.** There is no separate outcome
authority today; the canonical v1.5 outcome surface is the Decision
Ledger's observed outcome (recorded exactly once on an ACCEPTED decision
with its execution/deployment/learning references — MKT-042). Outcome
memory items are composed from those canonical observed outcomes and
cited BY the decision id. Cross-record citations name canonical ids of
the composed kinds ONLY — references to records of authorities outside
the frozen composition vocabulary (/executions, /workflows) are not cited
because §6 lists no execution/workflow records for client memory.

## Boundaries

- DERIVED, NEVER AUTHORITATIVE: the module exposes ZERO mutation methods
  over ANY authority (proven statically: no mutation verb in the route
  file; the public contract exposes exactly three read methods; the
  module internals contain ZERO SQL — all authority access is through the
  composed public contracts; the composition root wires NO db/ids into
  the module). No migration is owned, so the expected-migration list is
  unchanged (asserted by the pre-existing infra-adapters test).
- READ-ONLY BY CONSTRUCTION: GET routes only; mutating verbs are 405 at
  the router; after every read/probe the authoritative rows are
  byte-identical (proven in the integration battery via SQL digests over
  goals/evidence/experiments/decisions/learnings/deployments/playbooks/
  playbook_versions/clients).
- VIEWS ARE COMPUTED, NOT STORED TRUTHS: every count is cross-checked
  against DIRECT SQL ground truth over the authority tables in the
  integration tests; a live-follow test mutates through the REAL
  authority APIs (new evidence, new recorded decision, new appended
  learning) and observes the memory follow on the very next read; the
  same inputs + the same projection version derive byte-identical views
  (pinning), and a version bump would be disclosed in the response
  (`projectionVersion` + the full `projection` disclosure on every view).
- ISOLATION BEFORE TRAVERSAL: canonical ownership resolves before any
  dependent read; cross-tenant identifiers are the uniform 404; the
  isolation battery covers anonymous 401, foreign agency/client/
  workspace/kind 404, malformed/unknown 404 and suspended 403.
