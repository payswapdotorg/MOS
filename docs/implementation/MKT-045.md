## What was implemented

**Migration choice — DISCLOSED: NO MIGRATION (live derivation).** The module
owns NO durable state: there are no `ai_operator_*` tables, no persisted
queue and no refresh operation — nothing to rebuild, because nothing is
stored (the disclosed AC-4 choice; the /reporting and /profit-intelligence
live-derivation precedents of MKT-029/030/043). The expected-migration list
is UNCHANGED; migration 038 remains reserved for the MKT-048 sibling, and
this delivery takes no migration number at all. Every attention item is
COMPUTED at read time from the authorities' own rows through their public
contracts; authority changes are visible on the very next read (the
live-follow proof).

Module `/ai-operator` (`public.ts` + `internal/` only — the
profit-intelligence house shape):

- `src/modules/ai-operator/public.ts` — the frozen contract:
  `AI_OPERATOR_RANK_VERSION = 'ao-rank-v1'` (the frozen rank calculation
  version; scores are versioned, never silently re-stated),
  `ATTENTION_CATEGORY_VOCABULARY_VERSION = 'ao-categories-v1'` + the frozen
  eight-category §7 vocabulary (`ATTENTION_CATEGORIES`), the exported
  `AI_OPERATOR_ASSUMPTIONS` set (category base weights, severity/recurrence
  modifier ranges, weak-evidence grades + threshold, margin pressure
  threshold ratio, capacity demand minutes per job + trigger ratio, the
  per-category caps — structured, explicit, no hidden constants, shipped
  verbatim in every response), `ATTENTION_SOURCE_REF_KINDS` (the closed
  source-reference vocabulary — the /profit-intelligence pass-through kinds
  included so consumed figures' canonical references are never dropped),
  `ATTENTION_ACTION_CONTRACT_KINDS` (the closed consequential-action-contract
  vocabulary — the EXISTING MOS surfaces a ranked candidate flows through),
  `ATTENTION_RATIONALE_FACTOR_KEYS` (the closed rationale-factor keys), the
  `AttentionItem` shape (deterministic `itemId`, category, tenant scope,
  `priorityScore`, `rank`, `sourceRefs`, structured `rationale`,
  `actionContract`, `scoreAssumptionKeys`), the three view shapes (agency
  queue, client slice, item detail — each carrying the
  `RankingDisclosure`), and `AiOperatorModuleApi` — EXACTLY THREE read
  methods, zero mutation verbs.
- `src/modules/ai-operator/internal/attention-derivation.ts` — the PURE
  derivations + the deterministic ranking core (NO I/O, NO clock reads, NO
  randomness — the same authority rows derive byte-identical items in
  byte-identical order at ANY time):
  - blocked work (instance blocked/paused, execution pausing/paused,
    deployment blocked/disabled — the operator path is a NEW deployment —
    and job expired/declined; the recurrence modifier counts FAILED
    executions linked to the same workflow instance, capped);
  - approvals (policy decisions with outcome `unknown` — the actions stuck
    at the policy gate; severity by reason code `no-active-policy` 10 /
    `no-matching-rule` 8 / default 5; the recurrence modifier counts OTHER
    undecided decisions on the SAME dimension, capped; the client
    narrowing keeps only this client's decisions in the client slice);
  - client risk (CURRENT weak-grade evidence — D/E/F per the frozen
    assumption set; superseded records never count; the item exists at/above
    the frozen threshold; severity = the capped weak count; the full grade
    distribution ships in the rationale);
  - anomalies (executions failed / `unknown` / `reconciling` — UNKNOWN is
    the worst posture, never success; failed + UNSAFE retry classification
    escalates +2 capped; the recurrence modifier is the attempt history,
    capped);
  - scope leakage — CONSUMED from the /profit-intelligence client view's
    indicators verbatim (count + source refs + its calculation version
    inside the rationale — NEVER recomputed here);
  - margin pressure — CONSUMED from the /profit-intelligence realized
    margin figures (negative margin is ALWAYS pressure at severity 10; a
    below-threshold ratio is pressure with the deterministic
    depth-below-threshold severity; non-derivable margins are honest
    absences — NO item, never fabricated pressure);
  - the capacity constraint (exactly one agency-pool item: projected demand
    = (open + in-flight jobs) × the frozen per-job minutes against the
    authorization-ACTIVE field-agents' declared weekly availability
    minutes; zero declared capacity with open demand is the total
    constraint);
  - opportunities (experiments ready / analyzing / concluded-with-
    causal-supported — the promotable finding promotes through the Decision
    Ledger — plus CONTRADICTED learnings, the revision opportunity);
  - the ranking core: `priorityScore = categoryBaseWeight + severity
    (capped 0..10) + recurrence (capped 0..5)`; the total order is score
    DESC → category ASC (lexicographic) → itemId ASC; 1-based contiguous
    ranks; `composeRankingDisclosure` ships the versions + the full
    assumption record + the sort rule + the CONSUMED
    /profit-intelligence calculation version in every view.
  Every item carries the EXISTING consequential-action contract REFERENCE
  (a policy/approval gate dimension where one gates the flow, the canonical
  target record and the frozen one-line flow statement) — a REFERENCE,
  never a command.
- `src/modules/ai-operator/internal/ai-operator-module.ts` — the live read
  model: composes the twelve authority public contracts (clients,
  workspaces, workflows, executions, deployments, jobs, policies, evidence,
  experiments, learnings, field-agents, profit-intelligence — the frozen
  dependency-matrix line), gathers the plain row snapshots through their
  public contracts ONLY, hands them to the pure derivations and composes
  the ranked views. Canonical Client ownership resolves FIRST
  (unknown/tombstoned identifiers → the uniform 404 upstream, before any
  dependent traversal). The jobs enumeration runs over the RESOLVED human
  agent PROFILES (the marketplace listing takes the agent profile id;
  accepted offers take the user id) and is filtered to the owning agency's
  scope — the disclosed enumeration window (jobs never reachable through
  this agency's human agents stay out of the derivations). Zero mutation
  methods; zero owned state; zero SQL in the module internals.

Routes (`src/api/ai-operator-routes.ts`, registered additively in
`src/api/routes.ts`; module exposed additively in `src/api/application.ts`
and `src/composition-root.ts`) — EXACTLY THREE GETs, read-only by
construction:

- `GET /api/ai-operator/:agencyId/attention-queue` — the agency's ranked
  attention queue (every live-derived item across the agency's LIVE
  clients: blocked work, approvals, client risk, anomalies, scope leakage,
  margin pressure, the agency capacity constraint and opportunities).
- `GET /api/ai-operator/:agencyId/attention-queue/:itemId` — one attention
  item by its DETERMINISTIC id, re-derived in the agency queue's context
  (nothing is stored; foreign ≡ unknown ≡ malformed → the uniform 404).
- `GET /api/ai-operator/:agencyId/clients/:clientId/attention-queue` — the
  client's attention queue slice (this client's items; the agency-scoped
  approvals and the agency-pool capacity constraint are excluded, the
  capacity exclusion DISCLOSED with the honest reason).

The scope is SERVER-DERIVED on every read: the authenticated identity + the
durable agency membership (suspended member 403, anonymous 401 fail-closed)
+ the agency's LIVE clients + its ACTIVE human_agent membership users
enumerated from durable state — never accepted from the caller. The path
`agencyId`/`clientId`/`itemId` are SELECTORS re-validated against durable
state (a caller-supplied identifier is never authorization). Tenant
identity can never arrive via DTO — no request body, no DTO validation, no
query parameters (proven statically). The uniform 404 covers foreign ≡
unknown ≡ malformed agencies, clients and item ids (no cross-tenant
existence oracle — an item of ANOTHER agency's queue is simply absent from
this one); authorization is re-resolved FRESH in the execute step of every
route.

## Boundaries

- DERIVED, NEVER AUTHORITATIVE: the module exposes ZERO mutation methods
  over ANY authority; it ranks action candidates only, never executes or
  creates them — every consequential action continues through the EXISTING
  policy/approval contracts on their own surfaces. Proven statically: no
  mutation verb in the route file (mutating verbs are 405 at the router);
  the public contract exposes exactly three read methods; the module
  internals contain ZERO SQL (all authority access is through the composed
  public contracts); no route or module method drives any policy/
  decision/workflow/execution/evidence/job mutation surface (proven
  statically in the boundary test); no migration is owned, so the
  expected-migration list is unchanged.
- THE ACTION CONTRACT IS A REFERENCE, NOT A GATEWAY: each item's
  `actionContract` names the existing MOS surface (policy-evaluation,
  workflow-instance-transition, deployment-lifecycle, job-outcome-
  submission, execution-reconciliation, evidence-append, experiment-
  lifecycle, learning-revision, decision-recording, field-agent-
  availability) with the policy gate dimension where one gates it and the
  canonical target record — the operator drives the named contract through
  its own authorization path; this module never does.
- RANKING DETERMINISM: the priority score is a PURE function of the
  authority rows — no clock factor, no randomness (proven statically: no
  clock read in the derivation files; the only clock use is the module's
  `generatedAt` stamp). Same authority state + same rank version ⇒
  byte-identical queue order (the pinning proof, integration-tested). The
  score, the category vocabulary and every assumption value are VERSIONED
  and exported — never silently re-stated.
- ISOLATION BEFORE TRAVERSAL (§14): every view resolves canonical Client
  ownership first; the agency view re-resolves each server-derived client
  entry (the tombstoned-Client backstop fails closed); items never cross
  the resolved tenant scope (the uniform 404 battery).
- READ-ONLY BY CONSTRUCTION: GET routes only; after every read/probe the
  authoritative rows are byte-identical (proven in the integration
  battery with SQL digests over nine authority tables).
- Items are COMPUTED, not stored truths: every queue count is
  cross-checked against DIRECT SQL ground truth over the authority tables
  in the integration tests; a live-follow test mutates through the REAL
  authority APIs and observes the queue follow on the very next read.
