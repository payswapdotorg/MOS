## What was implemented

**Discovery — DISCLOSED (the proposal surface).** The repo has no module
named "proposals" or "sales": the v1.5 proposal surface IS the Decision
Ledger (`/decisions`, the MKT-041 delivery). A proposal-shaped record is a
Decision whose type is proposal-shaped (the creator-operations domain pack's
`sales_agent` capability vocabulary and the decisions contract's proposal
fields — objective, scope dimension rows, goals link, expected outcomes,
assumptions, economics) whose disposition is ACCEPTED. The carry therefore
anchors on a canonical decision id, resolves ownership canonically through
`/decisions` FIRST (resolveDecisionOwnership), and derives every carried
field programmatically from that record. The `/evidence` public contract's
shared §21 material-key guard is consumed READ-ONLY (the /decisions
precedent) over the carried snapshot.

**Migration choice — DISCLOSED: MIGRATION 040 TAKEN (the pre-assigned
number).** The existing `/playbooks` and `/deployments` public creation
commands expose NO provenance-carrying surface (no source-reference fields
on the created rows), and §8 demands retained provenance + version
identity. The module therefore OWNS an append-only continuity ledger in the
035/036 house style — `040_sales_continuity.sql` (038 is MKT-048's, 039 is
MKT-045's; both reserved for siblings, untouched):

- `sales_continuity_carries` — one row per logical carry: the SOURCE
  references (canonical proposal decision id + exact-content create
  fingerprint — the proposal VERSION identity: the /decisions ledger is
  append-only, corrections are NEW records, so the decisionId IS the
  version and the fingerprint is the content proof), the CARRIED RECORD
  references (playbook id + version id + version number, later deployment
  id), the CARRIED STRUCTURE SNAPSHOT (`carried_payload` jsonb — the
  derived scope/goals/outcomes/assumptions/economics, byte-stable after
  the claim), the §8-style logical identity (client id + idempotency key +
  create fingerprint), the forward-only state ladder
  (`carrying → carried → deployed`, CHECK-fenced closed shape) and the
  server-derived provenance columns.
- `sales_continuity_events` — the append-only continuity tail
  (`carry-claimed` / `playbook-carried` / `deployment-carried`).
- Triggers: identity IMMUTABILITY after insert, no-DELETE (carries are
  linkage history), append-only events, a forward-only COMPLETION GUARD
  (playbook refs set exactly once together with `carrying → carried`;
  deployment ref set exactly once together with `carried → deployed`),
  cross-tenant reference fences. Creates/alters NOTHING outside the two
  `sales_continuity_*` tables.

Module `/sales-continuity` (`public.ts` + `internal/` only — the house
shape):

- `src/modules/sales-continuity/public.ts` — the frozen contract:
  `SALES_CONTINUITY_CARRY_STATES` (`carrying/carried/deployed`),
  `SALES_CONTINUITY_EVENT_KINDS`, `SALES_CONTINUITY_CARRIED_DIMENSIONS`
  (the five §8 dimensions: scope, goals, outcomes, assumptions,
  economics), `SALES_CONTINUITY_DERIVATION_VERSION = 'sc-carry-v1'`
  (same decision record + this version ⇒ byte-identical carried payloads
  and playbook inputs — the profit-intelligence calculation-version
  precedent), the carried structure/snapshot shapes (the /decisions
  contract's own field types, never shadowed), the STRUCTURAL ownership
  ports (client/workspace — the /decisions precedent), the /decisions,
  /playbooks and /deployments composed-command ports, and
  `SalesContinuityModuleApi` — exactly two carry commands + the
  read/round-trip surface.
- `src/modules/sales-continuity/internal/continuity-derivation.ts` — PURE
  deterministic derivations (no I/O): the carried snapshot over the five
  §8 dimensions, the playbook inputs (name/description/strategy derived
  from the objective/scope with the playbook DTO bounds enforced by
  deterministic truncation), the minimal clean deployment metadata
  (no required packs/capabilities, the DISCLOSED default
  `pooled-worker` runtime class + manual trigger — explicit assumptions,
  never silent constants), the carry create fingerprint, and the input
  guards (fail-closed on non-canonical ids, bad idempotency keys,
  incomplete provenance).
- `src/modules/sales-continuity/internal/continuity-store.ts` — the
  append-only ledger rows (SQL over ONLY the two sales_continuity_*
  tables).
- `src/modules/sales-continuity/internal/sales-continuity-module.ts` —
  the ORCHESTRATION:
  - `carryProposalToPlaybook` — canonical owner resolution through
    /decisions FIRST (unknown/foreign/orphaned = uniform 404 upstream);
    the proposal gate (only an ACCEPTED decision is carryable, 409
    otherwise — disposition authority stays /decisions, this is a read);
    a disabled owning Client blocks the carry (409); then §8 replay
    convergence: the SOURCE fence (UNIQUE per proposal version) converges
    a re-carry to the recorded outcome (`replayed = true`, NO second
    playbook), the logical (client, idempotency_key) fence rejects a key
    reused for a different logical create (409), and a claim left
    `carrying` is an UNRESOLVED claim (re-carry is 409, never a blind
    replay — the UNKNOWN posture); finally the Client-scoped Playbook +
    its first Version are created THROUGH the existing
    `createPlaybook` + `createPlaybookVersion` commands (their own
    validation and the frozen client/goal policies run intact), and the
    ledger row completes `carrying → carried` with the linkage.
  - `carryPlaybookToDeployment` ("where applicable") — the carried
    version moves `draft → review → published` THROUGH
    `setPlaybookVersionStatus` (the frozen lifecycle; activation policies
    run inside the playbook authority; an already-published version skips
    the leg — convergent after operator publication; a RETIRED version
    never enters, 409); then `createDeployment` configures one deployment
    (born DRAFT) whose selection is DERIVED from the published version's
    own deployment metadata — the /deployments authority's validation
    runs intact and the MKT-040 validate-before-activate gate is NEVER
    invoked here (activation stays /deployments' own routes). One-shot
    per carry with the same replay-convergence semantics.
  - The read/view surface — `getCarry`, `resolveCarryOwnership`,
    `listCarriesForClient`, `listCarryEvents`, and the three round-trip
    views: `getContinuity` (carry-anchored), `getContinuityForProposal`
    (proposal → carried records) and `getContinuityForPlaybook`
    (delivery side → proposal).

Routes (`src/api/sales-continuity-routes.ts`) — exactly seven surfaces:

- `POST /api/decisions/:decisionId/carry` — the playbook carry
  (owner|admin of the OWNING agency).
- `GET /api/decisions/:decisionId/carry` — the proposal-anchored
  continuity view (any active member).
- `POST /api/sales-continuity/carries/:carryId/deployment` — the
  deployment carry (owner|admin).
- `GET /api/sales-continuity/carries/:carryId` — the carry view.
- `GET /api/sales-continuity/carries/:carryId/events` — the event tail.
- `GET /api/clients/:clientId/sales-continuity/carries` — the Client's
  carries.
- `GET /api/playbooks/:playbookId/carry` — the round-trip view
  (delivery side → proposal).

There is deliberately NO carry update and NO delete route (the ledger is
append-only, forward-only, DB-backstopped), and NO
validate/activate/transition surface (the MKT-040 gate stays the
/deployments routes' alone). The carried payload is NEVER a request field
— the DTOs accept ONLY the idempotency key + the optional goalId and
reject every identity/lifecycle/linkage/snapshot/provenance field (no
manual re-entry anywhere); scope and provenance are SERVER-DERIVED.
Authorization follows the hard-boundary posture: the owning record is
resolved from durable state BEFORE authorize (uniform 404 for
foreign = unknown = malformed identifiers — no cross-tenant oracle),
suspended agencies are 403, anonymous is 401, collaborators read but
cannot carry (403).

## Boundaries

- ORCHESTRATES, NEVER DUPLICATES: the only writes this module can cause
  anywhere are through the /playbooks and /deployments EXISTING public
  creation/status commands (`createPlaybook`, `createPlaybookVersion`,
  `setPlaybookVersionStatus`, `createDeployment`); the module SQL touches
  ONLY the two `sales_continuity_*` tables (proven statically in the
  architecture battery); there is NO second playbook or deployment store,
  NO write to their tables, NO re-declared creation contract.
- The MKT-040 validate-before-activate gate is NEVER invoked from this
  module or its routes; the carried deployment is born DRAFT and
  activation stays the /deployments authority's own routes.
- Provenance + version identity retained END-TO-END: the ledger row
  carries the canonical proposal decision id + content fingerprint (the
  version identity — a successor proposal record carries FRESH identity;
  the old carried identity is never rewritten, DB-backstopped), the
  carried snapshot stays byte-stable after the claim, and the round-trip
  views compose the LIVE decision/playbook/version/deployment records
  through their public contracts with the source references.
- Idempotency: the SAME proposal version re-carry converges to the
  recorded outcome (200, `replayed = true`, no second playbook, no
  second ledger row — the DB source fence backstops the module logic); a
  new proposal version carries fresh identity; the logical-key fence
  rejects key reuse for a different logical create (409).
- Server-derived scope: the carry scope resolves canonically through the
  /decisions public contract BEFORE authorization (uniform 404 for
  unknown/foreign/orphaned anchors); the optional goalId and deployment
  target workspace are scope INPUTS validated inside the composed
  authorities — never authorizations.
