## What was implemented

Migration `037_apps.sql` (PRE-ASSIGNED number; own tables only):

- `apps` — the APP KEY OWNERSHIP rows: one row per app key; the first
  publisher owns the lineage (ON CONFLICT DO NOTHING — concurrent first
  publishes converge to exactly one owner). The owner publisher identity
  is SERVER-DERIVED (`dev:<userId>` for the authenticated
  platform_developer, `svc:<label>` for the internal service principal)
  and the row is immutable (UPDATE/DELETE rejected by triggers).
- `app_versions` — the immutable versioned MANIFEST REGISTRY: one row
  per (app_key, version), DB-UNIQUE-fenced (`app_versions_key_version_unique`);
  UPDATE and DELETE rejected outright by triggers (published App
  Versions are immutable — mos-app-ecosystem-v1.5.md "Upgrade and
  rollback"; architecture-lock v1.5 #11; the 008/028/030 registry
  precedent). The full frozen "Manifest" column set: app key, the
  per-version SERVER-DERIVED publisher, immutable semantic version,
  platform compatibility range (ordered by a REAL semver comparator —
  `apps_semver_cmp`, numeric component ordering), capabilities +
  capability versions, input/output schemas, requested data scopes,
  requested mutation scopes, network destinations, runtime class, event
  subscriptions, UI surfaces + routes, configuration schema, required
  credential names (LOGICAL NAMES ONLY), app-owned state namespaces
  (namespaced `app:<ownKey>:<local>`; the singular-authorities denylist
  applied), migration version, dependencies (the in-row declaration,
  mirrored row-wise), certification state (born `UNVERIFIED` — platform
  territory; the frozen three-value enum CHECK), declared support level,
  metering dimensions. The publisher-consistency trigger fences every
  version row against the key's owning publisher. NO tenant columns:
  an App Version is global catalog state.
- `app_dependencies` — the per-version DEPENDENCY rows: append-only
  (UPDATE/DELETE rejected — part of the immutable version), unique per
  (version, kind, publisher, key), with the VALIDATION BACKSTOP trigger:
  an extension dependency must have a published version INSIDE the
  declared range in the migration-028 registry (read-only); an app
  dependency must reference an existing published app key with a version
  in range; self-dependencies are impossible.
- Closed-vocabulary CHECKs (DB, never a caller freedom): certification
  enum (UNVERIFIED | COMMUNITY_VERIFIED | MOS_CERTIFIED), runtime class
  (the closed /executions four-class set, mirrored), data scopes, mutation
  scopes, UI surface kinds (the closed six-kind vocabulary of "UI and
  developer model"), metering dimensions (the closed economics
  vocabulary). The §21 material-key validator
  (`apps_payload_has_no_material_keys`) fences every jsonb payload at
  every nesting level. NO column capable of holding secret material or
  a secret handle.

Module `src/modules/apps/` (the App registry authority for manifests):

- `public.ts` — the frozen manifest contract (AppManifest — the DECLARED
  content; publisher identity and certification state are deliberately
  NOT manifest-input fields), the closed vocabularies with meanings, the
  read model (AppVersionRecord), the SERVER-DERIVED publisher identity
  type (AppPublisherIdentity), the READ-ONLY /extensions STRUCTURAL PORT
  (`AppsExtensionsPort` — the MKT-023 structural-port precedent, exactly
  the /deployments posture), the compatibility-query contract, the
  module API (publishAppVersion / getAppVersion / findAppVersion /
  listAppVersions / queryCompatibleAppVersions) and the pure helpers
  (semver comparator, range matcher, namespace predicate, manifest
  guard, fingerprint) exported for tests and future SDK/portal callers.
- `internal/store.ts` — the pure input guards (the frozen §Manifest
  shape; CERTIFICATION-SHAPED keys → 403 ForbiddenError — platform
  territory; PUBLISHER/TENANT/PROVENANCE-shaped keys → 422; material
  keys → 422 at every nesting level), the REAL semver comparator and
  the shared dependency-satisfaction predicate, the canonical-JSON
  fingerprint, and the AppsStore (the single publish transaction:
  ownership row → ownership check → immutable manifest row → dependency
  rows; conflict classification).
- `internal/module.ts` — publishAppVersion (guard → dependency
  validation through the /extensions port (existence + in-range, REAL
  semver) and against this registry (app deps; self-deps already
  rejected) → the atomic insert; 409 on the immutable-version fence and
  the key-lineage fence), the reads, and queryCompatibleAppVersions
  (platform range + runtime class + dependency satisfaction, with
  honest per-version ineligibility reasons).

Routes `src/api/apps-routes.ts` — exactly five frozen routes:

- `POST /api/apps` — publish (platform_developer |
  platform_administrator — the MKT-032 extension-portal role precedent;
  the internal service principal publishes like every platform surface).
  The publisher identity is derived SERVER-SIDE from the authenticated
  principal in `execute`; authorization runs BEFORE validate/execute.
  Audit event: `apps.version.published` (append-only, server-derived
  actor/scope).
- `GET /api/apps` — the published version catalog, newest first (any
  active member).
- `GET /api/apps/:appKey/versions` — the version history by app key
  (any active member).
- `GET /api/apps/:appKey/versions/:version` — the manifest by EXACT
  (app key, semantic version) (any active member; unknown → 404).
- `POST /api/apps/compatibility` — the compatibility query (any active
  member; a PURE read with a structured body — no audit, no state
  change).

NO update or delete routes exist (AC-4); every mutating verb 405s at
the router. Certification transitions have NO route here — the
marketplace/trust surface is MKT-050 territory.

Wiring (all shared-file touches ADDITIVE): `application.ts` adds
`readonly apps: AppsModuleApi`; `composition-root.ts` constructs
`createAppsModule({ db, clock, ids, extensions })` — the REAL /extensions
public-contract instance satisfies the READ-ONLY port structurally
(TypeScript structural typing; no cross-module import exists inside
src/modules/apps); `routes.ts` registers the routes after the
deployments family.

## Boundary proof

- Immutability (AC-4): the (app_key, version) UNIQUE fence; the
  outright UPDATE/DELETE triggers on `app_versions` (including
  certification-only UPDATEs — trust cannot be forged even by direct
  SQL) and `app_dependencies`; no update/delete routes; re-publish 409
  with zero rows. Proven by tests/integration/apps-api.test.ts
  (the immutability battery) + the direct-SQL backstops.
- No authority transfer (AC-1/AC-11): ZERO imports of another module
  anywhere under src/modules/apps (the empty dependency-matrix allowance
  — the /deployments posture); the /extensions dependency is the
  READ-ONLY AppsExtensionsPort (getExtensionVersion +
  listExtensionVersions — no register/install/configure/invoke method
  exists on the port or the module API). Proven by
  tests/architecture/apps-boundary.test.ts + tools/arch-check.
- DTO guards (AC-3): certification-shaped keys → 403 (module boundary —
  platform territory; also 422 at the route DTO as an unknown/forbidden
  field); publisher/tenant-identity/provenance/registry-identity keys →
  422; secret-shaped VALUES → 422 at every nesting level (§21). Every
  rejection proven with ZERO rows (integration battery).
- Publisher server-derived (AC-5): the manifest INPUT has no publisher
  field (route DTO forbidden key + module guard rejection); the record's
  publisher is derived from the authenticated principal; the DB row and
  the ownership lineage carry exactly `dev:<userId>` (verified by
  direct SQL); a second publisher on an owned key is a 409 lineage
  conflict.

## Workspace/tenant scope rules (documented choice — AC-8)

Publishing is PLATFORM territory: the frozen `platform_developer` role
(users/public.ts — "wired by later extension Work Items"; MKT-032 wired
it, this Work Item reuses it) or `platform_administrator`; the internal
service principal publishes like every platform surface. Reads (catalog,
history, exact-version manifest, compatibility query) are open to every
AUTHENTICATED ACTIVE member — the global-catalog read posture of the
merged /extensions and /domain-packs registries (their GET surfaces are
"any active member"); the registry rows carry no tenant columns at all.
Anonymous callers receive 401 on every route. Install-time scoping and
server-derived grants are MKT-048 territory.

## The 403/422 posture for certification (AC-5 / AC-9)

A developer can never self-certify: caller-supplied certification state
(any of certificationState/certification/trustLevel/trust/certified) is
rejected 403 ForbiddenError at the MODULE boundary (the single semantic
enforcement point — reachable by SDK/module callers and future portal
surfaces; proven by the unit battery) and additionally 422 at the HTTP
route DTO (forbidden authority field; proven by the integration battery
with zero rows). The registry starts every developer publish at
UNVERIFIED; trust transitions are the MKT-050 platform marketplace/trust
surface — no route exists here, and the migration-037 trigger rejects
UPDATE outright, so even direct SQL cannot forge a certification on a
published row.

## Honest limitations

- App installation/upgrade/rollback (MKT-048), the App SDK/Developer
  Portal (MKT-049), Marketplace/trust surfaces (MKT-050) and the
  metering ledger (MKT-052) are LATER Work Items: this registry only
  PUBLISHES and READS manifests. The declared scopes, UI surfaces and
  metering dimensions are validated declarations — no grant, rendering
  or metering happens here.
- Certification TRANSITIONS (UNVERIFIED → COMMUNITY_VERIFIED →
  MOS_CERTIFIED) have no surface in MKT-047 by design: the
  architecture-lock #11 immutability requirement and the AC-4 "no
  update routes" demand conflict with row-level transitions, so v1
  stores certification as born-UNVERIFIED metadata frozen on the
  published row; MKT-050 owns the platform transition surface (its
  worker will evolve the storage — e.g. a certification ledger —
  without rewriting published manifests).
- The compatibility query resolves app dependencies against the
  PUBLISHED registry (not the caller's environment): the runtime
  platform version, runtime class and extension versions arrive from
  the query input. This is the documented v1 semantics for MKT-048
  consumption.
- The arch-check provision is a disclosed tooling accommodation for a
  frozen-spec documentation gap (see the architecture note above); it
  adds a strictly-enforced boundary and relaxes nothing, and it should
  be replaced by the spec-parsed module list once the Architect
  ratifies `/apps` in spec/architecture.md §6.
