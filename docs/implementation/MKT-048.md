## What was implemented

Migration `038_app_installs.sql` (PRE-ASSIGNED number; own tables only —
the 036/035 house style):

- `app_installs` — the APPEND-ORIENTED SELECTION LEDGER: one row per
  EXACT-VERSION selection of a (workspace, app key) lineage. Columns:
  the immutable opaque id, the SERVER-DERIVED scope chain
  (agency/client/workspace FKs — workspace-within-client trigger
  re-fenced at every write), the EXACT (app_key, app_version_id,
  version) identity (registry-match trigger re-verified against the
  immutable migration-037 row — even direct SQL cannot drift it), the
  operation enum (install | upgrade | rollback; install ⇔ selection_seq
  1 shape CHECK), the SERVER-DERIVED granted scopes (closed frozen
  vocabularies CHECK-fenced; least-privilege subset trigger — a grant
  can never exceed the manifest request), the policy decision
  reference, the monotonic selection sequence (UNIQUE per lineage), the
  lifecycle (born ACTIVE; the ONLY sanctioned transition is
  ACTIVE → SUPERSEDED — shape CHECK), install provenance
  (installed_by/installed_at, server-derived), and the §8 logical
  command identity + create fingerprint. FENCES: the
  current-selection partial unique index (at most ONE ACTIVE row per
  (workspace, app key) — the database serializes concurrent duplicate
  installs), the §8 (workspace_id, idempotency_key) unique fence, and
  the history-preserving trigger (DELETE rejected outright; UPDATE may
  ONLY perform the supersession transition with every recorded column
  immutable).
- `app_install_events` — the APPEND-ONLY lifecycle event tail
  (installed | upgraded | rolled_back) with the payload-shape CHECK
  (an install carries no predecessor; an upgrade/rollback carries BOTH
  prior_install_id and from_version), the (workspace_id,
  idempotency_key) §8 fence, and the events-consistent trigger (the
  event must agree with the ledger row it announces). UPDATE and
  DELETE are rejected outright.

Module `src/modules/app-installs/` (the App installation authority):

- `public.ts` — the frozen contract: the selection-operation and
  lifecycle vocabularies (install/upgrade/rollback; ACTIVE/SUPERSEDED
  with the single sanctioned transition), the PURE selection/upgrade
  state machine (`evaluateSelectionRequest` — install legal only on an
  empty lineage; upgrade selects a NEW version; rollback reselects a
  PREVIOUSLY INSTALLED approved version), the PURE scope-intersection
  derivation (`intersectGrantedScopes` — request ∩ policy-allowed ∩
  the frozen vocabularies), the PURE compatibility-eligibility
  resolution (`resolveTargetCompatibility` — honest reasons), the
  server-declared platform version (APP_INSTALLS_PLATFORM_VERSION —
  never a request field), the record/outcome types, the /workspaces
  ownership + /extensions availability STRUCTURAL PORTS, and the
  module API (install/upgrade/rollback + reads). Imports exactly the
  /apps and /policies publics (the matrix-listed direct directions);
  zero internals imports.
- `internal/module.ts` — the write paths. INSTALL: canonical workspace
  ownership (uniform 404 unknown/foreign; disabled boundaries → 409)
  → exact (app key, version) resolution through the /apps public
  contract → §8 replay convergence → lineage-first-selection check →
  MKT-047 compatibility contract (the server-declared platform
  version + the workspace's AUTHORIZED extension versions — honest
  422 on ineligibility) → the FAIL-CLOSED extension-dimension policy
  gate (only an explicit recorded allow proceeds; deny → 403 zero
  rows) → the SERVER-DERIVED grant derivation (per-scope policy
  evaluations; the operation gate decision id rides the row) → the
  single transactional append. UPGRADE appends the successor
  (selection_seq + 1) and supersedes the prior in ONE transaction —
  the prior row's historical identity is preserved exactly (the
  response `prior` is the durable post-transition row). ROLLBACK
  reselects a PRIOR selection row of the same lineage (foreign/unknown
  target → uniform 404), re-running the compatibility contract and
  the policy gate at rollback time (the strictest posture).
- `internal/store.ts` — the append-oriented ledger store: reads,
  the §8 replay lookup, the current-selection lookup, and the ONE
  transactional write path (guarded supersession UPDATE + successor
  INSERT + event INSERT, with the race backstops classified into
  idempotency-taken / current-fence / stale / validation-backstop).

Routes `src/api/app-installs-routes.ts` (six frozen surfaces, POST/GET
only):

- `POST /api/workspaces/:workspaceId/app-installs` — install one EXACT
  published App Version (agency_owner/agency_admin — the extensions
  install posture; the service principal installs like every platform
  surface). The scope chain is SERVER-DERIVED from the pipeline's
  canonical owner; granted scopes are derived INSIDE the module; the
  DTO has NO scope field at all and rejects every authority-shaped and
  material-shaped key (422, zero rows).
- `GET /api/workspaces/:workspaceId/app-installs` — the workspace's
  installed apps: CURRENT selections + the FULL append-oriented
  history.
- `GET /api/workspaces/:workspaceId/app-installs/:installId` — one
  selection row (foreign install ids → uniform 404).
- `POST /api/workspaces/:workspaceId/app-installs/:installId/upgrade`
  — select a NEW exact version for FUTURE invocations.
- `POST /api/workspaces/:workspaceId/app-installs/:installId/rollback`
  — reselect a PREVIOUSLY INSTALLED approved version.
- `GET /api/agencies/:agencyId/app-installs` — the agency rollup of
  CURRENT selections.
- The append-only lifecycle EVENT tail is a module-level read
  (listWorkspaceAppInstallEvents) consumed by tests and future
  surfaces — deliberately NOT a route (the frozen surface is exactly
  the six above). NO update or delete routes exist: the single
  sanctioned supersession happens inside the module's transaction,
  never through a caller-facing rewrite.

Composition (the disclosed frozen-matrix registration row
`/app-installs ──→ /apps, /policies, /workspaces, /extensions`): the
/apps registry and /policies engine are consumed through their PUBLIC
contracts (READ-ONLY over /apps; every /policies evaluation recorded

availability port is ADAPTER-WIRED at the composition root (the flat
extension-version view of the nested manifest record — the
/deployments capability-check precedent). No mutation surface over any
composed authority (composition, not authority transfer —

architecture-lock v1.5 #7/#13).

## Honest limitations

- App INVOCATION is not this Work Item (a later v1.5 surface): the
  granted scopes are recorded and derivable, but no invocation context
  minting happens here — the install ledger is the authority for
  future-selection semantics only.
- The policy gate rides the frozen EXTENSION dimension of /policies
  (Apps are versioned composition packages OVER Extensions — the
  declared boundary of the install operation carries the app key,
  version, runtime class, certification state and requested-surface
  counts as attributes). A dedicated 'app' dimension would need a
  frozen-vocabulary change, which is spec territory.
- Rollback requires the workspace's CURRENT extension set to still
  satisfy the PRIOR version's dependencies (the strictest posture —
  the compatibility contract re-runs at rollback time). An
  incompatible prior version is honestly rejected rather than
  force-installed.
- The concurrent-duplicate-install convergence treats identical
  concurrent logical commands as §8 REPLAYS (200 replayed, zero new
  state — the /extensions install posture); only a DIVERGENT command
  against the existing lineage is a 409. Exactly one row ever exists
  (the current-selection fence).
- The `prior` field of an upgrade/rollback response is the durable
  POST-transition row (SUPERSEDED with the stamp) — the honest
  selection-change view, not a stale in-memory snapshot.
- Environmental: the sandbox cannot download the pinned MinIO binary
  (network restriction to dl.min.io) — the 9 s3-object-store test
  failures are PRE-EXISTING on clean main (verified via git worktree)
  and unrelated to this Work Item; the libicu60 deb needed by the
  embedded PostgreSQL harness had to be staged manually (the harness
  download path SIGTERMs in this sandbox) using the same
  SHA256-verified artifact.
