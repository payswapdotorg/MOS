## What was implemented

**NO new module, NO new table, NO migration, NO spec edit.** The
delivery is (a) an OUTBOUND SDK artifact under `tools/app-sdk/`, (b) a
THIN Developer Portal route family over the EXISTING /apps registry
authority (the MKT-032 extension-portal precedent: one authority,
multiple route families), and (c) ONE disclosed additive optional field
on the /apps registry publish contract (the signing step). The only
shared-file touches are additive: `src/api/routes.ts` (one import + one
registration call), `src/api/apps-routes.ts` (the optional DTO field
pass-through), and the /apps module contract (below).
`src/api/application.ts` and `src/composition-root.ts` are UNTOUCHED
(the portal composes the already-wired `modules.apps` contract).

### 1. The App SDK — `tools/app-sdk/` (the outbound artifact)

A STANDALONE hand-frozen mirror of the /apps (+ /app-installs
read-model) PUBLIC contracts — "SDKs generated from stable capability
contracts":

- `src/types.ts` — the frozen-mirror TypeScript types (manifest, record,
  signature, compatibility query, publisher identity, install read
  model);
- `src/vocabularies.ts` — the frozen RUNTIME copies of every closed
  vocabulary + meaning map (+ the core-authority namespace denylist and
  the §21 material-key list);
- `src/semver.ts` — the REAL semver comparator mirror
  (`compareSemver`/`appVersionInRange`);
- `src/fingerprint.ts` — the canonical-manifest sha256 fingerprint
  (`appManifestFingerprint` — the identical digest the registry computes
  and persists), `signManifest`, the mirror of the registry's signature
  guard (`appManifestSignatureProblems`);
- `src/validate.ts` — the OFFLINE validator: the faithful non-throwing
  mirror of the registry's `assertValidAppManifest` (identical verdicts,
  problem strings, 403-vs-422 rejection classes — AC-3), plus the
  PROJECT-level rules (capability-contract reference resolution against
  `capabilities/<slug>.json`, version agreement, orphan detection,
  UI-surface correspondence with `ui/surfaces.json`, test-file presence,
  `signature.json` verification with a re-sign hint);
- `src/scaffold.ts` — the project scaffolder (DETERMINISTIC:
  byte-identical regeneration): `mos-app.json` (a manifest skeleton
  VALID against the real MKT-047 guard), one capability-contract file
  per declared capability, the presentation-only UI-surface
  declarations, a `node:test` test skeleton, and a README with the full
  workflow;
- `src/docs.ts` — the offline documentation generator (Markdown from the
  frozen contracts; the 19-field manifest reference table, every
  vocabulary with meanings, the signing guide, the endpoint reference);
- `src/client.ts` — the typed HTTP client over the Developer Portal +
  registry routes (catalog / version history / version view / validate /
  publish / docs / compatibility; bearer auth; typed `MosApiError`
  preserving 401/403/404/409/422 semantics; wire-forms the publish body
  so typed manifests work against the DTO);
- `cli.ts` — the developer CLI: `scaffold | validate | sign | docs |
  publish` (offline except `publish`).

**Posture (proven by tests/architecture/developer-portal-boundary
.test.ts): NO file under src/ imports the SDK (outbound artifact, never
a runtime dependency of core modules), and NOTHING under tools/app-sdk
imports the MOS repository source (standalone — node builtins and
intra-package imports only; the package can be copied out of the repo
and keeps working).**

### 2. The Developer Portal — `src/api/developer-portal-routes.ts`

EXACTLY six frozen routes (GET + delegated POSTs only; no update/delete
verb anywhere):

- `GET /api/developer-portal/catalog` — the developer catalog (distinct
  app keys, version counts, the REAL-semver newest version + the
  publication-newest record) — a thin derivation over
  `modules.apps.listAppVersions`;
- `GET /api/developer-portal/apps/:appKey/versions` — the version
  history view (thin over `listAppVersions`; malformed key → uniform
  404; listing semantics converge with the direct /api/apps family);
- `GET /api/developer-portal/apps/:appKey/versions/:version` — the
  developer version view: the manifest + VALIDATION STATUS (the
  integrity check recomputes the canonical fingerprint against the
  immutable row's persisted `createFingerprint`) + the vocabulary
  annotations (the frozen meanings) — uniform 404 for
  foreign≡unknown≡malformed;
- `POST /api/developer-portal/validate` — ONLINE validation through the
  REAL registry guard (`assertValidAppManifest` + the signature guard) —
  PURE (no state change, no audit — the POST /api/apps/compatibility
  pure-read precedent); returns the guard's own problem strings and the
  403-class marker for certification territory;
- `POST /api/developer-portal/publish` — the DELEGATED publish: exactly
  the /api/apps posture (the frozen platform_developer role gate; the
  server-derived publisher identity; the identical manifest DTO with the
  authority-field/material-key rejection lists) delegating to the SAME
  `modules.apps.publishAppVersion` command — the publish remains
  immutable-versioned with born-UNVERIFIED certification (MKT-047
  semantics; the 409 fences, key-lineage fence and dependency validation
  all remain the authority's). Emits the append-only audit event
  (`developer_portal.app.published`);
- `GET /api/developer-portal/docs` — the documentation surface (AC-6,
  the CHOSEN served form — see the disclosure below).

Server-derived scope everywhere: reads are open to authenticated ACTIVE
members (the global-catalog posture of /apps and /extensions);
publishing is platform territory; anonymous callers 401 fail-closed;
suspended/non-active users 403.

### 3. The signing step — the disclosed additive registry field (AC-5)

The /apps registry contract had NO signing field. Per the dispatch
("add it additively to the registry's manifest validation as an
OPTIONAL field with a disclosure — do NOT invent a second registry"),
the publish contract gained:

```ts
publishAppVersion(input: {
  manifest: AppManifest;
  identity: AppPublisherIdentity;
  idempotencyKey: string;
  signature?: AppManifestSignature | null;   // ← the OPTIONAL additive field
})
// AppManifestSignature = { algorithm: 'manifest-sha256-fingerprint', digest: <64-hex> }
```

**The choice DISCLOSED: hash attestation (not key-based signatures).**
The digest is the manifest's CANONICAL FINGERPRINT — sha256 over the
canonical JSON (keys sorted at every level) + the `|mkt-047-app-manifest`
domain suffix — the IDENTICAL value the registry already computed and
persisted for every row (`create_fingerprint`, the §8 logical-command
identity since MKT-047). The developer computes it offline
(`node tools/app-sdk/cli.ts sign <dir>`); the registry re-computes
server-side and REJECTS a mismatch 422 with zero rows before any write
(fail-closed; `appManifestSignatureProblems` in the /apps module, called
from `publishAppVersion` BEFORE dependency validation and the insert).
When verified, the attested digest is anchored FOREVER by the immutable
row's persisted fingerprint column — anyone can re-verify offline
forever (the SDK client + `validationStatus.integrity` on the version
view do exactly this).

Disclosure details:
- The signature rides the PUBLISH ENVELOPE (a sibling of
  `idempotencyKey`), NOT inside `AppManifest`: the frozen MKT-047
  manifest shape stays byte-identical (the strict 19-field
  `MANIFEST_FIELDS` guard is untouched — asserted by the boundary test),
  and the strict-shape guard would otherwise need a schema change;
- Whether a historical publish was SIGNED is not persisted as a distinct
  boolean — that would require an ALTER TABLE on the sibling-owned
  `app_versions` table (a migration). The digest itself is fully
  verifiable against the persisted fingerprint; the publish RESPONSE
  discloses acceptance (`signature: { algorithm, digest, verified: true }`)
  on both publish surfaces (portal + direct /api/apps, which accepts the
  same optional field);
- Unsigned publishes remain valid (fully backwards compatible — the
  MKT-048 app-installs module and every existing test/consumer are
  untouched).

### 4. The documentation surface (AC-6) — the choice DISCLOSED

**CHOSEN: a served route** — `GET /api/developer-portal/docs` derives
the reference at read time from the /apps public contract's frozen
constant exports (the closed vocabularies + meaning maps) + a frozen
manifest-schema field table + the signing guide + the endpoint
reference. NO runtime mutation: the route writes nothing, persists
nothing, and reads no mutable state (a pure function of frozen
constants — asserted by the integration test: the row count is
unchanged across a docs call). The SDK CLI `docs` command generates the
equivalent reference OFFLINE from the drift-pinned mirror; the unit
drift test asserts the served manifest-schema table is IDENTICAL to the
SDK's offline table, and the integration test asserts the served
vocabularies deep-equal the SDK mirror's — the served and offline
documentation never fork. Static generation into docs/ was NOT chosen
(the served route cannot drift from the contract constants it derives
from; a generated docs/ file could).

## The drift-test design (AC-1/AC-3)

The SDK is a hand-frozen mirror of the authority — the dispatch's
sanctioned "hand-frozen mirror WITH a drift test" form. The drift
suite (`tests/unit/app-sdk-drift.test.ts`) pins EVERY mirrored
dimension to the authority, so ANY authority-side change without a
same-change SDK regeneration FAILS:

1. **TYPE-level pins (compile-time)**: a 23-element `TYPE_PINS` tuple
   whose element types are `Expect<Equal<MirrorType, AuthorityType>>`
   — `tsc --noEmit` fails the moment a public-contract type changes
   shape (manifest, record, signature, compatibility, publisher
   identity, install read model);
2. **RUNTIME vocabulary pins**: every closed vocabulary array and
   meaning map is deep-equal to the authority export;
3. **FINGERPRINT pin**: the SDK digest equals the authority's
   `appCreateFingerprint` over the full manifest corpus (+ key-order
   independence);
4. **SIGNATURE-guard pin**: identical problem lists over the signature
   corpus (valid, mismatched, wrong algorithm, malformed, non-object);
5. **VALIDATOR EQUIVALENCE (AC-3 — the shared-source test)**: over a
   71-case MUTATION CORPUS (fully-valid shapes + systematically-invalid
   manifests covering EVERY rejection class of the frozen guard:
   certification territory, authority-shaped keys, unknown fields,
   closed-vocabulary violations, unordered ranges, duplicates, material
   keys at nesting levels, namespace denylist, self-dependency,
   dependency shapes, malformed scalars, array/null/string manifests),
   the SDK's `validateAppManifest` returns the IDENTICAL verdict,
   problem strings, rejection class and summary the authority's
   `assertValidAppManifest` produces (ForbiddenError →
   'certification-territory' = the registry's 403; InvalidRequestError
   → 'invalid' = 422);
6. **DOCUMENTATION pin**: the served route's manifest-schema table
   equals the SDK's offline table.

The offline validator is a MIRROR BY DESIGN (the registry guard runs
server-side on the publish path; the SDK runs offline on the developer's
machine) — the schema is never forked silently: the corpus equivalence
test is the proof, and the drift pins fail loudly on any divergence.

- **SDK outbound-only** — both import directions pinned: nothing under

- **No new authority** — no module directory, no arch-check provision

  the /api/apps route family (still exactly five routes), the migration

## Honest limitations

1. The v1 attestation is a HASH attestation (digest of the canonical
   manifest), not an asymmetric key-based signature — the dispatch
   offered either; hash attestation reuses the registry's existing
   persisted fingerprint (zero schema change, zero migration, fully
   offline-verifiable forever). Key-based signing would need key
   management infrastructure that does not exist in the frozen v1.5
   contracts; a later Work Item can extend the algorithm vocabulary
   (the closed vocabulary makes that an additive, disclosed change).
2. Whether a historical publish was SIGNED is not persisted as a
   distinct boolean (would require ALTER TABLE on the sibling-owned
   app_versions table). The verified digest is anchored by the row's
   createFingerprint; publish responses disclose acceptance; the
   version view discloses the integrity verdict (recomputed vs stored
   fingerprint) — which also detects any storage-level corruption.
3. The version-history listing of an unknown-but-well-formed app key
   returns the (empty) list, exactly like the direct /api/apps family
   (thin convergence); the uniform 404 applies to exact-version reads
   (foreign≡unknown≡malformed). Disclosed as deliberate convergence,
   not a portal-specific choice.
4. The /api/apps publish DTO (frozen MKT-047 surface, mirrored by the
   portal publish DTO) accepts network-destination ports as STRINGS on
   the wire while the canonical typed manifest (and the fingerprint)
   carries NUMBERS — the registry deserializes the wire form back to
   the identical typed form, so typed-manifest signatures verify; the
   SDK client wire-ifies transparently. Direct apiCall consumers must
   sign the typed form (the integration fixtures demonstrate the twin).
5. The SDK mirror is maintained by hand: the drift tests make silent
   forking impossible, but a contract change still requires a
   same-change mirror update (the regeneration contract documented in
   the SDK header + README).
6. Environmental (pre-existing, NOT introduced here): the 9
   s3-object-store integration failures (MinIO provisioning —
   dl.min.io unreachable from this sandbox) fail IDENTICALLY on clean
   main 2849907; nothing in this delivery touches object storage.
