## What was implemented

Migration `042_app_marketplace.sql` (PRE-ASSIGNED number; own tables
only — the 038 house style):

- `trust_events` — the APPEND-ONLY TRUST TRANSITION LEDGER: one row
  per governance move of one app lineage. Columns: the immutable
  opaque id, the app key (FK to the migration-037 `apps` ownership
  rows — read CHECK-ONLY; no registry row is ever created or mutated
  here), the monotonic per-lineage `transition_seq` (UNIQUE; the
  derived CURRENT state is the newest event's `to_state`), the closed
  transition label (verify | certify | decertify | revoke), `from_state`
  / `to_state` (both CHECK-fenced against the frozen
  UNVERIFIED/COMMUNITY_VERIFIED/MOS_CERTIFIED vocabulary), the bounded
  operator reason, the SERVER-DERIVED provenance
  (recorded_actor/recorded_via/correlation_id/causation_id/recorded_at)
  and the §8 logical command identity + create fingerprint. FENCES: the
  legal-(transition, from, to)-triple CHECK (exactly the frozen
  one-way ladder + the disclosed down moves; no skip, no same-state),
  the global idempotency-key unique index, the CHAIN-CONSISTENCY
  trigger (seq 1 must depart from the UNVERIFIED birth state; seq N
  must depart from seq N−1's `to_state` — the derived state can never
  disagree with the recorded tail, even by direct SQL) and the
  APPEND-ONLY triggers (UPDATE and DELETE rejected outright).
- `app_reviews` — the APPEND-ONLY REVIEW RECORDS (display metadata):
  the structured rating (1..5 CHECK band), the closed verdict
  vocabulary (positive | mixed | negative), the bounded body (1..2000),
  the OPTIONAL exact-version target (`app_version_id` FK to the
  migration-037 registry — the version-consistency trigger re-fences
  it belongs to the SAME app key; NULL = an app-level review), the
  SERVER-DERIVED reviewer provenance and the §8 command identity.
  UPDATE and DELETE are rejected outright by triggers. NO jsonb and no
  material-shaped column exists anywhere in either table (§21).

NO app catalog table is created (the marketplace NEVER becomes a
second registry — the /apps registry of migration 037 stays the sole
catalog; 038 stays the sole install authority; NO metering or
attribution table — MKT-052 territory).

## Disclosures

1. TRUST-TRANSITION SEMANTICS (AC-2). The frozen vocabulary is the
   spec's one-way ladder: verify (UNVERIFIED → COMMUNITY_VERIFIED) and
   certify (COMMUNITY_VERIFIED → MOS_CERTIFIED) — NO skipping
   (UNVERIFIED → MOS_CERTIFIED is illegal; certification follows
   community verification). DISCLOSED DOWN MOVES (the spec's arrows
   are one-way; revocation must exist for governance):
   decertify (MOS_CERTIFIED → COMMUNITY_VERIFIED) and revoke
   (COMMUNITY_VERIFIED → UNVERIFIED or MOS_CERTIFIED → UNVERIFIED).
   Every move — up or down — is an APPEND-ONLY EVENT with operator
   provenance; there is no silent rewrite anywhere (the DB triggers
   reject UPDATE/DELETE; the chain-consistency trigger keeps the tail
   the single source of the derived state; the /apps registry's
   certification_state column stays FROZEN AT BIRTH, as migration 037
   already documented: "trust transitions arrive ONLY through the
   future platform marketplace/trust surface, never by rewriting a
   published manifest row" — this ledger IS that surface).
2. TRUST-TRANSITION AUTHORIZATION (the command surface's model).
   Transitions are OPERATOR/GOVERNANCE actions, not community
   self-service: the route requires `platform_administrator` or the
   internal service principal. A `platform_developer` is explicitly
   INSUFFICIENT (403 — "a platform_developer can never self-certify",
   the MKT-047 certification-territory contract); a plain agency
   member is likewise insufficient.
3. THE MKT-048 ADDITIVE WIRING (AC-5; the ONLY touch of a sibling
   authority's internals, strictly additive). The /app-installs gate
   action's `certificationState` attribute now carries the
   marketplace-DERIVED current trust state instead of the registry
   birth state, so /policies rules can gate installs on the LIVE trust
   level. Implementation: `AppInstallsTrustStatePort` (an OPTIONAL dep
   declared in /app-installs' own public entry — the /policies→
   /credentials structural-port precedent, deliberately off-matrix and
   disclosed in the matrix note) satisfied STRUCTURALLY by the
   marketplace module's `resolveAppTrustState` and wired at the
   composition root (`trustState: appMarketplace`). UNWIRED, the
   module is byte-identical to the MKT-048 delivery. The PURE
   `buildInstallGateAction` helper is UNCHANGED (the registry record
   stays its input). NOTHING else in the gate, grants or ledger
   changes: the fail-closed /policies evaluation (explicit allow
   required, deny-overrides) remains the sole install authority — an
   MOS_CERTIFIED app under a denied policy still fails; an UNVERIFIED
   app under a permissive policy still installs (both integration
   batteries). A port RESOLUTION ERROR propagates (the selection fails
   closed): an unresolvable policy input never silently degrades to a
   stale value.
4. REVIEW MODEL (AC-4). Reviews are DISPLAY METADATA. NO policy
   consumes review state in this delivery — the eligibility vocabulary
   exposes reviewCount/averageRating read-side for FUTURE explicit
   policy consumption only. Review authorization: any ACTIVE
   authenticated member (the community); the reviewer provenance is
   server-derived. Reviews attach at the app level (appVersionId null)
   or at an exact registry version (validated to belong to the SAME
   lineage — a foreign version id is the uniform 404).
5. THE AGENCY SCOPE OF THE DISCOVERY SURFACE (AC-1) is AUTHORIZATION,
   not a data partition: the command-center posture (uniform 404
   foreign≡unknown≡malformed; suspended 403; anonymous 401; scope
   resolved server-side from durable membership state) — while the
   catalog itself is GLOBAL registry state with no tenant columns (the
   037 posture). Both authorized agencies see the same published
   catalog; the marketplace owns no tenant-scoped catalog state.
6. FIRST-PARTY/COMMUNITY CLASSIFICATION is DERIVED from the
   server-derived registry publisher identity: 'svc:<label>' =
   first-party, 'dev:<userId>' = community. It is never a
   caller-suppliable label.
7. MARKETPLACE ATTRIBUTION BOUNDARY (mos-app-ecosystem-v1.5.md
   "Economics"). NO billing, charging, metering or attribution state
   is owned in MKT-050 (MKT-052 territory); the boundary is asserted
   statically (boundary test) and declared in the module contract.
8. THE LISTING WINDOW is the /apps registry authority's bounded
   newest-first public listing (500 rows) — the honest disclosure: the
   marketplace tallies the registry's bounded listing, never an
   unbounded recount (the command-center evidence-posture precedent).

## Boundaries (what this module must never become)

- NOT a second registry: no app catalog table; every catalog fact is
  an /apps registry row consumed READ-ONLY through the public
  contract (asserted statically + integration ground truth).
- NOT an authority: trust NEVER grants anything by itself — no scope,
  no install, no grant ever derives from trust; the only trust
  consumption is ONE policy ACTION ATTRIBUTE (the disclosed wiring);
  the /policies engine and the MKT-048 gate stay the sole install
  authority.
- NOT a metering/billing surface: no attribution state (MKT-052).
- NOT a tenant authority: no agency/client/workspace columns; route
  authorization composes the /agencies membership + platform-role
  authorities.
