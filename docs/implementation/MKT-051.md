## The four first-party packs (AC-1)

One pack per incumbent-capability family, all published through the REAL
`POST /api/apps` command (MKT-047) under the disclosed first-party
identity — the internal service principal, whose server-derived publisher
is `svc:internal-api-token` (the MKT-050 marketplace derives the
first-party classification from the `svc:` prefix). Each pack has TWO
published versions (1.0.0 + 1.1.0, the latter adding one capability) so
the upgrade/rollback lifecycle of AC-2 is provable with real registry
rows.

| Pack | Family | UI surfaces (presentation only) | Composes over (READ-ONLY) | Bounded state namespace |
|---|---|---|---|---|
| `mos-analytics` | reporting/analytics | command-center-card + report-page | /reporting (Agency Command Center), /profit-intelligence (workspace/agency profit), /integrations (connected data sources), /clients, /workspaces (the scope-as-data enumeration) | `app:mos-analytics:report-layouts` |
| `mos-crm` | CRM/pipeline | client-room-panel + action-menu | /clients (client record), /decisions (Decision Ledger pipeline) | `app:mos-crm:pipeline-views` |
| `mos-sheets` | spreadsheet workflows | workspace-tab + editor-pane | /evidence + /metrics (the observation ledgers ARE the workbook rows) | `app:mos-sheets:documents` |
| `mos-portal` | client portal | client-room-panel + report-page | /reporting (Client Decision Room), /clients | `app:mos-portal:presentations` |

## The lifecycle proof (AC-2)

Driven end-to-end by `tests/integration/first-party-apps-api.test.ts`
through REAL commands only (no SQL shortcuts for publish/install/trust):

```text
publish (POST /api/apps, service principal, signed manifests)
  → marketplace listing visible (GET /api/app-marketplace/:agencyId/apps —
    publisherKind=first-party, birth trust UNVERIFIED)
  → trust transitions (POST /api/app-marketplace/apps/:appKey/trust —
    verify then certify, the REAL operator command path → MOS_CERTIFIED)
  → install into a workspace (POST /api/workspaces/:id/app-installs —
    server-derived grants: the policy intersection denies workspace:read,
    visibly constraining both grants AND presentation)
  → authorize (the policy gate honored: an agency-scoped deny blocks
    installs with zero rows; a superseding allow restores them)
  → invoke/read (POST /api/first-party-apps/workspaces/:id/packs/:appKey/surfaces
    — the composition keys on the workspace's CURRENT install selection
    and pins the EXACT immutable registry row)
  → observe bounded state (the app:mos-sheets:documents document with
    lineage to canonical observation ids; mutate/read/export/delete)
  → upgrade to 1.1.0 (POST .../app-installs/:id/upgrade — future
    compositions pin the NEW manifest; the capability-gated presentation
    changes: mos-portal highlights null → [], granted scopes re-derived)
  → rollback to 1.0.0 (POST .../app-installs/:id/rollback — future
    compositions pin the OLD manifest again; all three ledger rows retain
    their ORIGINAL versions, DB-asserted)
```

The full lifecycle runs for `mos-portal` (upgrade→rollback with the
capability-gated presentation flip) and `mos-sheets` (bounded state + the
gated action across the version change); the publish/install portions run
for all four packs.

## Boundaries (AC-3 — the incumbent-capability discipline)

Proven by `tests/architecture/first-party-apps-boundary.test.ts` (static)
and the integration tests (DB-asserted):

1. **Public-contracts-only**: the module imports ONLY platform + the
   matrix-listed modules' public entries (an explicit allowlist test +
   the arch-check provision). Zero module internals, zero SQL, zero `Db`
   port, zero `pg`.
2. **Zero mutation verbs over authorities**: every `deps.<authority>.<method>`
   call in the module tree is asserted to be a READ method (the
   per-authority allowlist in the boundary test). The pack action menus
   DECLARE existing authority command routes
   (`mos-sheets:append-observation` → `POST /api/clients/:clientId/metrics`
   gated on the granted `metric:append` scope;
   `mos-crm:record-decision` → `POST /api/clients/:clientId/decisions`);
   pack code executes NOTHING — the operator's mutations flow through
   the authority routes under the platform's own authorization.
3. **Bounded state**: in-memory, namespaced under the pack's own
   manifest-declared `app:<key>:<local>` namespaces only (the
   migration-037 denylist re-verified at use), §21-guarded via the
   SHARED /apps guard, bounded (64 entries / 64KiB / 64 lineage refs),
   with export/delete semantics and canonical lineage. The integration
   test asserts with direct SQL row counts over 13 authority tables that
   NO authority table changes through the pack state surface.
4. **Non-goals discipline**: no alternate workflow/execution/retry
   engine, no CRM authority (the client roster and pipeline stages are
   the /clients and /decisions authorities' own data), no reporting truth
   (every figure cites its authority view), no tenant store (the scope
   chain arrives from the install record), no evidence store, no policy
   engine (the install gate stays the /policies engine composed by
   /app-installs).

## Integrations stay behind the App/Integration contracts (AC-4)

The `mos-analytics` manifest declares the analytics connector family:
ONE network destination (`analytics.api.provider.example:443/https`) and
the `ANALYTICS_API_KEY` credential LOGICAL NAME. The declaration is
honest metadata about what the pack's connected data sources need — it
is consumed ONLY by the EXISTING `/integrations` authority (an operator
registers a generic-analytics connection with a credential reference;
the pack's data-sources surface then READS the connection records
through `/integrations#listConnectionsForClient`). The constraint is
proven three ways: (a) the boundary test asserts NO fetch/HTTP-port/URL
capability exists anywhere in the module tree; (b) the manifest reason
names the /integrations authority; (c) the integration test asserts the
data-sources surface creates zero connections (row-count proof).

## The HTTP surface (six routes)

```text
GET    /api/first-party-apps/workspaces/:workspaceId/packs                  the pack catalog with LIVE registry + install state
POST   /api/first-party-apps/workspaces/:workspaceId/packs/:appKey/surfaces COMPOSE one declared surface (the invoke/read)
GET    /api/first-party-apps/workspaces/:workspaceId/packs/:appKey/state    read the bounded app state (?namespace=)
POST   /api/first-party-apps/workspaces/:workspaceId/packs/:appKey/state    set/delete bounded app-state entries + lineage
GET    /api/first-party-apps/workspaces/:workspaceId/packs/:appKey/state/export  the export serialization
DELETE /api/first-party-apps/workspaces/:workspaceId/packs/:appKey/state    the delete semantics
```

Authorization: the standard `requireWorkspaceAccess` posture (any active
member for reads/compositions; agency owner|admin for the app-state
mutations); the app-state audits are dot-namespaced
(`firstpartyapps.state_mutated` / `firstpartyapps.state_deleted`) and
name the (workspace, app, namespace) — never an authority record.

## The disclosed route-layer fix (first-party publish path)

The service principal's display label (`Internal API token`) does not
satisfy the frozen `svc:<label>` publisher shape the registry persists
(migration 037 CHECK: `^(dev|svc):[a-z0-9][a-z0-9._-]{0,63}$`), so the
first-party publish path was structurally unreachable through the real
command. The label is now slugified at the two publisher-identity
derivation points (`src/api/apps-routes.ts` +
`src/api/developer-portal-routes.ts`: 'Internal API token' →
'internal-api-token'). This is a display-only normalization with zero
authority semantics — the publisher identity stays server-derived from
the authenticated principal, and every `dev:<userId>` publish is
byte-identical to the MKT-047/049 deliveries (their integration suites
pass unchanged).

## Disclosures

1. **No migration** (the required preference) — see above.
2. **In-memory bounded app state** — process-local; a service restart
   clears presentation state (layouts, view configs, document drafts).
   The spec requires export/delete semantics and lineage, which are
   implemented; durability was deliberately not taken because v1
   presentation packs do not need it. Honest limitation, disclosed.
3. **The route-layer publisher-label slugification** — see above.
4. **The `metric:append` action declaration** — the mos-sheets editor
   pane offers the append-observation action only when the install's
   granted mutation scopes include `metric:append`; invoking the action
   is the operator's client calling the EXISTING /metrics route. The
   pack never appends anything itself.
5. **Environmental** — the 9 s3-object-store integration failures are
   the known MinIO class (the sandbox cannot reach dl.min.io); they
   fail identically on clean main and are NOT masked or deleted.
