## Contract summary

`/app-metering` meters the app ecosystem's REAL events and derives
marketplace attribution aggregates — WITHOUT moving financial authority
into Apps:

- **The append-only meter event tail** (migration 044,
  `app_metering_events`): one immutable row per metered usage observation
  over the real events —
  - `installations` (unit `selections`): one meter event per MKT-048
    install-ledger selection row (install, upgrade and rollback each
    count once — the ledger's append-only rows ARE the installation
    events). Source: `(app-install-selection, installId, lifecycle
    event id)`, occurredAt = the row's `installedAt`.
  - `invocations` (unit `invocations`): one meter event per MKT-022
    extension-invocation ledger row (the invocation surface
    mos-app-ecosystem-v1.5.md "Install and invoke" names: "Invocation
    uses the existing short-lived Extension invocation context"). Source:
    `(extension-invocation, invocationId, executionId)`, occurredAt =
    the invocation's `issuedAt`. The row carries the invocation's RAW
    extension facts (id, key, publisher, version — re-verified against
    the immutable registries by trigger) and NO app identity: app
    attribution of invocations is a VIEW-TIME derivation, never
    materialized on the tail.
  - `compute-runtime` (milliseconds), `data-volume` (bytes),
    `premium-capabilities` (capability-uses): runtime-host usage
    observations ingested through the module-level command
    `recordMeterObservation`, each citing the canonical invocation
    record the usage was observed in (validated through the /extensions
    public ledger).
- **The frozen metering vocabulary** (`am-meter-v1`): the spec's five
  dimensions with explicit units — CHECK-fenced per dimension in
  migration 044 (the storage mirror of the /apps registry's
  meteringDimensions vocabulary; one frozen set, one owner).
- **The derived attribution read models** (`am-attrib-v1`): three
  GET-only views — workspace, agency portfolio (per app / per publisher
  / per period), publisher commercial (per app / per period, NO tenant
  identities) — derived LIVE over the module's own tail with source
  references, the frozen calculation version and the disclosed
  assumption record (the /profit-intelligence discipline).
- **The rebuildable rollup projection** (migration 044,
  `app_metering_rollups`): the derived (workspace, app-or-unattributed,
  dimension, month) aggregates, materialized by the disclosed recompute
  path `recomputeAttributionRollups()` (one transaction: DELETE +
  INSERT…SELECT from the tail — the operating-graph rebuild precedent).
  Rollups NEVER feed the attribution views (both derive independently
  from the tail; the tests prove they agree).

| `recordMeterObservation(input, provenance)` | module-level command | The usage-observation ingestion (compute-runtime / data-volume / premium-capabilities) with fail-closed context guards. |

| `getAgencyAppMetering(agencyId)` | read | The agency portfolio view. |

| `getAppMeterEvent(eventId)` / `listWorkspaceMeterEvents(workspaceId)` | read | Raw tail reads. |

The HTTP surface is EXACTLY three GETs (`GET /api/app-metering/
workspaces/:workspaceId`, `GET /api/app-metering/agencies/:agencyId`,
`GET /api/app-metering/publishers/:userId`) — the collection, ingestion
and recompute are module-level operations for server-side callers
(background workers / future invocation hosts), the operating-graph
rebuild precedent. NO POST/PUT/PATCH/DELETE route exists in the family.

## Boundaries

- **Metering is observation, not billing** (the Economics rule:
  "Marketplace attribution is separate from the core financial
  authority"): no price, rate, amount, currency, charge, invoice,
  payment or balance column or method exists ANYWHERE in the migration,
  module, store or routes (statically proven by
  tests/architecture/app-metering-boundary.test.ts — the
  billing-verb battery). The module's only mutations are meter-event
  appends and the derived-projection rebuild.
- **Collection is event consumption, never a write into another
  module's tables**: the store's DML targets exactly
  `app_metering_events` (INSERT) and `app_metering_rollups` (DELETE +
  INSERT in the recompute); every cross-module read composes the /apps,
  /app-installs, /extensions public contracts (the boundary test pins
  the FROM/INSERT/DELETE targets). The integration suite proves the
  authority tables are byte-identical after collection (md5 snapshots).
- **At-most-once metering of collected sources**: a partial UNIQUE
  (source_kind, source_id, dimension) fence over the collected source
  kinds + deterministic `collect:`-prefixed §8 command keys
  (workspace-scoped) — re-collection appends ZERO rows; concurrent
  collections converge. Ingestion keys may not take the reserved prefix
  (the guard rejects it).
- **Append-only tail**: UPDATE and DELETE are rejected by database
  triggers; corrections are NEW records (restatements are new events;
  interpretation belongs to the versioned derivation).
- **No second tenant/identity authority**: the scope chain resolves
  through the /workspaces canonical ownership structural port; the
  attribution-read authorization is the /agencies membership +
  platform-role authority at the route layer.

## The attribution derivation (am-attrib-v1 — disclosed assumptions)

- `installationUnit: one-per-selection-row` — every MKT-048 selection row
  (install/upgrade/rollback) counts once; `currentInstallationBasis:
  active-selection-rows` — the CURRENT install count per app is the
  ledger's ACTIVE rows (superseded history stays metered but is not
  "currently installed").
- `invocationAppAttribution: dependency-declared-current-selection` — an
  invocation meter event attributes to the app whose CURRENT selection in
  the same workspace declares a manifest dependency on the invoked
  extension (publisher + key) with a range containing the invoked version
  (the /apps REAL semver comparator). Zero or multiple matches →
  `disclosed-unattributed` (counted in the raw totals and the
  unattributed remainder, never dropped, never split).
- `periodBasis: source-occurred-at-utc-calendar-month` — period buckets
  use the source event's own occurredAt, never the meter recording time.
- `premiumCapabilityBasis` / `usageQuantityBasis` — the ingestion guards
  validate the CONTEXT (installed current selection, manifest-declared
  dimension/capability/namespace, real same-workspace invocation record);
  the quantity itself is runtime-host-reported.

## Disclosures

- **Migration number**: 044 (PRE-ASSIGNED; 039/041/043 remain
  reserved-but-unused by sibling deliveries). The rollup table is a
  derived projection WITHOUT append-only triggers BY DESIGN — it is
  replaced atomically by the disclosed recompute (the tail is the sole
  source of truth; any rollup row is rebuildable from it).
- **Invocation attribution is a derivation, not a fact**: the invocation
  meter events carry the RAW extension facts; the per-app invocation
  attribution derives at view time under am-attrib-v1. If the assumption
  changes, a NEW calculation version re-derives — the tail never
  changes.
- **Usage quantities are runtime-host-reported**: the module validates
  the (app, workspace, invocation) context (installed current selection,
  manifest-declared dimension/capability/namespace, real same-workspace
  invocation record) but not the measurement itself — the honest
  ingestion trust boundary.
- **Observed usage must cite an invocation record** (the canonical
  provenance reference). Bounded app state has no storage surface in the
  v1.5 chain yet (MKT-048 stores none), so no data-volume events are
  auto-collected — the ingestion command is the runtime host's recording
  path, and a data-volume observation may carry the manifest-declared
  app-state namespace when one is in play.
- **The publisher view's currentSelectionCount is the honest null**: not
  derivable at platform scope through the /app-installs public contract
  (no global by-app listing). The publisher view also scans the
  invocation slice of the tail to derive linkage per workspace (bounded
  by total invocations metered — a v1 scale disclosure).
- **The collection surface is module-level, not HTTP** (the
  operating-graph rebuild precedent): background workers / future
  invocation hosts compose `collectWorkspaceMetering`; the frozen HTTP
  surface of this Work Item is exactly the three GETs.
- **Shared-file touches were additive and conflict-tolerant**: spec
  §6/matrix (the disclosed minimal registration mirroring MKT-043/048),
  composition-root/routes/application (append-only additions), and the
  shared architecture tests (counts + migration list + the
  app-metering registration). One PRE-EXISTING lint error on clean main
  (the unused `last` variable in tests/architecture/apps-boundary.test.ts,
  introduced by the MKT-050 delivery) was repaired in passing — the
  variable is now consumed by the updated migration-order assertions;
  no semantics changed.
