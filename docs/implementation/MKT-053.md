## 1. What this delivery is

MKT-053 introduces the **durable mission DATA MODEL layer** of v1.6: the
agency-scoped Growth Mission records that express the outcome being pursued
(architecture-v1.6.md §1: "A Growth Mission expresses the outcome being
pursued. The outcome may be creator-specific or business/product-specific."),
mapped INTO the existing Goal authority.

What it is NOT (the bounded scope):

- **NO Growth Operator.** No controller, scheduler, timer, loop, replanner or
  any execution logic exists in this module (architecture-lock-v1.6.md rule
  17 — MKT-054 is a LATER Work Item). This module exposes exactly the durable
  record commands; the MKT-054 controller will compose them server-side
  through the same module API.
- **NO second authority.** The mission is a durable orchestration LAYER over
  existing Goals/Playbooks/Workflows/Executions/Experiments/Evidence/Learning
  (rule 16). `/goals` remains the canonical measurable business-intent
  authority; the mission never re-states, re-computes or owns goal progress —
  it holds goal REFERENCES plus its own declared target metrics.
- **NO human-amplification dependency.** The autonomous mission path is fully
  executable with zero human treatment (rule 41); a genuinely mandatory human
  approval is represented explicitly as the terminal
  `blocked_pending_human_action` state, never a hidden dependency.

## 3. Lifecycle map (the disclosed MKT-053 state machine)

```text
draft  ──activate──▶ active ──pause──▶ paused ──resume──▶ active
   │                   │                 │
   │                   │                 └──stop──▶ stopped_by_user (terminal)
   └──stop──▶ ─────────┤
                         ├──achieve──────────────▶ achieved (terminal)
                         ├──stop─────────────────▶ stopped_by_user (terminal)
                         ├──block:human──────────▶ blocked_pending_human_action (terminal)
                         ├──block:capability─────▶ blocked_by_unavailable_capability (terminal)
                         ├──exhaust:budget/quota──▶ budget_quota_exhausted (terminal)
                         ├──constrain:policy─────▶ policy_constrained (terminal)
                         └──fail:bounded-recovery─▶ failed_after_bounded_recovery (terminal)
```

- All seven terminal states are the architecture-v1.6.md §2 list, VERBATIM,
  and have NO outgoing transitions (frozen in code, in the
  `GROWTH_MISSION_TRANSITIONS` table and in the migration's
  `growth_mission_event_consistent` pair trigger).
- **The honest-state rule** (§2: "The controller never silently converts a
  block into success."): a blocked/failed/stopped/exhausted/constrained
  mission can never be moved to `achieved` (or anywhere else) by ANY later
  transition; `achieved` is reachable ONLY from `active`.
- The non-terminal vocabulary (`draft`/`active`/`paused`) is the disclosed
  implementation decision recorded here (the architecture defines no
  non-terminal mission machine — the MKT-006 Goal-state precedent). `paused`
  exists because the MKT-054 controller semantics need pause/resume; the
  pause verb is a record transition only, never a scheduler.
- Activation (and resumption) requires an ACTIVE agency and **at least one
  ACTIVE goal mapping** (a mission pursues through the Goal authority — the
  measurable anchor). Terminal transitions are never blocked by boundary
  state (recording history is always available — the goals precedent).

## 4. Storage (migration 045_growth_missions.sql — the PRE-ASSIGNED number)

Five OWN tables, CHECK-fenced vocabularies, the 038/040/044 house style:

| Table | Role | Discipline |
| --- | --- | --- |
| `growth_missions` | the agency-scoped mission record (state, CAS version, the version-tail pointer) | identity/scope/provenance immutable; the CAS version advances by exactly one; the pointer only ever ADVANCES and must reference an existing declared version; DELETE rejected |
| `growth_mission_versions` | the append-only declared-objective tail (objective VERBATIM + family + contexts + provenance) | UPDATE/DELETE rejected outright — corrections are NEW version records |
| `growth_mission_target_metrics` | the per-version declared target metrics (comparator CHECK + `intermediate` flag) | append-only with the version snapshot |
| `growth_mission_events` | the append-only history tail (kind-shape CHECKs, gapless per-mission sequence, frozen transition-pair trigger + the current-state-match trigger, the terminal-decision-family shape CHECK) | UPDATE/DELETE rejected outright |
| `growth_mission_goal_mappings` | the mission→goal mapping (FK-anchored to the migration-007 `goals` table; agency scope-chain trigger; terminal-freeze trigger; removal-only UPDATE fence; no-DELETE; ACTIVE (mission, goal) partial-unique fence) | goal removal is a recorded removal triple — history is never erased |

The migration's only touches of other authorities' tables are the
CHECK-ONLY trigger reads (`goals`/`clients`/`agencies`) plus the `goal_id` FK
anchor — no row of another authority is ever created or mutated from here.

## 5. Boundaries

- **Dependency posture** (the disclosed matrix row
  `/growth-missions ──→ /agencies, /goals`): both consumed public contracts
  arrive through declared narrow STRUCTURAL PORTS
  (`GrowthMissionAgencyPort`, `GrowthMissionGoalPort` — the
  /experiments canonical-ownership port precedent). ZERO imports of any
  other module exist anywhere under `src/modules/growth-missions` (proven by
  `npm run arch:check` and `tests/architecture/growth-missions-boundary.test.ts`).
- **HTTP surface** (GET/POST only — `src/api/growth-missions-routes.ts`):
  - `POST /api/agencies/:agencyId/growth-missions` — create
    (agency_owner|agency_admin|platform admin|service)
  - `GET  /api/agencies/:agencyId/growth-missions` — list, ALL lifecycle
    states (any active member)
  - `GET  /api/growth-missions/:missionId` — the composed honest read-back
  - `GET  /api/growth-missions/:missionId/versions` / `.../history` — the tails
  - `POST /api/growth-missions/:missionId/versions` — the objective correction
    (a NEW version record, never an in-place rewrite)
  - `POST /api/growth-missions/:missionId/status` — the lifecycle transition
    (REQUIRED reason)
  - `POST /api/growth-missions/:missionId/goal-mappings` — map an EXISTING goal
  - `POST /api/growth-missions/:goalId/removal` — the honest recorded removal
  - NO PUT/PATCH/DELETE anywhere in the family (proven by the boundary test).
- **Fail-closed isolation**: the path identifiers only SELECT the durable
  scope (never an authorization); uniform 404 for foreign ≡ unknown ≡
  malformed agency/mission/goal identifiers (no cross-tenant existence
  oracle); a suspended membership or disabled identity is the 403; anonymous
  calls fail closed 401. Provenance is server-derived (actor from the
  authenticated principal, correlation from the ambient context — the DTOs
  reject every provenance-shaped key).

## 8. Disclosures

- **The non-terminal state vocabulary is an implementation decision** (§3
  above): the architecture defines only the terminal list; `draft`, `active`
  and `paused` are the smallest honest set, with `paused` included because
  MKT-054's controller semantics name pause/resume. Recorded here per the
  MKT-006 Goal-state precedent.
- **All seven §2 terminal states are strictly terminal** (no outgoing
  transitions) — the literal frozen-architecture reading. A future
  unblock/resume-after-human-action semantics for MKT-054 would need an
  Architect-clarified state extension (or successor missions); MKT-053
  deliberately does not invent one (workers may not redesign frozen
  architecture).
- **No §8 idempotency key on mission creation** (the goals precedent —
  user-created business-intent records; concurrent creation is serialized by
  server-generated identity, and CAS versions guard every mutation).
- **Mutation responses compose the detail AFTER the transaction commits**
  (the pool's READ COMMITTED snapshot would otherwise observe the
  pre-commit state on separate connections).
- **The `agency_operator` role may READ but not mutate** mission records at
  the route layer (the goals create/mutation posture). The MKT-054
  controller will drive mutations server-side as a service principal, so
  route roles do not gate the autonomous path.
- **Environmental**: the known repo-wide environmental classes (MinIO/S3
  provisioning, the deployment-topology SIGTERM race, the redis-cache-lock
  flake) are unrelated to this module; see the delivery report for the exact
  clean-main comparison results.
