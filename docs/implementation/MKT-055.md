## 1. Contract summary

### 1.1 What this module IS

The connection/authorization **MODEL** layer for social accounts:

| Surface | Contract |
| --- | --- |
| `social_accounts` (migration 046) | One **external account identity** — platform id (the integration connection's `adapter_key` carried as DATA), external account id, display identity, verified-at — attached to a Client (agency derived SERVER-SIDE through the integration connection's own `/clients` chain) and an OPTIONAL Workspace, THROUGH an **EXISTING authorized integration** (the canonical `integration_connection_id` reference is READ-ONLY: immutable, never moved, never mutated). |
| `social_account_grants` | The append-oriented **OAuth authorization-grant records**: `pending → authorized → expired/revoked/refreshed/superseded` (the frozen transition table below). Each authorized grant carries its **credential-vault reference** (the ONLY token-related column) and the successor link. |
| `social_account_grant_scopes` | The **scope records**: the EXACT granted scope list recorded **VERBATIM** (`granted-scope`, order preserved by position) plus the **platform-normalized capability tags** (`capability-tag`). |
| `social_account_events` | The fully **append-only authorization-grant/history tail**: one immutable row per lifecycle event, with the `operator \| external-signal` initiation source, the bounded reason, the best-effort provider-revoke disclosure and server-derived provenance. |

### 1.2 The module API (src/modules/social-accounts/public.ts)

- **`startAuthorization`** — appends the PENDING round (state token +
  requested scopes as INTENT, optional pre-bound account for reauthorize)
  and returns the authorize URL built by the flow implementation.
  Requires the integration connection to be `connected` (an *authorized*
  integration); validates the optional workspace through the
  `/workspaces` structural port.
- **`completeAuthorization`** — correlates the round by the OPAQUE state
  token (scoped to the caller's client — a foreign round is the uniform
  404); policy-gates the provider egress; the flow implementation
  exchanges the code and returns the verbatim grant facts; the module
  creates the grant's OWN vault reference (a **dangling handle is
  rejected — zero rows**); binds the account identity (see §3); fills the
  round exactly once; appends the scope records + events.
- **`refreshAuthorization`** — resolves the current grant
  (authorized/EXPIRED — the refresh-token recovery), double policy gates
  (network egress + credential use), resolves the current token material
  through the `/credentials` **authorized-execution** path (IN-PROCESS
  only), hands it to the flow, appends the **successor grant** (its OWN
  new vault reference + verbatim scope records) while the old grant moves
  to `refreshed` with the successor link and its reference is disabled.
- **`expireAuthorizationGrant`** — the explicit `authorized → expired`
  observation (server-side callers; the reads ALSO refuse lazily on
  expired-by-time grants).
- **`disconnectAccount`** (operator) / **`recordExternalRevocation`**
  (externally-signalled) — the terminal death: the live grants are
  revoked, the vault references are DISABLED, the binding moves to
  `disconnected` / `revoked` (BOTH terminal) and every
  authorization-bearing read refuses from then on.
- **`getUsableAuthorization`** — THE fail-closed consumer surface for
  MKT-056+ (adapters, distribution): the account + current authorized
  grant + verbatim scopes + tags + the vault reference, or `null` when
  the connection is dead or the token expired. **Module-level ONLY —
  never an HTTP route** (never an authorization oracle).
- Reads: `getSocialAccount`, `resolveAccountOwnership` (the canonical
  owner context composed through the `/integrations` connection owner
  context), `listSocialAccountsForClient/Workspace`,
  `getAuthorizationGrant` + `listAuthorizationGrantsForAccount` +
  `getAuthorizationGrantScopeFacts` (REFUSE — `ConflictError` — on
  disconnected/revoked connections and revoked grants),
  `listAccountEvents` (always readable — audit; the events carry no
  authorization payload).

### 1.3 The frozen vocabularies (CHECK-fenced in migration 046)

```
account:   connected → disconnected | revoked          (both terminal)
grant:     pending    → authorized | expired | revoked
           authorized → expired | revoked | refreshed | superseded
           expired    → refreshed | superseded | revoked
           revoked / refreshed / superseded → terminal
scope:     granted-scope | capability-tag
event:     authorization_started | authorization_completed |
           authorization_expired | authorization_revoked |
           grant_refreshed | grant_superseded |
           account_disconnected | account_revoked
initiated: operator | external-signal
```

## 2. Boundaries

### 2.1 Dependency posture (frozen matrix row, the disclosed registration)

```
/social-accounts ──→ /integrations, /credentials, /policies, /workspaces
```

- **`/integrations`** — the canonical connection reference + ownership
  chain, consumed READ-ONLY through the public contract
  (`resolveConnectionOwnership`): the connection owns the client chain;
  this module never re-derives tenants from caller input, and no
  integration row is ever mutated from here.
- **`/credentials`** — the vault: references created, resolved
  (authorized-execution scope, in-process only, after a policy allow)
  and disabled through the public contract. The grant's reference is its
  **own kind** `social_account_oauth` — never shared with
  product/source/store credentials (**lock rule 28**: it confers no
  product/source/store access; the module has no such surface at all).
- **`/policies`** — the fail-closed gates in front of every
  provider-touching flow step: `network` dimension
  (`social-account.complete` / `social-account.refresh` /
  `social-account.revoke`) and `secrets` dimension
  (`social-account.credential`). Deny/unknown → `PolicyDeniedError`
  BEFORE any material resolution or provider traffic (the integrations
  `requirePolicyAllow` pattern).
- **`/workspaces`** — the optional workspace narrowing, consumed through
  the narrow canonical-ownership **STRUCTURAL PORT** (the `/app-installs`
  precedent; the real `WorkspacesModuleApi` satisfies it at the
  composition root).

### 2.2 Provider neutrality (AC-7 + lock rule 18)

- The **platform identity is the integration connection's adapter key
  carried as DATA** — there is no platform name, endpoint, OAuth URL
  shape or provider branch anywhere in the module code (proven by the
  static boundary test scanning `src/modules/social-accounts/**` +
  `src/api/social-accounts-routes.ts` for the v1.6 MVP platform names).
- The module defines the **provider-neutral OAuth FLOW PORT**
  (`SocialAccountFlowImplementation`: buildAuthorizeUrl,
  exchangeAuthorizationCode, refreshAuthorization, revokeAuthorization)
  — the seed of the MKT-056 adapter contract. Flow implementations
  arrive **as DATA** through the module dependencies (the MKT-023
  adapter-registry precedent), validated at construction (unique
  adapter key).
- **The production composition registers NO flow** — the registry is
  EMPTY until the MKT-056+ adapter deliveries wire real platform flows.
  Any flow step against a platform with no registered flow is refused
  fail-closed (`ConflictError`, zero rows). The disclosed composition
  seam is **`AppOptions.socialAccountFlows`** (the `extraSinks`
  precedent): integration tests supply the local provider double
  through it.
- No capability discovery, publishing, analytics or distribution surface
  exists here — those are MKT-056+ scope. The capability tags are
  recorded facts, never interpreted.

### 2.3 Secret separation (AC-3 + §21 + lock rule 28)

- **Tokens NEVER enter the social-account tables.** There is no token,
  code, secret, material or handle column anywhere in migration 046
  (proven by the architecture battery; the only token-named column is
  `state_token` — the OAuth anti-CSRF state parameter, opaque
  server-generated protocol data, deliberately not a secret).
- The flow implementation provisions the token material into the
  platform secret backend (the deployment-level provisioning path the
  production adapter host will own) and returns an **opaque handle**;
  the module immediately turns it into a `/credentials` vault reference
  (`createCredentialReference` fails closed on a handle that does not
  resolve — the dangling-handle rejection, zero rows).
- Material resolves ONLY through `/credentials`' authorized-execution
  path, in-process, after a fail-closed policy allow (the integrations
  `resolveCallMaterial` precedent), and is handed to the flow
  implementation in-process only — never persisted, logged or queued.
- The OAuth `code` is transient single-use protocol data: never
  persisted, logged or audited (no column exists for it).

## 3. Lifecycle map

```
                ┌──────────── authorize-start (module: startAuthorization)
                ▼
            PENDING round (state token + requested scopes [+ pre-bound account])
                │  complete (module: completeAuthorization — policy gate,
                │  code exchange through the flow, vault reference, binding)
                ▼
   ┌─ binding: CONNECTED (born) ── grant: AUTHORIZED (single fill)
   │      │                                │
   │      │                    expire (observation) ──────────────┐
   │      │                                ▼                      │
   │      │                            EXPIRED ── refresh ──► new AUTHORIZED
   │      │                                │        (successor grant + link;
   │      │                                │         old reference disabled)
   │      │                     reauthorize └─► new round → new AUTHORIZED
   │      │                                │         (old grant superseded)
   │      │                    refresh ─────┘
   │      ▼                                ▼
   │  DISCONNECTED (operator) / REVOKED (external signal)
   │      └── BOTH TERMINAL: live grants revoked, vault references
   │          disabled, every authorization-bearing read refuses.
   │          Re-connect of the same identity = a FRESH binding row
   │          + fresh cycle (never an in-place reactivation).
   └──────────────────────────────────────────────────────────────┘
```

**Binding semantics (AC-4):**
- one connection binds one platform identity — partial unique fence
  `(integration_connection_id) WHERE status = 'connected'`;
- one active binding per (client, platform, external account) — partial
  unique fence (the same identity on another connection of the same
  client is rejected fail-closed);
- re-connecting the SAME identity under the SAME integration is
  **idempotent**: the existing binding is reused, the current grant is
  superseded (its vault reference disabled), the grant history grows —
  **no duplicate active binding**;
- one authorized grant per account — partial unique fence; the supersede
  / refresh transition happens BEFORE the successor insert, inside ONE
  transaction;
- a DIFFERENT identity on a bound connection (or on a pre-bound
  reauthorize round) is rejected fail-closed with the round left
  pending (retryable).

**Death semantics (AC-5):** disconnect and externally-signalled
revocation have identical failure modes. Every lifecycle transaction
that can land an authorized grant on, or kill, an EXISTING binding
(complete, refresh, disconnect, external revocation) takes the
**account-row lock FIRST** inside its transaction and re-checks the
connection state under the lock — so a completion/refresh racing a
death either observes the terminal state and refuses (its fresh vault
reference is compensated away — no orphan) or commits before the death
sweep reads the live-grant set under the same lock: **no authorized
grant or active vault reference can survive on a dead binding**. The
death sweep itself reads the definitive live-grant set (`authorized` +
`expired`, `FOR UPDATE`) inside the transaction and disables each
reference (idempotently) immediately before revoking it. An unexpected
abort can never zombify INTO use; the disclosed edge cases are in §6.

## 4. Secret-separation proof (the AC-3 evidence chain)

1. **Structural:** migration 046 has NO material-capable column (the
   architecture test proves the absence per table).
2. **Kind separation:** every token reference is created with kind
   `social_account_oauth` — the grant's own least-privilege reference;
   the module never creates, resolves or disables any other kind (its
   only credential operations target references it created).
3. **Resolution path:** `resolveCredentialMaterial` with the
   `authorized-execution` scope of the connection's owning chain — the
   integration test proves a foreign scope resolves NOTHING.
4. **No zombie grants:** refresh/supersede/disconnect/revocation disable
   the replaced grants' references through the vault
   (`setCredentialStatus → disabled`), asserted by the integration
   battery after every death path.
5. **The events carry no authorization payload** (no credential
   reference, no token facts) — the audit tail stays readable after
   death without exposing anything usable.

## 6. Honest limitations & disclosed edge cases

1. **No real platform OAuth** — by dispatch: real platform OAuth
   endpoints are not callable from the sandbox. The provider boundary is
   exercised by the **LOCAL provider double** (a loopback HTTP server +
   the flow implementation in test code, `tests/integration/helpers/
   oauth-provider.ts`) — a disclosed test double at the provider
   boundary ONLY; the connection model under test is fully real.
2. **The golden path is module-level.** The spawned production API
   registers no flow (MKT-056+), so `authorize-start`/`complete`/
   `refresh`/`reauthorize` over HTTP would 409 against the production
   composition. The integration suite drives the flow family through
   the SAME in-process application (composed against the SAME database
   the API serves) via `AppOptions.socialAccountFlows` — the app-metering
   module-command precedent — and exercises the ROUTE family for the
   reads, the deaths, the authorization/isolation battery and the
   fail-closed no-flow 409. The flow ROUTES themselves (authorize-start
   body → 201 etc.) are exercised for the DTO/authorization layers via
   the 409 + 422 probes; their happy-path HTTP behavior will be proven
   end-to-end by the MKT-056+ adapter deliveries.
3. **A failed completion leaves no active orphan vault reference
   (COMPENSATED).** The vault reference is created BEFORE the binding
   transaction (so a dangling handle aborts with zero rows). If the
   transaction itself then fails (a fence rejection, a consumed-round
   race, a version-race), the freshly created reference is disabled
   best-effort as a compensation before the original error surfaces —
   the integration battery pins that the rejected conflicting binding
   leaves the client's ACTIVE `social_account_oauth` reference count
   unchanged. If the compensation itself cannot run (a vault outage
   after the DB failure), an active reference with a live handle but no
   grant could remain: unreachable through any MOS surface (no grant
   references it), disclosed as the residual vault-hygiene edge (not a
   zombie grant).
4. **The disable-before-transition wedge.** If a durable state
   transition fails AFTER a vault reference was disabled (a rare
   race/vault error), the old grant may remain `authorized` with a
   disabled reference: every use fails closed at the material resolution
   (the authorized-execution path returns null), and the recovery is the
   reauthorize cycle. The ordering can never zombify INTO use.
5. **A never-completed expired round is never a supersede target.** A
   stale PENDING (possibly pre-bound) round can be expired as a round
   (`pending → expired`, no credential — the shape CHECK admits it); the
   completion supersede logic targets FILLED grants only (authorized or
   expired WITH a vault reference), because transitioning a
   never-completed row to `superseded` is illegal under the migration-046
   payload shape. The regression test pins the sequence
   expire-stale-round → reauthorize → clean supersede.
6. **The composed external-revocation reason is budget-checked BEFORE
   any side effect.** `recordExternalRevocation` embeds the signal source
   into the recorded reason; the COMPOSED string is validated against
   the event reason budget up front (`composeExternalRevocationReason`,
   unit-pinned) so an over-budget composition is a clean 422 — never a
   mid-death failure after vault references were already disabled.
7. **`expireAuthorizationGrant` records `initiatedBy: 'operator'`** for
   server-side callers; a future adapter host that wants to attribute
   provider-observed expiry as `external-signal` can reuse the event
   vocabulary (both sources exist) — the current command does not take
   the initiation source as a parameter (scope discipline).
8. **The state token has no TTL.** An abandoned PENDING round stays
   pending; a very late callback would still complete it (the state
   token is unguessable). A pending-round timeout belongs to the adapter
   host (MKT-056+); the `pending → expired` transition exists in the
   frozen table for it.
9. **The display identity is the binding-time record.** A provider-side
   rename does not rewrite the binding (identity columns are immutable);
   live identity reads are the future adapter layer's surface. A
   reauthorize round returning a DIFFERENT external account id is a
   fail-closed conflict (the platform identity of a binding is frozen).

## 9. Delivery history

- **Initial delivery** (base `1bf699b`, pushed as `b48a401` + `e32ba6c`):
  the full module, migration 046, the three test batteries and this
  runbook. The session died before the completion report was written.
- **Resume fix pass** (this delivery): a full-code review of the pushed
  head against the acceptance criteria surfaced four contract-level
  gaps, all fixed with regression coverage —
  1. the `expired → refreshed` edge of the frozen grant transition
     table was unreachable from `refreshAuthorization` (it resolved
     `authorized` grants only, contradicting the pinned public contract);
  2. the supersede target of a completion could pick a never-completed
     expired round, whose transition to `superseded` violates the
     migration-046 payload shape (a raw CHECK failure);
  3. an over-budget composed external-revocation reason was rejected
     only mid-death, after the vault references were already disabled;
  4. aborted completions/refreshes could leave an ACTIVE orphan vault
     reference (no compensation) and the death sweep raced concurrent
     completions (a straggler authorized grant could survive on a dead
     binding). The fix: account-row-lock-first serialization in every
     binding-touching transaction + best-effort reference compensation.
  Smaller items: the injected clock in the lazy-expiry check, the
  round's workspace narrowing carried into the code-exchange flow
  context, and the refresh scope records moved inside the refresh
  transaction.
