## 1. Contract summary

### 1.1 What this module IS

The **delivery plane** behind the MKT-001 `/notifications` boundary stub
(name + authority, no business logic — the boundary identity is validated
at module construction):

| Surface | Contract |
| --- | --- |
| `notification_records` (migration 047) | The agency-scoped durable **§14 notification records**: event type, urgency, human-readable explanation, **source reference** (the producing authority's kind + canonical UUID id, recorded VERBATIM — never re-derived), required action (NULLABLE), deep link, the requested channel set (jsonb, vocabulary-trigger-fenced) and the email context (recipient **user id** + the `/credentials` vault **reference id** — never an address, never material). `delivery_status` is the **adapter-plane lifecycle only**: `pending → delivered \| partial \| undelivered`, `delivered` TERMINAL. |
| `notification_delivery_receipts` | The **fully append-only delivery attempt tail**: one immutable row per attempt — channel, the per-(notification, channel) gapless `attempt_seq`, outcome (`delivered \| failed \| refused \| duplicate_skipped`), the bounded honest reason, the provider message id when present, the deciding `/policies` decision id when a gate refused, timestamp, server-derived provenance. UPDATE/DELETE are rejected by the database outright; **retries append NEW receipts, never rewrite**. |
| `notification_delivery_dedup_fence` | The **idempotency fence**: exactly ONE notification per `(source_kind, source_id, event_type, occurrence_key)` — a GLOBAL unique index (canonical producer UUIDs cannot collide across tenants). A replayed event never double-delivers; the second attempt surfaces the honest `duplicate_skipped` receipts referencing the EXISTING notification. Fence rows are immutable. |
| `notification_inbox_states` | The **in-app projection read state** (the future console surface): one row per in-app-delivered notification, born `unread`; the single sanctioned transition is `unread → read` (READ terminal — an acknowledged notification is never un-acknowledged); the read facts (`read_at`, `read_by_actor`) are set exactly once. |

### 1.2 The frozen vocabularies (CHECK-fenced in migration 047; pinned by unit + boundary tests)

- **Channels (6):** `in-app`, `email` (the two MVP adapters that ship) +
  `whatsapp`, `telegram`, `sms`, `signal` (**declared-but-unimplemented
  capability keys** — a request naming them is honestly REFUSED with a
  receipt: "no delivery adapter is registered", never silently dropped).
- **Urgency (4):** `low`, `normal`, `high`, `critical`.
- **Event types (5 — the MVP set grounded in the authorities existing at
  base):** `mission.state_changed`, `mission.blocked_pending_human_action`
  (the v1.6 human-growth blocker), `execution.failed`,
  `execution.unknown_outcome` (the first-class UNKNOWN reconciliation
  state), `workflow.attention_required`. Future producers extend the
  vocabulary through a disclosed migration.
- **Source kinds (4):** `mission`, `execution`, `workflow`, `job` (the
  source id is the producer's canonical UUID).
- **Receipt outcomes (4):** `delivered`, `failed` (provider/transport
  failure — retryable), `refused` (fail-closed: policy denial, acceptance
  mismatch, no adapter, unresolved recipient/credential),
  `duplicate_skipped` (the fence fact — NEVER a delivery outcome, never
  part of the `delivery_status` computation).
- **Delivery status (4):** `pending`, `delivered` (TERMINAL), `partial`,
  `undelivered`.
- **Read status (2):** `unread`, `read` (terminal).

### 1.3 The module API (src/modules/notification-delivery/public.ts)

- **`recordNotification(input, provenance)`** — the recording + fan-out
  command: input guards (pure, §21 material-key backstop included) →
  idempotency fence lookup (a replay appends the duplicate-skipped
  receipts and STOPS; a foreign-agency fence hit is the uniform 404 — no
  oracle) → record + fence in ONE transaction (born `pending`) → the
  per-channel fan-out (adapter attempts BETWEEN the transactions — no
  receipt claims what did not land; a crash leaves the honest `pending`
  record) → receipts + the in-app projection row + the status move in ONE
  transaction.
- **`redeliverChannel({notificationId, channel}, provenance)`** — the
  channel retry: re-runs the per-channel pipeline and appends the NEW
  receipt (attempt sequences advance); refuses a channel outside the
  requested set, a delivered notification (terminal) and an
  already-delivered channel (the recorded history is immutable fact).
- Reads: `getNotification`, `listNotificationsForAgency` (optional client
  narrowing), `listReceipts` (the complete attempt tail),
  **`listInbox`** (the in-app read surface — optional client narrowing +
  unread-only filter), `getInboxEntry`.
- **`markInboxRead({notificationId, expectedVersion}, provenance)`** —
  the single sanctioned CAS transition (unread → read, terminal).
- **`listRegisteredAdapters()`** — the registry read (channel + declared
  acceptance).

### 1.4 The per-channel pipeline (channel-agnostic — a future channel
plugs in by registering an adapter, NO module changes)

1. **Adapter lookup** — no registered adapter (a future capability key)
   → the honest `refused` receipt ("no delivery adapter is registered").
2. **Acceptance check** — the adapter's DECLARED urgency/event-type
   subsets (AC-2); outside → `refused` ("not sanctioned … fail-closed").
3. **The `/policies` channel gate** — `notification.channel.<channel>` on
   the **network** dimension (the delivery-egress dimension this plane
   uniformly consults; the `social-account.complete` precedent), with
   `channel`/`urgency`/`eventType` selector attributes so a declared
   boundary can sanction per urgency/event-type subsets. **deny AND
   unknown both refuse** (the fail-closed enforcement outcome); the
   receipt carries the deciding **decision id** (traceability into the
   append-only `/policies` decision ledger).
4. **The adapter attempt** — the email adapter internally: recipient
   address resolution through the structural port → the
   **secrets-dimension credential gate** (`notification.email.credential`,
   resource = the vault reference id — the `social-account.credential`
   precedent) → vault material resolution (authorized-execution scope,
   in-process only) → the deterministic render → the transport send.

### 1.5 The HTTP surface (src/api/notification-delivery-routes.ts)

GET/POST ONLY (no PUT/PATCH/DELETE anywhere in the family — asserted by
the boundary test):

- `POST /api/agencies/:agencyId/notification-delivery` — record + fan-out
  (owner|admin); the replay answers **200** with `duplicate: true` (vs
  201 for the first recording).
- `GET  /api/agencies/:agencyId/notification-delivery[?clientId=…]` — the
  agency's records (any active member).
- `GET  /api/agencies/:agencyId/notification-delivery/:notificationId` and
  `…/receipts` — the record + the complete receipt tail (member; uniform
  404 for foreign/unknown/malformed).
- `POST /api/agencies/:agencyId/notification-delivery/:notificationId/redeliver`
  — the channel retry (owner|admin).
- `GET  /api/agencies/:agencyId/notification-inbox[?clientId=…&unreadOnly=…]`
  — the in-app read surface (the future console surface).
- `POST /api/agencies/:agencyId/notification-inbox/:notificationId/read` —
  the CAS read transition (member).

## 2. Boundaries (what this module deliberately does NOT do)

**Boundary rule 9 — the delivery plane is NOT task/action state:**
`delivery_status` is the ADAPTER-plane lifecycle ONLY. There is NO
task-done, action-taken, acknowledged-work or business-state field
anywhere in the migration, the module or the routes (the static boundary
test pins the absence of the task/action-state vocabulary). The module
NEVER records "task done" or "action taken"; the replay/`markInboxRead`
surfaces are delivery/read facts, not work states.

- **No notification-policy authoring** — the `/policies` authority
  (MKT-021) stays the sole policy engine; this plane only CONSULTS it
  fail-closed per channel attempt.
- **No secret material anywhere** — the email provider credential is a
  `/credentials` vault REFERENCE id on the record (§21); material
  resolves ONLY in-process, inside the sanctioned email adapter subtree,
  after the fail-closed allow; the module core and the store never touch
  it (pinned by the boundary test).
- **No address guessing** — the recipient is a canonical MOS user id; the
  address resolves ONLY through the recipient-address structural port
  (an ACTIVE member of the notification's agency — the workspace/client
  context). A raw address is not even a field on any input surface; the
  DTOs reject `recipientAddress`/`to`/`email`/`address` outright.
- **No future-channel adapters** — WhatsApp/Telegram/SMS/Signal are
  declared capability keys refused honestly with receipts until their
  deliveries register real adapters.
- **No credential ownership** — the vault is consumed READ-ONLY (the
  module never creates/mutates/disables a credential reference; the
  social-accounts grant lifecycle is NOT repeated here).
- **No adapter-registry mutation route** — adapters are composition-root
  DATA; the registry read stays module-level.

## 3. The adapter contract (AC-2) and the provider seam (AC-7)

`NotificationDeliveryAdapter` — the platform-neutral, pluggable contract:
`channel` + `acceptance` (the DECLARED urgency/event-type subsets) +
`deliver(request) → {outcome: delivered|failed|refused, reason,
providerMessageId, policyDecisionId?}`. Adapters arrive as **DATA**
through the module dependencies (the `/integrations` adapter-registry
precedent), are validated at construction (unique channel, legal
acceptance subsets) and are wired at the composition root ONLY (the
sanctioned `internal/adapters/**` home — the static architecture checker
allows exactly the composition root and tests to import them).

- **`InAppDeliveryAdapter`** (internal/adapters/in-app/) — the always-on
  internal channel (accepts every urgency/event type). Its delivery
  effect is the **module-owned durable projection**: the adapter decides,
  the module persists — the inbox row (born `unread`) is appended
  ATOMICALLY with the delivered receipt. ALL SQL lives in the module
  store (the single DML home — pinned by the boundary test).
- **`EmailDeliveryAdapter`** (internal/adapters/email/) — the real email
  mechanics: recipient resolution through the port, the
  secrets-dimension credential gate, vault material resolution, the
  deterministic render (subject `[MOS][<urgency>] <event type>`; body =
  explanation + source + required action + deep link) and the send
  through the **`EmailTransport` provider seam**. Its declared acceptance
  EXCLUDES `low` urgency (a real, testable MVP profile: low-urgency
  events stay in-app only).

**The disclosed provider seam:** `EmailTransport` is the port between
the adapter and the concrete provider send. **Tests** supply the
deterministic in-repo double (records the resolved address + rendered
message + material BYTE LENGTH — never material content; NO real network
calls anywhere in the suite). **The production composition** wires the
disclosed `UnwiredEmailTransport` (the NoCache/UnavailableLock degenerate
adapter precedent): every send honestly FAILS with the "not wired"
reason — the receipt records the truth, nothing is silently dropped, no
network is touched — until the provider-wiring work item lands a real
transport (which will live under the sanctioned adapter subtree and be
wired at the composition root ONLY; no provider SDK import outside it).

**The disclosed off-matrix structural port:** the recipient-address port
(`RecipientAddressResolutionPort`) is composed at the composition root
from the `/users` + `/agencies` public contracts (the `/app-installs`
structural-port precedent — deliberately off-matrix, disclosed here and
in the module-dependency-matrix authority note): an address resolves ONLY
when the recipient user exists AND holds an ACTIVE membership in the
notification's agency.

## 7. Disclosures

1. **Double dispatch** (see the header): the parallel MKT-068 session's
   commits are merged with strategy `ours` and stay reachable; this
   session's tree won per the MKT-069 precedent.
2. **The email provider seam is UNWIRED in the production composition**
   (the disclosed `UnwiredEmailTransport`): production email attempts
   honestly fail with "not wired" receipts until the provider-wiring work
   item lands a real transport over the platform HttpCallPort. The
   integration suite asserts BOTH behaviors (the deterministic double's
   delivered path module-level; the spawned API's honest unwired failure).
3. **The recipient-address port is off-matrix** (composed from `/users` +
   `/agencies` at the composition root — the frozen v1.6 row is
   `/notification-delivery → /notifications, /policies, /credentials`):
   the disclosed `/app-installs` structural-port precedent.
4. **The in-app inbox read state is AGENCY-scoped** (one projection row
   per notification, not per user): the AC names the singular in-app
   projection; per-user inbox semantics belong to the future console
   (MKT-074) if the product wants them.
5. **Dangling email credential references are rejected at creation**
   (uniform 404, never persisted — the migration-047 FK + the
   growth-missions goal-mappings precedent); the honest refused RECEIPT
   covers the runtime unresolvability (disabled/tombstoned/mismatched
   credentials and policy denials).
6. **The event-type vocabulary is the MVP set** (5 types grounded in the
   authorities existing at base); future producers extend it through a
   disclosed migration — the delivery plane records the event type
   VERBATIM and never interprets it.
