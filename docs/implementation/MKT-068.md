## 1. Contract summary

### 1.1 What this module IS

The **delivery plane** behind the MKT-001 `/notifications` BOUNDARY (the
stub stays boundary-only — name + authority, no business logic added to
it; the delivery plane lives in `/notification-delivery`):

| Surface | Contract |
| --- | --- |
| `notifications` (migration 047) | The agency-scoped durable **notification records** carrying the FULL §14 field set: event type, urgency, human-readable explanation, source reference (the producing authority's kind + opaque record id, carried as DATA — never resolved here), nullable required action, deep link (a RELATIVE console route — CHECK-fenced) and the adapter-plane delivery status (`pending → dispatched`, exactly once — NEVER a business/task state). |
| `notification_delivery_fences` | The **dedup fence**: exactly one row per (source kind, source id, event type, occurrence key) — the race-free at-most-one-notification-per-event-occurrence backstop. A replayed occurrence never double-delivers; the second attempt surfaces honest duplicate-skipped receipts on the ORIGINAL notification. |
| `notification_delivery_receipts` | The fully **append-only delivery-attempt tail**: one immutable row per channel attempt — channel, outcome (`delivered \| failed \| refused \| duplicate_skipped`), provider message id when present, the honest bounded reason, the **policy decision id** that gated the attempt and server-derived provenance. Retries are NEW rows; UPDATE/DELETE are trigger-rejected. |
| `notification_inbox_items` | The **in-app read state projection** (the future console's read surface): exactly one durable inbox row per delivered notification (unique-fenced, at-most-once under concurrency) with the read/unread transition set EXACTLY ONCE (never unset, never re-set). |

### 1.2 The module API (src/modules/notification-delivery/public.ts)

- **`deliverNotification`** — THE delivery command: validates the input
  (the pure guards — vocabulary + §14 shapes, fail-closed by rejection
  BEFORE any write); claims the event occurrence on the dedup fence
  (notification row born `pending` + fence row, ONE transaction — the
  unique fence makes the claim race-free); dispatches synchronously
  through every registered channel that ACCEPTS the urgency/event type —
  the per-channel `/policies` gate runs BEFORE every adapter call and a
  non-allow FAILS CLOSED into an honest refused receipt (the adapter
  never runs for a denied delivery; one channel's refusal never blocks
  the others); appends one receipt per attempt; fills `pending →
  dispatched` exactly once. A REPLAYED occurrence dispatches NOTHING —
  it appends one duplicate-skipped receipt PER TARGETED CHANNEL on the
  winning notification and returns `duplicate: true`.
- **`getNotification` / `resolveNotificationOwnership` /
  `listNotificationsForClient`** — the record reads + the canonical
  ownership resolution (the route-layer uniform-404 input).
- **`listNotificationReceipts`** — the complete honest delivery history
  (oldest first).
- **`listInboxItems` (+ workspace filter/unread filter) /
  `listInboxItemsForWorkspace` / `getInboxItem`** — THE IN-APP READ
  SURFACE (the future console inbox): the projection rows JOINED with
  their notifications.
- **`markInboxItemRead`** — the read transition (append-only, exactly
  once; an already-read item is the honest 409; an unknown notification
  is the uniform 404).

### 1.3 The HTTP surface (src/api/notification-delivery-routes.ts)

| Route | Contract |
| --- | --- |
| `POST /api/clients/:clientId/notifications` | The delivery command (owner\|admin). One POST = claim + gates + receipts. A replayed occurrence returns the winning notification with the honest duplicate-skipped receipts (`duplicate: true`). |
| `GET /api/clients/:clientId/notifications` | The in-app inbox view (any active member); `?workspaceId=…` and `?unread=true` filters. |
| `GET /api/clients/:clientId/notifications/:notificationId` | One notification + its FULL receipt tail (any active member). |
| `POST /api/clients/:clientId/notifications/:notificationId/read` | The in-app read transition (any active member — exactly once; the second read is the honest 409). |
| `GET /api/workspaces/:workspaceId/notifications` | The workspace's in-app slice (any active member). |

NO update route (§14 facts are immutable at creation — corrections are
NEW notifications), NO delete route (history is append-only,
DB-trigger-fenced) and NO dispatch/retry route (a dispatch/retry worker
plane is future Work Item territory — the receipt model already admits
append-only retries).

### 1.4 Boundaries (what this module deliberately does NOT do)

- **NO task/action state** (boundary rule 9 — the heart): no
  done/acknowledged/acted-on verb or column exists anywhere. The
  delivery status is the adapter-plane lifecycle ONLY (`pending →
  dispatched`); the read state is the in-app projection's DELIVERY fact.
  Reading a message is not acting on its subject.
- **NO notification-policy authoring** — which channels/urgencies a
  deployment prefers is `/policies` data, declared by operators through
  the existing policy-declaration surface; this module never re-states
  it.
- **NO future channel adapters** — WhatsApp/Telegram/SMS/Signal are
  DECLARED-but-UNIMPLEMENTED capability keys
  (`PLUGGABLE_NOTIFICATION_CHANNEL_KEYS`); an adapter registering one is
  refused fail-closed at module construction until its Work Item moves
  the key into `NOTIFICATION_DELIVERY_CHANNELS` as part of a NEW
  vocabulary version.
- **NO provider SDK / no network in the module** — the email adapter is
  the ONLY sanctioned provider-seam subtree
  (`internal/adapters/email-adapter.ts`) and rides the
  `EmailTransportPort` seam; no SMTP/provider client exists in src.
- **NO worker/scheduler/retry loop** — dispatch runs synchronously inside
  `deliverNotification`.

## 2. The DeliveryAdapter contract (AC-2)

```ts
interface NotificationDeliveryAdapter {
  readonly channel: NotificationDeliveryChannel;     // 'in_app' | 'email'
  readonly acceptedUrgencies: readonly NotificationUrgency[];
  readonly acceptedEventTypes: readonly NotificationEventType[] | null; // null = all
  accepts(input: { urgency; eventType }): boolean;
  deliver(input: AdapterDeliveryInput): Promise<AdapterDeliveryOutcome>;
}
```

- **In-app** (`internal/in-app-channel.ts`, module-internal): delivery =
  the durable inbox projection row; the provider message id is the inbox
  row id. Accepts every urgency/event type (the always-on baseline
  channel). Constructed INSIDE the module (it persists the module's own
  tables).
- **Email** (`internal/adapters/email-adapter.ts`, the sanctioned
  provider-seam subtree, wired at the composition root as DATA):
  - accepts `important | urgent | critical` (routine stays in-app — the
    declared MVP subset; broadening is /policies-or-console territory,
    never silent);
  - resolves recipients through the `NotificationRecipientResolutionPort`
    (the operator context of the notification's own scope chain) with
    the PURE selection policy `selectNotificationRecipients` (the ACTIVE
    `agency_owner` members with active identities — deduped, sorted,
    capped at `NOTIFICATION_EMAIL_MAX_RECIPIENTS = 25`; no address is
    EVER a request field or a guess — nothing resolves → the honest
    failed receipt);
  - resolves the provider credential through the
    `NotificationEmailCredentialPort` (the narrow structural view of the
    `/credentials` vault — READ-ONLY) by vault REFERENCE id in the
    notification's authorized-execution scope (a dead/mismatched
    reference → the honest failed receipt; the material exists
    in-process ONLY);
  - sends through the **EmailTransportPort** (the documented provider
    seam — see §4).

## 3. The per-channel policy gate (AC-3)

Every channel delivery is gated BEFORE the adapter call:

```
dimension:  'network'                       (the delivery plane's outbound dimension)
operation:  'notification.channel.<channel>'  (channelPolicyKey — e.g. notification.channel.email)
attributes: { urgency, eventType, sourceKind }
scope:      { agencyId, clientId }           (the notification's own scope chain)
```

Only an explicit **allow** permits (`enforcementOutcome`; deny AND
unknown both deny — the POL-001 contract). A denied channel records the
honest **refused** receipt carrying the policy decision id (the decision
itself lives in the policy engine's own append-only ledger — the FK
links it) and a bounded reason naming the policy key. **Disclosure:**
the gate rides the `network` dimension for ALL channels including the
in-app channel (no egress) — uniform fail-closed sanction semantics:
every channel must be explicitly sanctioned, egress or not. Rules can
scope by operation AND by the urgency/event-type attributes (e.g. deny
`notification.channel.email` when `urgency = 'important'`), which is
exactly "a channel not sanctioned for the urgency/event type fails
closed". A fresh agency with NO policy: both channels refused
(`no-active-policy` → unknown → deny) — proven in the integration
battery with zero provider egress.

## 4. The email provider seam (AC-7 — documented)

```
EmailTransportPort.send({ recipients, fromAddress, subject, body,
                          credentialMaterial }) → { messageId }
```

- The adapter contains NO provider SDK and NO network code. A real
  transport (SMTP or a provider API over the platform HTTP port — no
  SDK, the OpenRouterAdapter precedent) is FUTURE composition-root
  wiring: it implements the port, receives the resolved credential
  material in-process, returns the provider message id.
- Until a transport is supplied, the composition root constructs NO
  email adapter (the channel is simply absent; the in-app channel
  always delivers — the fail-closed `socialAccountFlows` precedent).
- The integration tests supply the DETERMINISTIC IN-REPO test double (an
  in-process object) through the disclosed composition seam
  (`AppOptions.notificationEmailTransport` +
  `AppOptions.notificationEmailProvider` — the transport, the vault
  reference id and the sender address). **NO real network calls exist
  anywhere in the test suite.**

## 5. Idempotency (AC-5)

The fence key: `(source kind, source id, event type, occurrence key)` —
the pure `composeNotificationFenceKey`. The occurrence key is the
producing authority's discriminator for DISTINCT occurrences of the
same event type from the same source (a transition counter, an epoch, an
event id; grammar `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`). The claim
(notification + fence) is ONE transaction; the DB unique fence is the
race-free backstop — concurrent first-delivery attempts converge on one
winner and the losers take the duplicate path (no gate, no adapter, one
duplicate-skipped receipt per targeted channel). Retries are NEW
receipt rows — the receipt tail has no UPDATE path at all
(trigger-fenced).

## 6. The frozen vocabularies (nd-vocab-v1)

- **Event types (9):** mission_attention_required, mission_terminal,
  execution_attention_required, deployment_attention_required,
  approval_required, anomaly_detected, quota_exhausted, policy_denied,
  system_notice.
- **Urgencies (4):** routine, important, urgent, critical.
- **Source kinds (8):** growth_mission, execution, deployment,
  workflow_instance, job, experiment, platform, extension.
- **Channels — implemented (2):** in_app, email. **Declared-pluggable
  (4):** whatsapp, telegram, sms, signal.
- **Receipt outcomes (4):** delivered, failed, refused, duplicate_skipped.
- **Delivery statuses (2):** pending, dispatched.

All are CHECK-fenced in migration 047. **Disclosure:** the receipts
`channel` CHECK admits the FULL six-key declared set (so a future
channel adapter appends receipts without migration churn) while the
module-level registration accepts only the implemented two (fail-closed
until their Work Items arrive) — a future channel = one vocabulary move
+ its adapter, no DB change.

## 7. Persistence (migration 047 — the choice DISCLOSED)

Four OWN tables only (see §1.1). House-style fences: the tenant
scope-chain trigger (client-belongs-to-agency, workspace-to-client — a
forged cross-tenant UPDATE is rejected), the §14 content immutability
trigger, the single `pending → dispatched` fill (CAS version advance),
no-DELETE on notifications, fully append-only fences + receipts
(UPDATE/DELETE trigger-rejected), the 1:1 inbox fence with the single
append-only read transition, the honest receipt payload-shape CHECK
(delivered carries no reason; failed/refused carry the REQUIRED reason;
duplicate_skipped carries neither reason nor decision nor message id).
**No token/secret/material/handle column exists anywhere** — the
provider credential is the `/credentials` vault reference resolved at
delivery time (the reference id arrives through the composition seam,
never a module table). The receipts' `policy_decision_id` FK-anchors
the policy engine's own ledger.

## 10. Disclosures & limitations (honest)

1. **The production email transport does not exist yet (by design).** The
   §14 email MVP ships the ADAPTER (recipients, vault credential,
   envelope, outcomes, receipts) against the documented
   `EmailTransportPort` seam; a real SMTP/API transport is future
   composition-root wiring (and with it the env-config production
   provider settings — today the composition seam is the explicit
   `AppOptions` surface, the `socialAccountFlows` precedent). Until a
   transport is wired the email channel is ABSENT and the in-app channel
   carries every notification — fail-closed, never a fake send.
2. **The provider credential is a single explicit vault reference**
   (agency-scoped). A deployment serving multiple agencies configures
   its sending reference per what it wires; a notification whose agency
   has no resolvable reference fails the EMAIL channel honestly (the
   failed receipt names it) while the in-app channel still delivers.
   Per-agency provider-credential mapping is notification-policy/console
   territory (a later Work Item), never silently invented here.
3. **The HTTP email-channel golden path** runs through the module-level
   surface in the integration suite (the spawned production API cannot
   carry an in-process test transport across the process boundary); the
   HTTP round trip itself is proven on the same composition's in-app
   channel. The email channel's HTTP-path behavior is identical by
   construction (one composition seam).
4. **No retry/dispatch worker.** A dispatch/retry plane (re-dispatching
   the non-delivered channels of a dispatched notification) is future
   Work Item territory; the receipt model already admits it (append-only
   new rows; the module command is the single dispatch entry today).
5. **The per-channel gate rides the `network` policy dimension for every
   channel** (including the non-egress in-app channel) — the uniform
   fail-closed sanction posture (§3).
6. **The MVP recipient policy is the owning agency's active owners**
   (the accountable operators of the client context — pure, pinned;
   broadening is policy/console territory).

## 11. Risks

- The synchronous dispatch inside `deliverNotification` holds no
  transaction across adapter calls (claim → dispatch → receipts are
  separate steps): a crash between the claim and the dispatch fill
  leaves a `pending` notification with partial receipts — an honest,
  visible state the future retry worker can complete; the fence still
  prevents any double-delivery of the occurrence.
- The receipt `channel` CHECK admits the six declared keys; a future
  channel must still move its key into the implemented vocabulary (a
  reviewed, versioned change) before the module accepts its adapter —
  the DB cannot distinguish an accidental key typo in a future
  registration (the module-level fail-closed registration guard does).
- Agencies that never declare a `network` policy see every notification
  in-app-only-by-refusal (both channels refused, honestly recorded) —
  operators must declare the allowance to receive email; this is the
  intended fail-closed default, not a defect.
