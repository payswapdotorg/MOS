## 1. What this delivery is

MKT-069 introduces the durable **PRODUCT/MARKET INSPECTION AND MODEL
records** — the Product Intelligence layer of architecture-v1.6.md §8:

- the **agency-scoped Product Context records** carrying the **declared
  inputs** — public product/site URL(s), product-document references,
  source-code repository URL(s), connected source-workspace references,
  catalog/inventory references and current-analytics references — **each
  input carrying its authorization state** (public vs explicitly
  authorized). The declared inputs ride **IMMUTABLE version records**:
  corrections are NEW version records, never in-place rewrites;
- the **deterministic inspection pipeline**: fetch/extract over public
  product/site pages through the in-repo **GET-only page-reader contract**
  (the disclosed test-double fetcher; NO live network in the test suite)
  and authorized repository/workspace/catalog/analytics reads through the
  **/integrations public contract READ-ONLY** (a narrow structural port
  exposing `getConnection` + `executeRead` ONLY — `executeMutation` is
  structurally absent from the port type, so the module cannot express a
  mutation toward any external source). Every material source fact is
  retained as a **source-fact record with FULL provenance**: source
  URL/reference, fetched-at, extractor identity, content hash, extraction
  notes. Facts are **extracted observations, never conclusions** (§7);
- the **derived model records** — the §8 derivation set: product
  capabilities, user/problem hypotheses, ICP/audience hypotheses, value
  propositions, conversion paths, content-worthy features, market language
  and commercial metrics to optimize — each carrying (a) its **evidence
  references** (FK-anchored same-context source-fact ids), (b) its
  **AI-assistance disclosure** (model identity + call reference, validated
  through the /ai-runtime registry) when derived with ai-runtime
  assistance, and (c) a **verification state** computed SERVER-SIDE from
  its own evidence set: a derived record without backing evidence
  references is marked `unverified` and can never be presented as
  established (§7: "Model output is a claim unless backed by evidence").
  Hypotheses are hypotheses: they never become facts by repetition — every
  derived record ships the **claim-tier disclosure** and NO promotion path
  exists;
- the **risk flags**: explicit append-only risk records
  (compliance/privacy/toxicity/commercial/operational) with the severity
  vocabulary, evidence links and server-derived provenance.

What it is NOT (the bounded scope):

- **NO mutation surface toward any external source** (boundary rule 7).
  The read-only guarantee is STRUCTURAL: the page-reader port has exactly
  one method (`fetch`) and its request type has **no method field and no
  body field** — GET is the only expressible verb; the integrations
  structural port exposes `getConnection` + `executeRead` only. The future
  write seam is a DOCUMENTED, deliberately-unwired constant
  (`PRODUCT_INTELLIGENCE_WRITE_CAPABILITY_SEAM`) — see §7;
- **NO mission planning** (MKT-070 — the Product Marketing Mission
  Planner — is a LATER Work Item and attaches these model records BY
  REFERENCE through the read surface; AC-6). No channel-mix,
  metric-selection, attribution or mission-strategy logic exists;
- **NO web research** (MKT-062 — see the dependency disclosure in §8);
- **NO second evidence authority**: source facts are retained in this
  module's OWN migration-048 tables; the /evidence direction is consumed
  through the SHARED §21 material-key guard (the /sales-continuity
  /decisions precedent) — the ONE /evidence import
  (`containsMaterialKey`) lives in the module's store.

## 4. The inspection/derivation pipeline

```text
runProductInspection(contextId)
  ├── resolve context + CURRENT declared version + inputs (read-only)
  ├── for each input (declaration order):
  │     ├── public web kind  → pageReader.fetch({url, timeoutMs, sizeCapBytes})   [GET-only]
  │     │     ├── ok        → extractHtmlSourceFacts(body)  → 0..32 fact candidates
  │     │     ├── refused   → outcome 'fetch_transport_error'  (honest detail)
  │     │     └── http err  → outcome 'fetch_http_error'       (honest detail)
  │     └── authorized kind → integrations.getConnection (scope + connected checks)
  │           ├── not connected / foreign → 'read_refused'
  │           ├── PolicyDeniedError        → 'read_refused'
  │           └── executeRead(operation, {reference})
  │                 ├── ok + records → ≤25 'source_record' facts (verbatim)
  │                 ├── ok + 0 records → 'no_facts_extracted'
  │                 └── !ok / throw   → 'read_error'
  └── transaction (context row lock):
        ├── verify current_version_seq unchanged (mid-flight correction → 409)
        ├── insert the run (status: completed | partial | failed — honest)
        ├── insert the per-input outcome rows
        └── insert the retained facts (source ref, fetched-at, extractor,
            sha256 content hash of the MATERIAL, extraction notes, content)
```

- The **deterministic extractor** (`html-extract-v1`) is a PURE function
  (no clock, no randomness, no network): the same page always yields the
  same facts in the same order. It retains the document-head identity
  observations (title, meta description/keywords, og:title/description,
  canonical URL, language), the first ten headings and one bounded
  tag-stripped text excerpt — all VERBATIM, whitespace-collapsed and
  length-bounded.
- The **content hash** is the sha256 of the material a fact was extracted
  from: the fetched page body (all facts from one page share it) or the
  normalized provider record data (per authorized read).
- **Derivation** (the derived model records) is NOT performed by the
  inspection pipeline: the pipeline retains observations; the derived
  records are RECORDED by server-side callers (operators, the future
  MKT-070 planner) through `recordDerivedModel`, carrying their evidence
  references and AI-assistance disclosure.

- **The context-record guard**: identity/scope/provenance immutable; the
  CAS version advances by exactly one; the version pointer only ever

- **THE DEFERRABLE VERIFICATION INVARIANT** (the 025_policies deferred

- **The single-supersession fence** (the 015 /evidence pattern): at most

  its subject").
- **The integration-connection scope fence** (the 046 pattern): an

## 7. The read-only write seam (boundary rule 7 — documented, NOT built)

A future write capability toward inspected sources would arrive as a
**separately granted capability key** (e.g. `product-intelligence.write`)
consulted through the /policies public contract before any mutation, with
its own Work Item, its own policy dimension and its own audited gate. This
module defines NO such key, NO such gate and NO mutation method anywhere:

- the page-reader request type has **no method and no body field** — GET
  is the only expressible verb (the real adapter pins `method: 'GET'`);
- the integrations port type **cannot express** `executeMutation`,
  connection registration or webhook ingestion;
- the boundary test asserts all of this statically, plus that no
  write-capability key or write gate exists in the implementation code.

The seam is disclosed as the constant
`PRODUCT_INTELLIGENCE_WRITE_CAPABILITY_SEAM` on the public contract so the
rule is visible, not implicit.
