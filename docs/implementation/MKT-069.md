## 1. What this delivery is

MKT-069 introduces the durable **PRODUCT/MARKET INSPECTION AND MODEL record
layer** of v1.6: the agency-scoped Product Context records carrying the
declared inputs (each with its authorization state), the READ-ONLY
deterministic inspection pipeline over public sources and explicitly
authorized repository/workspace reads, the append-only source-fact ledger
with full provenance, the derived model records (the §8 derivation set)
with backing evidence references + verification states, and the
append-only risk flags.

What it is NOT (the bounded scope):

- **NO write capability toward any external source** (boundary rule 7:
  "Product Intelligence has read-only source-code/product inspection
  unless a separate write capability is explicitly granted"). The future
  write seam is a DOCUMENTED, deliberately-unwired constant
  (`PRODUCT_INTELLIGENCE_WRITE_CAPABILITY_SEAM`) — no code path consumes
  it, no route exists for it, and none of the module's ports can express
  a write (the read-only guarantee is STRUCTURAL: the fetcher port has
  exactly one method, `fetch`; the integrations structural port exposes
  `resolveConnectionOwnership` + `executeRead` only — `executeMutation`
  and the connection lifecycle are absent from the port type).
- **NO mission planning.** No channel-mix, metric-selection, attribution
  or mission-strategy logic exists (MKT-070 — the Product Marketing
  Mission Planner — is a LATER Work Item and attaches these records BY
  REFERENCE through the read surface; AC-6).
- **NO web research/niche clustering** (MKT-062), NO content/candidate
  records, NO experiment logic.
- **NO second evidence authority.** Source facts are THIS module's
  observation ledger; canonical evidence records remain /evidence's alone
  (cited read-only through the evidence port — the /decisions citation
  precedent).

Public entry: `src/modules/product-intelligence/public.ts`.

| Surface | Member | Notes |
| --- | --- | --- |
| create | `createProductContext({agencyId, declaration}, provenance)` | born at version 1; every explicitly-authorized input's `/integrations` connection reference must resolve within the agency (uniform 404 otherwise) |

  can never be asserted independently of the backing.
- **Risk kinds** (AC-4): `compliance`, `privacy`, `toxicity`,
  `commercial`, `operational`; **severities** (the /ai-runtime risk-class
  precedent): `low`, `medium`, `high`.
- Disclosures on every composed view: `vocabularyVersion` (`pi-vocab-v1`)
  and `inspectionCapability` (`source-inspection:fetch-read-only`).

## 4. The inspection/derivation pipeline

```text
declared inputs ──┬─ public ──────────▶ fetcher port (fetch ONLY) ──▶ site-page-extractor-v1
                  │                                                      │
                  └─ explicitly authorized ─▶ /integrations READ surface ─▶ integration-record-extractor-v1
                     (resolve + same-agency + connected;
                      operation 'source.read')                            ▼
                                                              product_source_facts (append-only, FULL provenance:
                                                              source URL/reference, fetched-at, extractor identity,
                                                              content hash, extraction notes)
                                                                            ▼
                                                   recordDerivedModel / recordRiskFlag
                                                   (backing source-fact ids + /evidence citations;
                                                    ai-assistance disclosure cross-checked via /ai-runtime;
                                                    verification state server-derived)
```

- **Determinism**: the extractors are pure functions (the same content
  always yields the same observation and the same sha-256 content hash).
- **All-or-nothing**: a failed fetch or authorized read fails the whole
  inspection command honestly — nothing persists.
- **The unchanged-source fence**: `UNIQUE (version, input, extractor,
  content_hash)` — an unchanged source never re-appends; a CHANGED source
  appends new facts.
- **CAS discipline**: fetches/reads happen OUTSIDE the write transaction
  (no external call under a row lock); the facts append under a re-locked
  row with the caller's expected version re-verified.
- **The ai-assistance disclosure is cross-checked, never self-attested**:
  the referenced `/ai-runtime` selection decision must resolve, belong to
  the context's agency, and have CHOSEN exactly the disclosed model
  identity (`chosenModelRegistryId`) — a mismatch is an honest 409.
- **Repetition never promotes**: an identical (context, kind, statement)
  derived record or risk flag is rejected (409) — restating a claim adds
  nothing, and the verification state reads PRESENCE of backing, never
  counts.

## 5. Storage (migration 048_product_intelligence.sql — the PRE-ASSIGNED number)

Six OWN tables (the 045/046 house style — CHECK-fenced vocabularies,
append-only UPDATE/DELETE rejection triggers, scope fences):

| Table | Role | Discipline |
| --- | --- | --- |
| `product_contexts` | the agency-scoped context record (CAS version + the version-tail pointer) | identity/scope immutable; CAS advances by exactly one; the pointer only ever ADVANCES and must reference an existing declared version; DELETE rejected |
| `product_context_versions` | the append-only declared-content tail (name + summary + provenance) | UPDATE/DELETE rejected — corrections are NEW version records |
| `product_context_inputs` | the per-version declared inputs (the §8 kinds + authorization states) | append-only with the version snapshot; the authorization-shape fence (authorized ⟺ reference; public ⟺ null); the per-kind authorization fence; the authorization FK anchor to `integration_connections` (the goal-FK precedent) |
| `product_source_facts` | the append-only source-fact ledger (AC-2) | UPDATE/DELETE rejected; the same-version input fence; the unchanged-source fence; full provenance columns |
| `product_derived_models` | the append-only derived model records (AC-3) | the verification-state shape fence; the hypothesis-kind fence; the ai-pair fence; the same-context source-fact fence; the same-agency evidence-citation fence; the repetition fence |
| `product_risk_flags` | the append-only risk flags (AC-4) | the same evidence/ai/repetition fences |

The migration's only touches of other authorities' tables are the
CHECK-ONLY trigger reads (`agencies`, `evidence`, `clients`,
`integration_connections`) plus the FK anchors — no row of another
authority is ever created or mutated from here.

## 9. Disclosures

- **The `/research` dependency timing** (AC-12): the registered row is
  the currently-satisfiable subset; `/research` joins at MKT-062 time.
- **The per-kind authorization map is an implementation decision**
  (§3): the architecture names the input kinds but not which may be
  public; the map is the smallest honest reading (a public product/site
  URL is public; an authenticated app environment and a connected source
  workspace are inherently authorized; the remaining kinds exist both
  ways), versioned with `pi-vocab-v1` and CHECK-fenced.
- **The `product_risk` derived kind vs the risk-flag family**: AC-3
  quotes the §8 derivation set (which includes "product risks") and AC-4
  separately specifies the explicit risk records. Both are implemented:
  `product_risk` is one of the nine derived kinds (the §8 set is complete
  1:1), AND the risk-flag family is the operative risk register with the
  risk-kind/severity vocabularies. A material product-risk derivation
  typically also files a risk flag; the duplication is model-vs-register,
  deliberate.
- **Derived records have no supersession path**: the ledgers are
  append-only; a revised claim is a NEW record with a distinct statement
  (the repetition fence only rejects IDENTICAL statements). Disclosed as
  the bounded AC-3 reading.
- **No §8 idempotency key on context creation** (the goals/missions
  precedent); every mutation is CAS-guarded.
- **The `agency_operator` role may READ but not mutate** product-context
  records at the route layer (the goals/missions posture); the MKT-070
  planner will drive mutations server-side as a service principal.
- **Authorized reads use the disclosed provider-neutral operation label
  `source.read`** (a read capability operation the repo/workspace-capable
  adapters of later Work Items will declare); the current first-party
  adapters do not declare it, so authorized-input inspection over the
  real adapter set fails honestly (disclosed in §7).
- **The inspection is all-or-nothing by design**: a single failed input
  fails the whole command (nothing persists) — the deterministic,
  honest-failure reading of AC-2; partial-success inspection would be a
  future, separately-justified behavior.
- **Environmental**: the known repo-wide environmental classes (the
  MinIO/S3 provisioning failures, the deployment-topology SIGTERM race,
  the redis-cache-lock flake) are unrelated to this module; see the
  delivery report for the exact clean-main comparison results.
