Work Item: **MKT-071** (spec/effective-backlog-v1.6.md §E: "extend the existing commerce integration boundary to catalog, product listing, price/inventory and order-event capabilities"; acceptance: "normalized catalog/order/listing capabilities with webhook idempotency and policy-gated mutations").

Dependencies: MKT-023 (the /integrations provider boundary), MKT-024 (the first-party connector mechanism + the commerce-cms connector) — both verified on the base chain.

Architecture anchors: spec/architecture-v1.6.md **§15** (the existing Integration boundary becomes capable of commerce operations: catalog read, product read/write where authorized, product listing, price/inventory read, order read, order webhook and attribution data) and **§16** (attribution is passthrough data; attribution is never silently treated as causal proof); spec/module-dependency-matrix-v1.6.md **boundary rule 8** (Commerce Discovery never writes directly to catalog/order tables; store mutations flow through Integrations).

This Work Item EXTENDS the existing `/integrations` commerce boundary — no new module, no new authority, no spec/ changes (the arch-check expected lists needed no update: no module registration, no matrix row).

## 1. What was delivered

### 1.1 The normalized commerce capability surface (AC-1)

The commerce capability-key vocabulary (frozen in `src/modules/integrations/public.ts`, `COMMERCE_CAPABILITY_KEYS` — the `'commerce-'` namespace is a CLOSED vocabulary enforced at adapter registration):

| Capability key | Kind | Operations | Adapter(s) |
|---|---|---|---|
| `commerce-catalog-read` | read | `listCatalog` (paged, category/product shape) | commerce-store, commerce-cms |
| `commerce-product-read` | read | `getProduct` | commerce-store, commerce-cms |
| `commerce-product-write` | **mutation** | `createProduct`, `updateProduct` | commerce-store ONLY |
| `commerce-listing-manage` | **mutation** | `createListing`, `updateListing`, `endListing` | commerce-store ONLY |
| `commerce-price-read` | read | `getPrice` | commerce-store, commerce-cms |
| `commerce-inventory-read` | read | `getInventory` | commerce-store, commerce-cms |
| `commerce-orders-read` | read (MKT-024 key, extended) | `listOrders` (+ `listOrderRecords` on commerce-store: paged, line-item shape) | commerce-store, commerce-cms |
| `commerce-order-webhook` | webhook (extends the event-stream family) | `order.created`, `order.updated`, `order.fulfilled`, `product.updated`, `listing.updated` | commerce-store |
| `commerce-event-stream` | webhook (the MKT-024 legacy key, kept first-class) | `order.updated`, `content.published` | commerce-cms |

**Two first-class commerce adapters** (both under the sanctioned `internal/adapters/commerce/` home, wired as DATA at the composition root):

- **`commerce-store`** (NEW, `commerce-store-adapter.ts`): the FULL v1.6 surface — every read above plus the two MUTATING capabilities. Its provider (a commerce store platform) authorizes mutations for connections whose token carries the `commerce.write` scope; a read-only token gets an honest `403 invalid_scope` refusal as DATA at runtime (the provider's per-connection authorization layer under the adapter's static declaration).
- **`commerce-cms`** (EXTENDED additively, `commerce-adapter.ts`): the FIRST-CLASS READ-ONLY commerce adapter — the MKT-024 orders/CMS/event-stream capabilities stay byte-identical, plus the four new read capabilities. Its provider grants READ scopes only, so the adapter declares NO mutation capability and never claims one (AC-4); a mutation attempt on it is rejected at capability discovery (422 `operation not declared by any mutation capability`).

**Capability-subset adapters are first-class**: the registry, module and routes treat the read-only subset exactly like the full surface; the round-trip test proves the subset round-trips honestly and rejects the rest.

Normalized record shapes (source-record envelopes, recordType `commerce.catalog-page` / `commerce.product` / `commerce.price` / `commerce.inventory` / `commerce.order`): the field contracts are typed in `public.ts` (`CommerceCatalogPageFields`, `CommerceProductFields`, `CommercePriceFields`, `CommerceInventoryFields`, `CommerceOrderFields` + `CommerceOrderLineItem`). Pure mapping functions live in `internal/adapter-support.ts` (the shared commerce provider JSON convention — paged cursors, product/price/inventory reads, order records with line items, mutation results, identified webhook events) and are re-exported through the module public entry for unit tests and future consumers (MKT-072).

### 1.2 The provider contract / test double (AC-2)

`tests/integration/helpers/commerce-provider.ts` — the LOCAL COMMERCE PROVIDER DOUBLE (the `oauth-provider.ts` house pattern): an in-process loopback HTTP server, fixture-driven, no live network. It implements the shared commerce provider JSON convention:

- **Reads**: `/health` (probe), `/commerce/v1/catalog?cursor=&limit=` (TWO fixture pages — pagination), `/commerce/v1/products/:id`, `/price`, `/inventory`, `/commerce/v1/orders` (the MKT-024 revenue shape), `/commerce/v1/order-records?cursor=` (TWO pages, full line-item records with attribution).
- **Mutations** (scoped `commerce.write`): `POST/PATCH /commerce/v1/products`, `POST/PATCH /commerce/v1/listings`, `POST .../listings/:id/end` — every received mutation RECORDED (the provider-visible side effects; zero side effects under refusals).
- **Authorization model** (the partial-capability variants): per-token grants — a full token (`commerce.read` + `commerce.write`) and a READ-ONLY token (`commerce.read` only); the provider enforces scopes on every request (`403 invalid_scope`).
- **Error taxonomy** (scriptable): `'ok'` | `'down'` (socket destroyed — provider-down/transport refused) | `'rate-limited'` (429 + Retry-After + X-RateLimit headers); plus the natural `401 unauthorized` for a wrong bearer token.
- **Webhook delivery**: `commerceWebhookSignature()` produces the `X-Commerce-Signature` HMAC-SHA256 header; the identified delivery payloads carry the provider's OWN event identity (`eventId`) that drives the dedup fence.

The MKT-024 sandbox provider (`sandbox-provider.ts`) was extended additively with the commerce-cms platform's read-only commerce endpoints (catalog/product/price/inventory fixtures + malformed variants).

### 1.3 Webhook idempotency (AC-3, AC-6)

Inbound order/product events are deduplicated by **(provider id, event id)** — `(adapter_key, provider_event_id)` — in a **dedicated fence** (migration 049 `commerce_webhook_event_fences`, UNIQUE index, fully append-only; the `notification_delivery_fences` MKT-068 precedent):

```
webhook → adapter HMAC verification (fail-closed 422, nothing recorded)
        → normalized provider event guard (fail-closed by rejection)
        → fence lookup
            REPLAY  → append ONLY the 'duplicate-received' history row
                      (referencing the ingested row it duplicated) —
                      200 deduplicated=true, never a silent drop; NO second
                      ledger event, NO second evidence
            FIRST   → derived 'source_fact' /evidence append (pinned
                      class/quality/provenance, through /evidence's own
                      public contract)
                    → ONE transaction: raw-ledger integration_events row +
                      the fence claim + the 'ingested' commerce_events row
                      (a concurrent duplicate race converges on the winner;
                      the loser records the duplicate-received row — see
                      §5 disclosures)
```

Event ingestion is **append-only with provenance**: received-at (server-stamped), provider (adapter key), **raw-event hash** (sha256 of the delivered payload — `hashWebhookPayload`), **normalized shape version** (`commerce-event-v1`).

**Event-stream continuity (AC-6)**: verified first deliveries append into the EXISTING `integration_events` ledger + `/evidence` exactly like the MKT-023 path (the `commerce-event-stream` family), and the fence composes with it (webhook → dedup → normalized append). Deliveries WITHOUT a provider event identity keep the legacy append-only semantics unchanged (no fence, no projection).

Two module surfaces:
- `ingestWebhookEvent` (the raw MKT-023 surface): a delivery carrying a provider event identity is fenced on first delivery; a REPLAY is rejected fail-closed (`ConflictError` naming the duplicate) — there is no fence bypass through the raw surface.
- `ingestIdentifiedWebhookEvent` (NEW, the idempotent twin): returns the dedup verdict + the appended records; the webhook ROUTE serves this surface (201 + the event shape for first deliveries — response-shape compatible with the MKT-023 contract; 200 + `deduplicated: true` + the duplicate-received row for replays).

### 1.4 Policy-gated mutations (AC-4)

Every mutating commerce operation passes the EXISTING `/integrations` policy gate **with its own capability key**: `requireDeclaredOperation` now returns the DECLARING capability, and the network-dimension action carries `attributes: { provider, capability: '<declaring capability key>' }` — so a policy rule can sanction exactly the mutation classes it means to (e.g. deny `integration.mutate` with `capability: 'commerce-product-write'` while allowing listing management). A policy not sanctioning the mutation fails closed: `PolicyDeniedError` (the honest 403-equivalent) BEFORE any credential material resolution or provider traffic, recorded in the `/policies` decision ledger — never a silent skip. The adapter NEVER claims a mutation capability the provider does not grant (commerce-cms declares none; commerce-store's provider enforces token scopes at runtime with honest `invalid_scope` data failures).

**The commerce mutation ledger** (migration 049 `commerce_mutation_records`): every store mutation that flowed through the boundary lands in this append-only ledger with its capability key (CHECK-fenced to `commerce-product-write`/`commerce-listing-manage`), the operation, the honest provider outcome (refusals included) and the gating policy decision id — the audit surface proving store mutations flow through Integrations and only Integrations (matrix boundary rule 8).

### 1.5 Attribution passthrough (AC-5, §16)

Order records (`CommerceOrderFields.attribution`) and order-event normalized shapes (`NormalizedProviderEvent.normalized`) carry the provider's attribution/reference fields **VERBATIM** as passthrough data — deep-equal, no transformation, no computation. NO attribution linking, matching or causal computation exists anywhere in the commerce layer (asserted statically by the boundary test: the forbidden vocabulary is absent from the code). MKT-073 owns attribution later.

### 1.6 Routes

- `POST /api/clients/:clientId/connections/:connectionId/webhook` — now serves the IDEMPOTENT surface (201 first delivery / 200 `deduplicated:true` replay / 422 unverified).
- `GET /api/clients/:clientId/commerce-events` — the commerce event history (ingested + duplicate-received rows).
- `GET /api/commerce-events/:commerceEventId` — one history row (member of the owning agency; uniform 404).
- `GET /api/clients/:clientId/commerce-mutations` — the commerce mutation ledger read-back.

**AC-8 hardening (disclosed)**: the `clientOwner`/`requireConnectionInClient` helpers and the list/single routes in `integrations-routes.ts` gained `isUuid` guards so malformed identifiers are the SAME uniform 404 as unknown/foreign ones (the house fail-closed battery, the MKT-055 social-accounts precedent). Before this delivery the older integrations routes surfaced the raw pg uuid-syntax error as a 500 for malformed ids; the whole route family now answers the uniform 404.

## 4. Boundary proofs

- **Mutations through the gate only**: no commerce mutation path exists outside `executeMutation` (the module's fail-closed gate: ownership → live pipe → capability discovery → network policy WITH the capability key → secrets policy → credential material → adapter); every executed mutation lands in the append-only `commerce_mutation_records` ledger (boundary rule 8's audit surface). Commerce Discovery (MKT-072, later) has NO direct store-write path available to it — MOS owns no catalog/order tables at all.
- **Append-only event history**: `commerce_events` rejects UPDATE and DELETE by trigger; the raw ledger `integration_events` keeps its migration-029 append-only backstops; the fence is fully append-only.
- **Isolation battery**: anonymous 401, uniform 404 (foreign ≡ unknown ≡ malformed — now including malformed ids on the older route family), suspended-membership 403, agency/server-derived scope on every surface.

## 5. Honest limitations & disclosures

1. **The concurrent-replay race leaves a possibly-orphaned evidence observation.** The first-delivery path appends the derived `/evidence` observation BEFORE the fence-claiming transaction (the evidence append is a cross-module call and cannot join the store transaction). Under a rare CONCURRENT duplicate first delivery, the losing attempt's evidence row remains — an honest observation of a delivery that really arrived — while the fence guarantees at-most-one INGESTED event (the loser records the duplicate-received row). Sequential replays (the normal case) never orphan anything: the fence is consulted before any append.
2. **No local catalog/listing projection.** Deliberate (see §1.7): the provider store stays the sole catalog authority; MOS keeps only the event history + mutation ledger + fence. If MKT-072 requires a local projection for planning, that is a NEW disclosed decision.
3. **Connection bookkeeping semantics preserved**: any `ok=false` adapter outcome (including provider refusals and malformed payloads) marks the connection `error/unreachable` per the FROZEN MKT-023 bookkeeping; recovery is the explicit connect transition (operational plumbing, never terminal). The tests reconnect after expected failures.
4. **The webhook route response changed shape for identified replays only**: first deliveries respond exactly like the MKT-023 contract (201 + the event shape, plus additive `providerEventId`/`commerceEventId` fields when present); replays respond 200 with the dedup outcome (a deliberate, disclosed contract addition — the idempotency the AC demands).
5. **Capability-scoped policy attributes are additive**: existing rules (operations-only, provider-scoped) are unaffected; only rules that declare a `capability` attribute key match on it.
6. **The `commerce-event-stream` legacy key** (MKT-024) is included in the frozen commerce vocabulary for continuity — the closed-namespace fence accepts it; `commerce-order-webhook` extends the family with identified/idempotent semantics.
