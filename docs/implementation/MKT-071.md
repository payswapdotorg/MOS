## 1. Contract summary

### 1.1 What this delivery IS

The commerce extension of the EXISTING /integrations boundary
(MKT-023/024), in four layers:

| Layer | Surface |
| --- | --- |
| **Normalized commerce contract** (`internal/commerce-normalization.ts`, re-exported through `public.ts`) | The closed capability-key/event-kind/delivery-outcome/shape-version vocabularies; the capability-subset declaration (`commerceCapabilitiesForProfile` — a read-only grant yields a read-only adapter, first-class); the provider scope convention (`commerceScopeProblem` — the adapter-side authorization pre-check); the PURE wire→normalized mapping functions (catalog pages, product detail, price, inventory, order details with line items, listing mutations, the webhook-event normalization with the attribution passthrough, the raw-event hash). Everything is exported through the module PUBLIC entry so the normalized mapping semantics are part of the TESTED module contract (AC-10) AND so the first-party commerce adapter consumes them through its single sanctioned import (the public entry — no connector import surface changed). |
| **Adapter extension** (`internal/adapters/commerce/commerce-adapter.ts`) | The MKT-024 `CommerceCmsAdapter` gains the MKT-071 operations (see §2), the construction-time capability profile (`grantedCapabilityKeys` — validated against the closed vocabulary; unknown keys fail construction loudly), the per-credential scope pre-check, the paged-read cursor, and the webhook-event identity composition. The frozen MKT-024 behaviors are unchanged: `listOrders` still maps order totals to revenue metric observations, `listContent` still maps CMS content to versioned source facts, and webhook deliveries WITHOUT a provider event id keep the legacy append-only path. |
| **Webhook idempotency** (`internal/module.ts` + `internal/store.ts` + migration 049) | Verified deliveries carrying the provider's own event id are deduplicated on the **(adapter_key, provider_event_id)** pair: the first delivery appends the event ledger row (migration 029 — the SAME event-stream path), the derived `source_fact` /evidence observation and the normalized projection (migration 049) inside ONE transaction whose first insert is the FENCE CLAIM; every replay is an honest `duplicate` receipt (never a silent drop) that references the first delivery and records ITS OWN raw-event hash. |
| **Policy-gated mutations** (`internal/module.ts`) | Every read/mutation policy gate now carries the DECLARING capability key as a decision attribute (`capability: 'commerce-product-write'` / `'commerce-listing-manage'` / …), so a policy not sanctioning a specific mutation capability fails closed (403 POLICY_DENIED with the capability named on the decision) — and capability-SCOPED rules are matchable (§5). |

### 1.2 What this delivery deliberately is NOT

- **No new module** — `/integrations` stays the sole commerce-capable
  boundary; nothing is registered in `spec/` (the arch-check expected
  lists needed no change — disclosed in §7).
- **No catalog/product/listing/order STATE tables** — the provider stays
  the commerce catalog/order authority (AGENTS.md "Commerce
  orders/inventory remain provider authority accessed through
  /integrations"; architecture §19 "not a … second commerce order
  authority"). Listing/product mutations are PROVIDER calls through the
  adapter port; MOS records event history + projections only.
- **No attribution linking/matching/causal computation** — the
  attribution/reference fields ride VERBATIM as passthrough data
  (architecture §16); MKT-073 owns linking later.
- **No Commerce Discovery missions** (MKT-072) and no second human
  marketplace/notification authority — untouched.

REAL read-only adapter through a SECOND spawned API process configured
with `MOS_COMMERCE_GRANTED_CAPABILITIES` (route surface).

## 3. Webhook idempotency design (AC-3/AC-6)

```
POST .../connections/:id/webhook
  → route: uniform-404 ownership fence → module:
    → fail-closed secrets-dimension policy gate (integration.webhook)
    → credential material resolution (in-process only)
    → adapter.verifyWebhook (HMAC X-Commerce-Signature)
        ├─ unverified → 422, NOTHING recorded (unchanged MKT-023 posture)
        ├─ no provider event id → LEGACY append-only path (unchanged)
        └─ event id present → normalize (fail-closed on unknown kinds /
             malformed bodies / non-scalar attribution) →
           module: validate identity bounds + §21 material-key backstop
             → dedup lookup (adapter_key, provider_event_id)
                 ├─ INGESTED elsewhere + SAME client → DUPLICATE path:
                 │    append 'duplicate' receipt (first_receipt_id → the
                 │    original, ITS OWN raw hash) → 200 duplicate:true,
                 │    the ORIGINAL event + projection returned; ledger /
                 │    evidence / projection UNTOUCHED
                 ├─ INGESTED elsewhere + OTHER client → ConflictError 409
                 │    (the global provider event-id namespace is
                 │    tenant-fenced — no cross-tenant oracle)
                 └─ not ingested → /evidence source_fact append →
                      ONE transaction { ingested receipt (the fence
                      claim) + ledger event + normalized projection } →
                      201 duplicate:false; a concurrent loser converges
                      on the partial-unique fence and is recorded as a
                      duplicate (the transaction aborted whole)
```

Read-backs: `GET /api/clients/:id/commerce-event-receipts` (the honest
delivery history — ingested AND duplicate rows) and
`GET /api/clients/:id/commerce-events` (one projection row per INGESTED
event, with the attribution passthrough verbatim).

## 4. Persistence — migration 049 (AC-9)

**Table-ownership choice (DISCLOSED):** MKT-071 registers NO new module,
so BOTH tables are OWNED by /integrations following the module's own
migration-029 store pattern:

- `commerce_event_receipts` — the webhook dedup fence + delivery history:
  the `(adapter_key, provider_event_id)` partial-unique INGESTED fence;
  CHECK-fenced vocabularies (delivery outcomes `ingested|duplicate`, the
  closed order/product event kinds — exactly the `commerce-order-webhook`
  capability's declared operations — and the normalized shape versions
  `commerce-order-v1|commerce-product-v1`); the raw-event sha256 per
  delivery; server-derived provenance; append-only UPDATE/DELETE
  rejection triggers; connection-consistency and duplicate-reference
  backstops.
- `commerce_events` — the normalized event projection: one immutable row
  per INGESTED event (duplicates never project) referencing the
  migration-029 ledger row (event-stream continuity) and the ingested
  receipt; the normalized payload + the attribution passthrough column
  (both CHECKed against material-shaped keys via the SHARED
  migration-029 IMMUTABLE validators); the projection-consistency
  trigger proves the projection can never disagree with its fence row.

**Capability-key fencing (disclosed):** capabilities are ADAPTER-DECLARED
registry data — the migration-029 discipline explicitly keeps the
database from storing the adapter set, so migration 049 CHECK-fences the
STORED vocabularies instead: the event-kind vocabulary IS the
commerce-order-webhook capability's operation list (fenced), together
with the delivery outcomes and shape versions. No capability-key column
exists (that would contradict the module's own frozen storage posture).

**No listing/product projection:** the store requires none — listing and
product state remain provider authority (§1.1); MOS records only the
event history + projections.

## 5. Policy gates (AC-4)

- Every mutating commerce operation passes the EXISTING fail-closed
  /integrations policy gates (network `integration.mutate` + secrets
  `integration.credential`) BEFORE any credential resolution or provider
  call — a policy not sanctioning the mutation fails closed with the
  honest 403 POLICY_DENIED and ZERO provider traffic (proven by the
  provider double's counters).
- The gate action now carries the DECLARING capability key
  (`attributes.capability`), so the decision record names WHICH commerce
  mutation capability was attempted, and client-scoped rules can deny
  per capability: the integration test declares a deny on
  `integration.mutate` with `attributes { capability:
  'commerce-product-write' }` and proves product writes are blocked
  while listing management stays allowed on the same connection.
- The adapter NEVER claims a mutation capability the provider does not
  grant: the construction profile (unknown keys fail loudly) and the
  per-credential scope pre-check (`products:write` / `listings:write`)
  refuse BEFORE any provider traffic; the provider's own 403
  (insufficient_scope) surfaces as the labeled `invalid-scope` data
  error (defense in depth, both layers tested).

## 6. Attribution passthrough (AC-5)

The provider's attribution/reference fields (e.g. `attributionRef`,
`utmSource`, `utmCampaign`, `landingRoute`) ride VERBATIM through:

- the `listOrderDetails` records (`commerce.order` source-record
  envelopes: `fields.attribution`, deep-equal asserted), and
- the normalized event projection (`commerce_events.attribution` +
  inline in `normalizedPayload`, deep-equal asserted).

Scalar fields are carried unmodified; non-scalar reference values fail
closed (the normalized contract carries SCALAR passthrough reference
fields). NO linking, matching or causal computation exists anywhere in
this module — the fields are recorded, never interpreted (MKT-073 owns
linking later).

  migration number 049 remains correct: 047/048 are the siblings'.
- **Spec touches: NONE.** No module is registered (arch-check parses the
  frozen §6 module list and the dependency matrix — both unchanged); the
  expected-migration-list maintenance lives in the architecture TESTS
  (the infra-adapters list + the sibling tail assertions), which is where
  the house keeps it.
- **Shared-file touches (all additive):** `src/composition-root.ts`
  (passes the capability profile to the commerce adapter — one
  conditional spread), `src/platform/config/config.ts` (the
  `MOS_COMMERCE_GRANTED_CAPABILITIES` parse + `describeConfig` entry),
  `src/api/integrations-routes.ts` (this module's own route surface:
  webhook outcome serialization, pageCursor, two read-back routes, UUID
  guards), and the six architecture-test files above.
  `src/api/application.ts` and `tests/architecture/arch-check.test.ts`
  needed NO change.
- **The "suspended 403" of the house fail-closed battery** maps to the
  suspended MEMBERSHIP (403, tested); a suspended CONNECTION on
  capability calls is the house ConflictError (409, tested with zero
  provider traffic) — the frozen MKT-023 behavior, unchanged.
- **Pre-existing latent gap hardened (in-scope surfaces only):** the
  MKT-023 integrations routes did not UUID-guard path/body identifiers,
  so a malformed id reached PostgreSQL and 500'd. The MKT-071 surfaces
  (connection-scoped routes via `requireConnectionInClient`, the client
  owner resolution, and the two commerce read-back routes) now carry the
  house UUID guard (the social-accounts/ai-operator pattern) so
  foreign≡unknown≡malformed are the uniform 404 on THIS Work Item's
  surfaces. Older non-commerce surfaces outside this delivery's scope
  (e.g. `GET /api/clients/:id/connections` with a malformed CLIENT id)
  retain their pre-existing behavior.
- **The legacy webhook path is deliberately non-idempotent:** deliveries
  without a provider event id cannot be deduplicated (there is no
  identity) — they keep the MKT-023/024 append-only behavior; no dedup
  is fabricated for them. Only order/product events carrying the
  provider's event id enter the fence.
- **Concurrent-replay semantics:** a concurrent FIRST delivery that
  loses the fence race is recorded as an honest duplicate (the store's
  transaction aborts whole — no orphan ledger/projection rows); the
  /evidence observation of the loser may be appended before the race is
  resolved (the evidence append precedes the transactional claim, the
  house ordering) — an orphaned evidence row is the pre-existing
  MKT-023/024 failure posture for evidence, disclosed here.
- **Environmental:** all six gates ran green in this sandbox — no
  MinIO/S3, redis-lock or deployment-topology flakes were encountered
  (the known environmental classes did not reproduce here).
