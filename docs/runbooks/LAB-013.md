## 3. Migration 067 — the fences

- Nine own tables ONLY (the §17 flow stages, created in the flow's own
  order so every citation points backward — the chain is acyclic by
  construction).
- CHECK-fenced closed vocabularies on every enumerated column: the
  actor split on EVERY stage table, the stage lifecycles, the
  verdict/outcome/fulfillment vocabularies, the origin + implementation
  kinds, the §16 action kinds, the strategy-citation kinds, the
  human-plane + real-test authority vocabularies, the jsonb key/shape
  fences on the structured citations (strategy_citation, required_action,
  quality_evaluator, cost/latency ceilings, provenance, implementation,
  human_plane_citation, real_test_citation), and the pinned
  `'lab-capabilities-contract-v1'` on every table.
- The FK anchors are EXACTLY the tenant tables (agencies, clients,
  workspaces) + same-module flow-stage rows — NO FK into /lab,
  /lab-agent-body, /integrations or ANY other module.
- The guarded lifecycles: identity/scope/config immutable; the single
  legal status advances (no resurrection, no reopen); the request's
  provider echo appears ONLY on the dispatch advance and is FROZEN after
  (a cancellation may not fabricate an outcome); the version chain scope
  + key fence on corrections.
- Append-only outright: results, verifications, simulations and
  real-tests reject UPDATE and DELETE; NO row of ANY stage table is ever
  deleted (nine no-delete triggers).
- THE UNVERIFIED-NEVER-PRESENTED trigger: a capability version citing a
  verification may cite ONLY a verdict 'pass' verification in its own
  scope (the module gate runs first; the trigger is the backstop).
- NO binary column, NO secret material, NO marketplace vocabulary
  anywhere (the delivered artifact is a bounded jsonb DESCRIPTOR).

## 5. Disclosures

- **THE ARENA ADAPTER IS THE COMPOSITION-ROOT SEAM, NOT MODULE CODE**
  (by design): the module knows only the two-method structural port;
  the composition root wraps the REAL /integrations instance
  (`listRegisteredAdapters` + `executeMutation` delegations — the
  contentStudioAgentBodies disclosed-wrapper precedent). No Arena
  provider adapter is wired as a first-party /integrations connector
  yet — an actual Arena connector registration is a provider-adapter
  Work Item (the /integrations registry is data-driven); the port makes
  that a pure composition-root wiring change with zero module impact.
- **The first-party quality evaluator is deliberately honest, not
  magic**: it performs the deterministic shape evaluation (the delivered
  artifact against the contract's declared output schema + the declared
  evaluation contract echoed on the evidence). Model-graded or
  human-graded evaluator backends arrive as future port implementations
  at the composition-root seam — never silent reinterpretation of the
  declared data.
- **A correction does not inherit the acquisition citations** (disclosed
  judgment call): `correctCapability` appends a new draft version with
  the first_party_declared origin and no verification citation — the
  LAB-011 per-version activation gate applies, and the corrected
  version is honestly unverified until new verified evidence exists.
  Re-linking a correction to new acquisition evidence is a future
  LAB-021/024 composition (the module's insert path supports it through
  the normal flow).
- **The human-plane fulfillment may complete a PENDING request**
  (disclosed judgment call — the smallest architecture-consistent
  reading of §17's "governed Arena request → human/provider result"):
  the human plane can fulfill asynchronously without a provider
  mutation echo, so the module advances pending → completed with the
  provider echo honestly null rather than blocking the human
  fulfillment on a dispatch. The provider-fulfilled path still requires
  the completed successful dispatch.
- **The request→result cardinality is 1→N by design**: multiple results
  may attach to one request (provider + human-plane fulfillments, or
  re-deliveries); each result carries its own verification chain. No
  uniqueness fence was placed on (request, result) because the §17 flow
  allows the honest multi-delivery reading; the capability version
  cites exactly ONE passing verification.
- **The spec registration is the granted worker exception**: the
  delivery appends the `/lab-capabilities` module list line + the
  registration paragraph to `spec/architecture.md` §6 (after the
  /lab-features paragraph — the LAB-003 precedent) and registers the
  module in the composition root + `ApplicationModules`; NO checker
  provision entry was added (the provision mechanism is structurally
  for spec-pending modules only). NO matrix row was added —
  `/lab-capabilities` consumes no other module (the /lab family
  empty-allowance posture, per the TL's pre-clearance).
- **Migration numbering**: 067 is pre-assigned (066 held by the
  in-flight parallel LAB-004 worker); the sibling boundary tests re-pin
  the canonical migration-list tail positions mechanically (the
