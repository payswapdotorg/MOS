## 1. Contract summary

### 1.1 What this delivery IS (and deliberately is NOT)

MKT-056 **EXTENDS `/social-accounts`** (the dispatch: *"Extend, do not
duplicate"*) — **NO new module, NO new spec §6 line, NO new matrix row**
(the frozen v1.6 matrix defines no social-adapter module; the
`/social-accounts` row `──→ /integrations, /credentials, /policies,
/workspaces` is UNCHANGED and remains exactly the MKT-055 registration —
the v1.6 row's `/clients` allowance stays deliberately unused, same
posture as MKT-055). The delivery is **contract-level only**: the
normalized capability plane + the adapter port + the conformance suite.
**NO live provider calls and NO concrete platform adapter ship here** —
those are MKT-057..061 (YouTube, Instagram Professional, Facebook Pages,
TikTok, X), which import the contract and run the conformance suite
against their own platform doubles.

### 1.2 The module API surface (module-level ONLY — no HTTP routes)

`listRegisteredSocialAdapters` (the registry as data) ·
`resolveAccountCapabilityMatrix` (the declared subset + the per-capability
scope satisfaction + the authorization-usable flag) · the ten normalized
operations (`verifyAccountIdentity`, `readAccountProfile`,
`discoverPublicContent`, `listOwnContent`, `getContent`,
`readAccountAnalytics`, `readContentAnalytics`, `readRestrictionSignals`,
`submitPublish`, `refreshPublishStatus`) · the publish-ledger reads
(`getPublishAttempt`, `listPublishAttemptsForAccount`,
`listPublishAttemptsForClient`, `listPublishStatusObservations`).

**Deliberately NOT shipped:** HTTP routes (the server-side consumers —
the adapter deliveries' host wiring and the MKT-065 distribution planner
— arrive later; the MKT-055 `getUsableAuthorization` module-level-only
precedent), content normalization into evidence/candidates (MKT-062),
platform-health interpretation (MKT-066), distribution planning/rights
gates (MKT-063/065). This contract **records and reports; it never
interprets**.

### 1.3 The fail-closed chain of every provider-touching operation

```
account lookup (unknown/foreign → uniform 404; dead binding → 409)
→ adapter registry lookup (no adapter registered for the platform → 409)
→ capability matrix (operation outside the declared subset → DATA failure
   'unsupported-capability', ZERO policy/provider work)
→ usable authorization (no authorized grant / lazy expiry / dead vault
   reference → DATA failure 'auth-expired')
→ scope pre-check (a required scope missing from the VERBATIM list →
   DATA failure 'insufficient-scope')
→ /policies network gate (non-allow → DATA failure 'policy-denied')
→ /policies secrets gate (non-allow → DATA failure 'policy-denied')
→ credential material resolution (in-process only, §21)
→ the adapter call (invocation failures return as DATA, never thrown)
→ the publish ledger (claim → fill; observations append)
```

Only **malformed input** throws (`InvalidRequestError` — fail-closed by
rejection, zero rows) and only **identity errors** throw
(`NotFoundError`/`ConflictError` — the MKT-055 uniform-404/409 posture).

## 2. The capability matrix vocabulary

```
families:       account | content-read | analytics-read | publish | restriction-signals
account:        verifyAccountIdentity | getAccountProfile
content-read:   discoverPublicContent | listOwnContent | getContent
analytics-read: readAccountAnalytics | readContentAnalytics
publish:        submitPublish | getPublishStatus
restrictions:   readRestrictionSignals

failure codes:  auth-expired | rate-limited | restricted | policy-denied |
                provider-unavailable | unsupported-capability | insufficient-scope
retryable:      rate-limited, provider-unavailable (derived — never declared)

publish states: submitted (born, UNKNOWN-in-flight) → accepted | published |
                failed | restricted (the single completion fill; terminal)
```

**Storage choice (disclosed):** NO capability-registration table — the
matrix is **adapter-declared registry data validated at construction**
(the migration-029 discipline "the database never stores the adapter
set"; the MKT-071 commerce precedent). What migration 050 CHECK-fences is
the OUTCOME vocabulary the matrix gates (publish states + failure codes).
The publish ledger IS architecturally required storage: a publish is a
side effect, and the AGENTS.md runtime rule ("non-idempotent unknown
side effects must not be blindly replayed") demands a durable fence.

## 3. The conformance suite (usage for MKT-057..061)

```ts
import { runSocialAdapterConformanceSuite } from '../tests/integration/helpers/social-adapter-conformance.ts';

const report = await runSocialAdapterConformanceSuite({
  adapter: myPlatformAdapter,        // implements SocialPlatformAdapter
  adapterHandle: myPlatformDouble,   // the double's observation surface:
                                     // callCount/contextsOf/setFailure/
                                     // clearFailure/advancePublish/
                                     // publishesForIdempotencyKey
  provider: myOAuthProviderDouble,   // the platform's SocialAccountFlowImplementation
                                     // backing double (the local-OAuth precedent)
  label: 'youtube',                  // unique embedded-database label
});
assert.equal(report.failed, 0);
```

The suite boots its own embedded-PostgreSQL stack + spawned API + the
in-process app with the adapter under test through the DISCLOSED
composition seams (`AppOptions.socialPlatformAdapters` +
`AppOptions.integrationAdapters` + `socialAccountFlows`), then runs the
17-scenario battery: registry data + capability-matrix view · verbatim
identity/scope/tag/config/material propagation · content/analytics/
restriction reads · the publish submit → replay idempotency → status
observation lifecycle · capability-subset enforcement (undeclared
families fail closed, ZERO provider traffic) · the strict scope
pre-flight · the four provider-failure taxonomy codes · the /policies
fail-closed gate (honest `policy-denied` data failures + RECORDED
publish refusals) · dead-binding and lazy-expiry refusals · cross-client
isolation · the unknown-platform refusal · the direct DB fences.

**Conformance preconditions on the adapter under test** (documented in
the suite header): declare the `account` family; the capability
`requiredScopes` must be satisfiable by the full-scope fixture grant
`['account:read','content:read','analytics:read','content:write']` (the
read-only fixture `['account:read','content:read']` drives the
insufficient-scope battery); operations follow the port contract
(failures as data, never thrown).

**This delivery's proof:** the FULL reference platform (all five
families) AND the READ-ONLY partial platform (account + content-read
only) both pass the suite — a capability-subset adapter is first-class.
Plus the direct module-level battery: provider-failed / restricted /
insufficient-scope-refused publish attempts record their honest
codes/signals on the ledger; refused keys burn honestly (a same-key
retry returns the recorded refusal as a duplicate — the caller
resubmits under a NEW key); the fence is per-account; the synchronous
publisher (submit-only, no status op) is a valid declared subset.

## 8. Honest limitations and disclosures

1. **Contract-level only — no live provider calls.** No concrete
   platform adapter ships (that is exactly MKT-057..061). The conformance
   suite runs against the disclosed in-memory reference double at the
   provider boundary; the contract HOST under test (gates, fence,
   ledger) is fully real.
2. **The X-platform fence limitation.** The platform-knowledge fence
   scans the distinctive identifiers (`twitter`, `x.com`, `api.x.com`)
   because the X platform's key is the single letter `x` — unscannable
   as a substring. The arch-check EXTERNAL_PACKAGE_IN_SRC rule covers
   the SDK-import half everywhere.
3. **Pre-flight-refused publish keys burn.** A submit refused
   pre-flight (unsupported-capability / insufficient-scope /
   policy-denied / auth-expired) is RECORDED as a failed attempt and the
   idempotency key answers the recorded refusal on replay — the same key
   can never become a different operation. A caller who fixes the
   underlying state resubmits under a NEW key. This is a deliberate
   honesty choice (the fence must be total), proven by the
   key-burning test.
4. **Interrupted submits stay `submitted` (UNKNOWN).** A
   contract-violating adapter that throws (or a process crash between
   the claim and the fill) leaves the honest unresolved state; the
   replay surfaces a ConflictError. There is no automated
   reconciliation/sweep worker — that is future Work Item territory
   (the MKT-065 distribution planner or a later worker); the state
   contract is in place for it.
5. **Policy denials are DATA, not thrown PolicyDeniedError** (a
   deliberate deviation from the `/integrations` executeRead precedent,
   following the notification-delivery honest-refusal precedent): the
   consumer of this surface is the future server-side orchestration
   (MKT-065) which must ROUTE on failure kinds (retry vs reauthorize vs
   replan); the closed taxonomy is the routing surface. The decision
   itself is still recorded in the policy engine's own ledger.
6. **The rate-limit observation is per-outcome only.** The connection
   row's rate-limit state is `/integrations`-owned (consumed READ-ONLY
   from here); social operations cannot update it. Observations ride
   the operation outcomes and the publish-ledger rows.
7. **The vault-label slugification fix** (`sa/<platform>/<grant>` labels
   now slugify the platform id's dashes): a latent MKT-055 bug for
   dash-carrying integration adapter keys (e.g. `facebook-pages`) —
   surfaced by the conformance suite's reference platform key; the fix
   is in the module commit with a comment, and the existing
   social-accounts integration suite (24/24) confirms no regression.
8. **The conformance suite's fixture grants are fixed vocabularies**
   (`account:read`/`content:read`/`analytics:read`/`content:write`).
   A future platform whose required scopes fall outside them supplies
   its own fixture grants — the suite's precondition is documented;
   extending the fixture vocabulary is a test-only change.
9. **Capability tags recorded by MKT-055 are passthrough context** for
   the adapters (they ride the call context verbatim); their
   interpretation is deliberately NOT part of this contract (the
   declared capability matrix is the authoritative surface).
