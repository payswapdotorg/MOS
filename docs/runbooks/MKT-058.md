## 8. Honest limitations and disclosures

1. **The restriction-signals family is UNDECLARED — the honest
   subset.** The documented Instagram Graph API exposes no
   account-level restriction/eligibility-signal endpoint and no
   media-level restriction field comparable to YouTube's
   uploadStatus/rejectionReason/regionRestriction. Account-level
   limitations surface as invocation failures through the documented
   error semantics (the code-10 account-type block, permission
   errors, the request-limit classes) — carried as the frozen
   taxonomy DATA — and hidden moderation state is never invented
   (architecture-v1.6 §11). Consequence: the conformance suite fires
   16 of its 17 scenarios (the restriction-signal scenario is
   structurally skipped); the capability-subset scenario EXERCISES
   the undeclared family's fail-closed refusal end-to-end — the
   strongest capability-subset demonstration in the MVP adapter set.
   The container `status_code=ERROR` fact (the provider's own
   content-processing failure) IS observable — it rides the publish
   status answer as a restriction signal of the RESTRICTED publish
   outcome (not as a readRestrictionSignals capability).
2. **The publish step lives inside the status poll (FINISHED →
   media_publish).** The documented flow REQUIRES waiting for the
   container to finish processing before publishing; the host fence
   guarantees submitPublish is called at most once per (account,
   key), and container processing is genuinely async (Reels
   containers can process for minutes to hours per the
   developer-community reports). The mapping: submit = the container
   creation (born accepted); the FIRST FINISHED poll fires the
   documented second step (media_publish) and reports published with
   the media id; later polls observe PUBLISHED. A status-poll
   operation that performs the provider's own publish mutation at
   the documented FINISHED state is a disclosed judgment call — the
   alternatives (blocking the submit on unbounded polling, or
   leaving a permanently-accepted never-published attempt) are both
   less honest. Re-publishing is impossible: the adapter only issues
   media_publish for containers whose status is FINISHED (never
   PUBLISHED), and the double models the documented creation_id
   idempotency (an already-published container answers the same
   media id).
3. **The PUBLISHED container poll carries NO content identity.** The
   documented container status surface answers `{ id, status_code }`
   (plus the status text) — no media id. The publish-time answer
   (the FINISHED branch) carries the media id; the host ledger and
   the observation history record it; a LATER poll's observation
   honestly reports providerContentId null (disclosed, asserted in
   the lifecycle battery).
4. **Successful calls report rateLimit: null** — the documented
   X-App-Usage / X-Business-Use-Case-Usage headers expose
   call-count/CPU/time percentages (not integers), which do not map
   onto the normalized observation shape's fields. The double
   verifiably sends the documented headers; the adapter verifiably
   reports the honest null (the integration battery asserts both
   sides). The recoverable backoff seconds
   (estimated_time_to_regain_call_capacity) DO map and ride the
   rate-limited failure observations. Fabricating integers would be
   dishonest; this is the documented surface.
5. **The exact 24h-cap and hashtag-window error envelopes are
   community-observed, not documented verbatim.** The documented
   guides guarantee the limits (quota_total 50 / quota_duration
   86400; 30 unique hashtags / 7 days) and that violation errors;
   the exact envelope text is not in the docs. The doubles model the
   documented REQUEST-LIMIT class (envelope code 4) with
   limit-descriptive messages; the ADAPTER classifies by the code
   class, so any code-4 envelope maps to rate-limited regardless of
   the text (disclosed; robust either way).
6. **An unknown content id is an honest restricted failure, not a
   null record** (the inverse of the YouTube precedent's empty-list
   answer): the documented Graph API node-read surface has NO
   empty-list semantics — GET /{unknown-id} answers the code-100
