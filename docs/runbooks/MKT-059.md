## 8. Honest limitations and disclosures

1. **The restriction-signals family is UNDECLARED — the honest
   subset** (the MKT-058 precedent). The documented Facebook Pages
   surface exposes no account-level or post-level
   restriction/eligibility-signal endpoint or field. Account-level
   limitations (the zero-page account-type answer, the Page-role/task
   refusals, the permission classes, the documented rate-limit classes)
   surface as invocation failures through the documented error
   semantics — carried as the frozen taxonomy DATA — and hidden
   moderation state is never invented (architecture-v1.6 §11).
   Consequence: the conformance suite fires 16 of its 17 scenarios (the
   restriction-signal scenario is structurally skipped); the
   capability-subset scenario EXERCISES the undeclared family's
   fail-closed refusal end-to-end.
2. **The page-token resolution doubles the provider calls of every
   operation.** The documented token model ("To interact with the Pages
   API, a Page access token is required... The app uses the [user]
   token to request a Page access token") is honored literally: every
   operation first resolves the PAGE ACCESS TOKEN through the
   documented `GET /me/accounts` surface with the USER token, then
   issues the documented Page-scope call with the PAGE token. This is
   the faithful reading of the documented model (the /me/accounts edge
   also answers each call's page-role tasks verbatim); it costs one
   additional documented call per operation and consumes no BUC budget
   (the user-token resolution call is not a Page-token call per the
   documented accounting "Pages API using a Page access token... are
   counted").
3. **The discovery surface is Page-feed-scoped ONLY — the caller query
   is honestly unused.** The documented Page feed edge carries NO query
   parameter; no general keyword/hashtag content search exists on the
   documented Pages surface (the Graph API /search?type=page surface is
   no longer part of the current documented Pages API, and the Page
   Public Content Access feature is an app-review-gated feature, not a
   scope-gated discovery surface). discoverPublicContent passes the
   documented feed edge through VERBATIM (the Page's own posts + the
   visitor/user posts + the tagged public posts); the interpretation of
   which records are "discovery-worthy" is MKT-062's job. The unused
   query rides the passthrough data of the in-memory double only.
4. **Successful calls report rateLimit: null** — the documented
   X-App-Usage / X-Business-Use-Case-Usage headers expose
   call-count/CPU/time percentages (not integers), which do not map
   onto the normalized observation shape's fields. The double
   verifiably sends the documented headers; the adapter verifiably
   reports the honest null (the integration battery asserts both
   sides). The recoverable backoff seconds
   (estimated_time_to_regain_call_capacity / _access) DO map and ride
   the rate-limited failure observations. Fabricating integers would be
   dishonest; this is the documented surface.
5. **The like-count fact is the documented reactions summary total**
   (the `reactions.summary(true)` field expansion). The Post node's
   reactions total spans ALL reaction types (like, love, care...);
   the documented surface exposes no like-only count on the node
   (like-only counts exist as the post_reactions_like_total INSIGHTS
   metric, which the analytics-read family requests VERBATIM). The
   reactions-total-as-likeCount mapping is DISCLOSED here and in the
   adapter's file header.

   surface — the born 'published' submission.** This differs from the
   YouTube/Instagram born-'accepted' convention (their documented
   surfaces are genuinely async). The honest reading of the frozen
   contract ("published — the content is live") applies: the post IS
   live when the POST answers. The SCHEDULED and VIDEO paths carry the
