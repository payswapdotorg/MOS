## 1. What this delivery is

Two modules, one Work Item:

### 1.1 `/research` — the Web Research authority (§7)

- **The AGENCY-SCOPED research-session records** carrying the declared
  research topic, focus question and SOURCES as IMMUTABLE versioned
  declarations (corrections are NEW version records, never in-place
  rewrites; CAS row-locked; the session-record mutation guard keeps
  identity/scope immutable, the CAS version advancing by exactly one and
  the version pointer only ever advancing). The eight frozen source
  kinds map the §7 source list one-to-one: web_page, documentation,
  research_paper, news, market_source, public_social_content (public)
  plus connected_repository, connected_workspace (AUTHORIZED — §7:
  "connected repositories/workspaces when explicitly authorized", each
  carrying a canonical `connected` integration-connection reference of
  the same agency, read through the frozen per-kind normalized operation
  labels `repository.read` / `workspace.read`, which await their
  adapters — an honest read_error until one exists).
- **The DETERMINISTIC RESEARCH PIPELINE** (`runResearch`): fetch/extract
  over public URLs behind the replaceable GET-only page-reader port
  (the first-party `ResearchHttpPageReader` over the platform
  HttpCallPort, honest about what it can and cannot parse; fetch
  http/transport failures and empty pages fail closed into honest
  per-source outcome records — never invented success) plus authorized
  reads through the /integrations public contract READ-ONLY (the
  structural port exposes getConnection + executeRead ONLY —
  executeMutation is structurally absent, so NO mutation can be
  expressed toward any research source).
- **Every material source fact retains FULL provenance** (§7 verbatim):
  source reference, fetched-at, extractor identity
  ('research-html-extract-v1' / 'research-integration-read-v1'), the
  sha256 content hash of the material the fact was extracted from, the
  extraction notes and the bounded verbatim content — extracted
  observations, never conclusions. Source facts live in the module's
  OWN migration-056 tables; **/evidence stays the sole evidence
  authority** (the ONE /evidence import is the shared §21 material-key
  guard `containsMaterialKey` in the module's store — the
  /product-intelligence precedent).
- **The append-only RESEARCH INSIGHT records** (the §7 model-output
  discipline): every AI-assisted derivation carries the /ai-runtime
  model-identity disclosure (a registry-resolvable model identity + call
  reference, validated through the model-identity port; the display
  label snapshotted at record time), and the verification state is
  computed SERVER-SIDE from the record's own evidence set (≥1 cited
  same-session source fact → evidence_backed; none → unverified) — a
  derived record without backing evidence can never be presented as
  established. Supersession is the correction path (same session, same
  derivation kind, single-supersession fence); the migration-056
  DEFERRABLE verification invariant is the commit-time backstop that
  makes the rule unfalsifiable even against direct SQL.
- **The read surface** `/content-intelligence` consumes now (by
  reference, through this public contract only) and
  `/product-intelligence` consumes later.

### 1.2 `/content-intelligence` — the Content Intelligence authority (§6)

- **The OBSERVATION INGESTION pipeline** (`runObservationIngestion`):
  platform observations are read through the /integrations public
  contract READ-ONLY (the structural port — getConnection + executeRead
  only) using the frozen per-observation-kind normalized operation
  labels (`platform_analytics → 'runReport'` — the EXISTING
  generic-analytics adapter label; `platform_content → 'content.list'`
  — awaits its adapter, recording the honest failed outcome until one
  exists), and EVERY normalized provider record is appended as ONE
  canonical `/evidence` 'observation' record through the /evidence
  public contract (`appendEvidence`) — **/evidence stays the SOLE
  evidence authority**; this module retains no shadow observation
  ledger. The ingestion run row records the honest outcome
  (completed | refused | failed, records observed, evidence appended,
  the appended evidence ids, detail).
- **The CLIENT-SCOPED append-only CANDIDATE records** (migration 057):
  the §6 observed-feature set as DATA — topic/entity, niche/sub-niche,
  content format, length (value + unit, both-or-neither), hook features
  (bounded multi-select), narrative structure, publishing time, observed
  performance, performance velocity, engagement, audience-fit signal,
  freshness, novelty, reuse/duplication risk — closed vocabularies
  exactly where the house pattern uses them (CHECK-fenced in the
  migration, mirrored in the module guards), FK-anchored same-Client
  /evidence observation links (≥1 required: the candidate cites the
  normalized observation its features were observed from) and optional
  FK-anchored /metric observation references as the observed-performance
  anchor (validated through the /metrics public contract READ-ONLY). A
  new observation is a NEW candidate — never an in-place rewrite.
- **The append-only HYPOTHESIS records with HONEST FRAMING**: §6's
  explicit non-claim ships on EVERY hypothesis view as the
  CONTENT_INTELLIGENCE_HYPOTHESIS_FRAMING constant ("observed
  competitor/platform performance does not by itself establish causality
  for this account — this record is an input to experiments, never a
  conclusion"). Hypotheses REQUIRE ≥1 same-client evidence reference
  (evidence/hypothesis separation), may cite same-client CANDIDATE
  records, same-AGENCY /research insight citations (validated through
  the /research public contract READ-ONLY — the AI-discipline
  disclosures ride the cited research records themselves, since this
  module's frozen row lists NO /ai-runtime dependency) and an optional
  /experiments reference (validated READ-ONLY through the /experiments
  public contract — NO experiment is created or transitioned here).
  Corrections ride the single-supersession chain (same client, same
  hypothesis kind).
- **The DETERMINISTIC niche clustering + candidate ranking** (the
  MKT-062 acceptance): pure functions with frozen calculation versions —
  `clusterContentCandidatesByNiche` ('ci-cluster-v1': groups by (niche,
  sub-niche) with per-cluster format/narrative histograms and the
  deduplicated sorted hook features) and `rankContentCandidates`
  ('ci-rank-v1': the DISCLOSED frozen weight vector over the
  closed-vocab observed features — audience fit, freshness, novelty,
  reuse risk — with a deterministic candidate-id tiebreak). Same inputs
  always produce the same outputs; the ranked order is a RECOMMENDATION
  as data toward planners — never a mutation, never an outcome claim.

### 1.3 What it is NOT (the bounded scope)

- NO second evidence authority (observations become canonical /evidence
  records; links are FK-anchored with same-Client trigger backstops).
- NO mutation toward any research source or platform (structural ports
  only; the page-reader request contract has no method field at all).
- NO experiment verb anywhere (hypotheses are INPUTS to /experiments; at
  most a READ-ONLY-validated reference).
- NO /ai-runtime consumption in /content-intelligence (the frozen row
  lists none — AI-derived research claims arrive as /research insight
  citations).
- NO mission/planner logic: candidates and hypotheses are attachable BY
  REFERENCE through the read surface (MKT-070+ compose them later).

```text

POST /api/research-sessions/:researchSessionId/insights            record one insight claim
POST /api/clients/:clientId/content-intelligence/ingestion-runs    run the observation ingestion (owner|admin)
GET  /api/clients/:clientId/content-intelligence/ingestion-runs    the ingestion-run tail
POST /api/clients/:clientId/content-intelligence/candidates        record one candidate (owner|admin)
GET  /api/clients/:clientId/content-intelligence/candidates        the candidate tail
POST /api/clients/:clientId/content-intelligence/hypotheses        record one hypothesis (owner|admin)
GET  /api/clients/:clientId/content-intelligence/hypotheses        the hypothesis tail
GET  /api/content-candidates/:contentCandidateId                   one candidate + links (uuid-grammar-guarded)
GET  /api/content-hypotheses/:contentHypothesisId                  one hypothesis + the §6 framing
```

Fail-closed battery: uniform 404 for foreign/unknown/malformed
identifiers (no existence oracle); a suspended membership is the 403;
anonymous calls fail closed 401 at the authenticator; provenance is
SERVER-DERIVED (the DTOs reject every provenance-shaped key; the
insight verificationState is a rejected authority field —
SERVER-COMPUTED only).
