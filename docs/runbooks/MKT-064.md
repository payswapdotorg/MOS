## 1. Contract summary

### 1.1 What this module IS

The **content asset and transformation authority** behind the immutable
versioned artifact records and the first-party/extension transformation
execution contracts:

| Surface | Contract |
| --- | --- |
| `content_assets` (migration 053) | The CLIENT-SCOPED **logical asset identities** the version records hang off (the version-sequence fence: one monotonic per-asset version column — explicit versions only, no floating pointers). |
| `content_asset_versions` | The **IMMUTABLE VERSIONED ARTIFACT RECORDS**: the opaque content-asset REF minted `ca:` + canonical version id (globally unique — the OTHER side of the MKT-063 seam, now complete), media/kind metadata, the CONTENT-ADDRESSED object-storage reference (the MKT-001 ObjectStore key — sha256 hex, set exactly for materialized/derived versions, NULL for drafts), the `/evidence`-anchored SOURCE PROVENANCE (required for source versions; a derived version's provenance IS the recorded transformation — the provenance-shape CHECK), the CHECK-fenced lifecycle (`draft` → `materialized`; `derived` is the BIRTH state of transformation outputs), the disciplined state-move trigger (the ONLY sanctioned UPDATE; no-DELETE). |
| `content_asset_lifecycle_events` | The fully **append-only lifecycle tail** (registration/materialization/derivation, the CHECK-frozen event shapes). |
| `content_asset_quality_observations` | The append-only **QUALITY OBSERVATIONS**: measurable facts only (duration, dimensions, bitrate, caption coverage, language, fps, sample rate, byte size — the closed ca-vocab-v1 metric vocabulary; a fabricated "score" cannot even be expressed). |
| `content_transformations` | The **RECORDED TRANSFORMATION REQUESTS**: the kind (the frozen family — the MKT-064 acceptance list VERBATIM), the per-kind parameters + output spec (bounded jsonb), the resolved ENGINE identity (frozen at request), the `/executions` FK reference (UNIQUE — one transformation per execution), the output version link set ONCE at completion (the requested → completed/failed terminal moves only). |
| `content_transformation_ingredients` | The **IMMUTABLE ingredient lineage links**: one row per (transformation, input version), the input ref FROZEN at request time, the position order, same-Client trigger-fenced. |
| `TransformationEngine` port | **The capability seam** (first-party engines or Extension/App engines as module DATA — the registry is EMPTY in production by default; a kind with no registered engine fails closed at request time — the MKT-056 discipline). |
| `requestTransformation` + `executeTransformation` | The transformation execution contract flowing **through the EXISTING `/executions` authority** (createExecution with the external-request link + transitionExecution for every lifecycle step — NO second engine, the MKT-054 cardinal rule). |

### 1.2 The frozen vocabularies (ca-vocab-v1)

- The **transformation kind family** — the MKT-064 acceptance list
  VERBATIM: `crop | reframe | padding | compilation | clip | caption |
  voice | translation | format`. The richer architecture-v1.6.md §10
  catalogue (aspect-ratio adaptation, sequencing, audio cleanup,
  background treatment, scene selection, thumbnail generation, metadata
  rewriting, compression optimization) maps onto these nine frozen
  kinds as engine-declared effects/parameters — the FAMILY is the
  frozen authority, the catalogue is its documentation (disclosed
  semantics decision).
- The **media kinds**: `video | audio | image | text | document`.
- The **lifecycle states**: `draft | materialized | derived` with
  EXACTLY ONE legal same-version move, `draft → materialized`
  (`derived` is the BIRTH state of transformation outputs — an existing
  version can never be mutated into an output; outputs are NEW
  versions, immutable at birth — the pure `isLegalContentAssetLifecycleMove`
  is the module twin of the migration-053 disciplined trigger).
- The **lifecycle event kinds**: `registration | materialization |
  derivation` (CHECK-frozen shapes: registration = draft birth,
  derivation = derived birth, materialization = the single move).
- The **transformation statuses**: `requested | completed | failed`
  (terminal moves only; a retry is a NEW transformation — the §6
  no-second-identity discipline).
- The **quality metrics** (closed): `duration_ms | width_px | height_px
  | bitrate_kbps | caption_coverage_ratio | language | fps |
  sample_rate_hz | byte_size` — the observation discipline: 'language'
  carries a bounded BCP-47-shaped text tag; every other metric a
  non-negative finite number; the coverage ratio bounded to [0, 1].

### 1.3 The module API (src/modules/content-assets/public.ts)

- **`registerAssetVersion`** — registers one immutable version record:
  `assetId: null` creates a NEW logical asset (version 1); a known
  asset id creates the NEXT explicit version (the (asset, version)
  DB fence; a correction is a NEW version = a NEW ref — the 063
  re-registration discipline). Born `draft`. Source versions REQUIRE
  the `/evidence`-anchored source provenance.
- **`materializeAssetVersion`** — THE MATERIALIZATION MOVE: stores the
  bytes through the content-addressed ObjectStore port, records the
  single sanctioned state move + its event in ONE transaction (CAS —
  the losing side of a race is the honest ConflictError; a
  materialized/derived version never re-materializes).
- **`recordQualityObservation`** — appends ONE immutable measured fact
  (the closed vocabulary; a re-measurement is a NEW row).
- **`requestTransformation`** — validates (kind, bounded parameters/
  output spec, EXPLICIT ingredient versions — a floating 'latest'
  pointer is rejected by the pure guard BEFORE any write), resolves the
  engine from the registry (declared engineId, else the first
  supporting kind; none → fail-closed ConflictError), creates the
  EXECUTION through the `/executions` public contract (external-request
  link `content-transformation:<id>`, the engine's declared execution
  kind, pooled-worker runtime class, deterministic §8 idempotency key),
  and records the transformation row (born `requested`) + the immutable
  ingredient links (versions and refs FROZEN at request time). Draft
  ingredients are rejected (an engine cannot read bytes that do not
  exist). **RIGHTS ARE NEVER CHECKED HERE** (boundary rule 5).
- **`executeTransformation`** — the module-side runner: drives the
  execution `created → queued → starting → running` through the
  `/executions` public contract, fetches the ingredient bytes through
  the ObjectStore port, runs the frozen engine choice, stores the
  output bytes (content-addressed, idempotent), records the
  `/content-rights` ingredient lineage links (composite ref → each
  ingredient ref — the 063 conjunction seam; idempotent by convergence
  on replay), completes the transformation in ONE transaction (the
  output asset + version born `derived` WITH its object, the derivation
  event, the engine's measured observations + the module's byte_size
  observation, the requested → completed move with the output link set
  ONCE), and transitions the execution `running → succeeded`. On
  failure: the execution transitions `running → failed` (SAFE
  classification — the module's writes are post-engine and
  transactional) and the transformation record moves `requested →
  failed` with the bounded reason. A COMPLETED transformation converges
  on replay (replayed=true); a FAILED one is settled — a retry is a NEW
  request.
- **Reads:** `getAssetVersion`, `resolveAssetRef` (the seam
  resolution), `resolveContentAssetsOwnership` (the route-layer
  uniform-404 input), `listAssetVersionsForClient`,
  `listVersionsOfAsset`, `listLifecycleEvents`,
  `listQualityObservations`, `getTransformation`,
  `listTransformationsForClient`, `listTransformationIngredients`.
- **Pure core (exported for tests + future callers):**
  `mintContentAssetRef`/`parseContentAssetRef` (the seam grammar),
  `isLegalContentAssetLifecycleMove`, `resolveTransformationEngine`,
  the full guard set.
- **The 063 seam satisfaction:** `createContentAssetReferencePort(api)`
  — the factory constructing the `ContentAssetReferencePort` the 063
  public contract declared (this module owns the real records those
  refs resolve to).

### 1.5 Boundaries (what this module deliberately does NOT do)

- **NO rights authority** (boundary rule 5): the module's ONLY
  `/content-rights` interaction is `recordLineageLink` during
  transformation completion — pure derivation bookkeeping (never a
  rights-state write, never a gate evaluation, never a permission
  write). An asset whose ingredients are rights-blocked can still be
  TRANSFORMED here but can never pass the 063 publication gate (the
  conjunction resolves through exactly the links this module records —
  proven by the integration AC-4 battery).
- **NO second execution engine** (the MKT-054 cardinal rule + lock
  rule 24): the module interacts with `/executions` exactly through
  `createExecution` / `transitionExecution` / `getExecution`; no
  execution table is written by the module; no worker host, dispatch
  loop or runtime identity of its own exists.
- **NO hardcoded provider list** (architecture-v1.6.md §10): engines
  are registered module DATA; the production composition registers
  NONE by default (the MKT-056 discipline) — a kind with no registered
  engine fails closed at request time (proven over real HTTP against
  the spawned EMPTY registry).
- **NO object-store implementation of its own**: the MKT-001
  ObjectStore port is consumed (fs impl retained for tests, memory for
  unit doubles, S3-class wired at the composition root).
- **NO evidence-module import**: `/evidence` is NOT a frozen allowance
  of this row — the source-provenance anchor rides as the id-based
  reference seam (the FK + same-Client migration-053 triggers are the
  DB backstop; the ROUTE layer resolves evidence canonically first —
  uniform NotFoundError for unknown/foreign; the `/app-metering`
  precedent), and the module surface surfaces the DB backstop's
  rejection as the same honest NotFoundError for module-level callers.

## 3. The transformation execution contract (the MKT-064 heart)

`requestTransformation` → `{ transformation (born 'requested'),
executionId, ingredients (frozen) }`, then `executeTransformation` →
`{ transformation (completed), executionId, output (born 'derived'),
replayed }`:

1. **REQUEST TIME**: the pure guards reject malformed shapes (unknown
   kind, unbounded payloads, the floating-version rejection, duplicate
   or over-bound ingredients) BEFORE any write; the engine resolves
   from the registry (fail-closed when unserved); the ingredient
   versions resolve EXPLICITLY (asset id + version number — uniform 404
   for unknown/foreign, ConflictError for drafts with no object); the
   output spec's `mediaKind` + `displayName` are validated; the
   EXECUTION is created through `/executions` (the §8 idempotency key
   deterministic from the pre-minted transformation id — an insert
   failure after a successful execution creation leaves a bounded,
   self-describing orphan: a `created` execution whose
   external-request ref names the transformation that never recorded —
   disclosed); the transformation row + ingredient links are recorded
   in ONE transaction.
2. **RUN TIME** (the module-side runner — the only "worker" this
   module has, invoked explicitly, no background loop): the execution
   walks `created → queued → starting → running` through the public
   transition API (each step with a deterministic idempotency key — a
   crash replay converges on the executions §8 ledger); the ingredient
   bytes are fetched through the ObjectStore port (engines stay PURE
   byte transformers — no store access of their own); the frozen
   engine choice runs; the output bytes are stored content-addressed;
   the `/content-rights` lineage links are recorded (composite ref →
   each ingredient ref; duplicate pairs converge — the same immutable
   fact); the completion transaction writes the output asset identity,
   the output version (born `derived`, object set at birth, NO
   evidence anchor — the transformation IS the provenance), the
   derivation event, the engine's measured observations + the module's
   `byte_size` observation, and the `requested → completed` move with
   the output link set ONCE; finally the execution transitions
   `running → succeeded`.
3. **FAILURE**: any error after `running` transitions the execution
   `running → failed` (SAFE classification — the module's writes are
   post-engine and transactional; a real engine with side effects of
   its own declares its own classification through its execution-kind
   choice — disclosed) and the transformation record settles
   `requested → failed` with the bounded reason. The failure-recording
   itself is best-effort (the ORIGINAL error stays the surfaced truth;
   a record left `requested` by a failed failure-recording is
   reconciled by a later `executeTransformation` replay — disclosed).
4. **REPLAY**: a completed transformation converges (replayed=true,
   the recorded outcome — no re-run, no new writes); a failed one is
   terminal (a retry is a NEW transformation request — the §6
   no-second-identity discipline).

**The engine registry (module DATA — the capability seam):**
`AppOptions.contentTransformationEngines` (the socialAccountFlows
composition precedent) — EMPTY by default in production (the MKT-056
discipline; the boundary battery proves the production composition
root registers NO double and the spawned-API HTTP battery proves the
fail-closed 409). Integration tests supply the disclosed doubles
through the seam.

**Rights NEVER gate transformation and transformation NEVER mutates
rights** (boundary rule 5, both directions): the module holds no gate
call, no rights-table write, no permission write — proven by the
boundary battery (#4) and the integration AC-4 (a rights-BLOCKED
ingredient transforms successfully; the derived composite can never
pass the 063 gate — blocked through the conjunction on exactly the
lineage links this module recorded).

## 5. Honest disclosures & known limitations

1. **No real media processing ships in this program** (the dispatch's
   honest-limitations requirement): the concrete first-party engines
   are DISCLOSED DOUBLES behind the REAL port contract —
   - `first-party:passthrough` (all nine kinds): a TRUE no-op — the
     single ingredient's bytes are the output verbatim (content
     addressed, so the output converges to the same object key);
     rejects multi-ingredient requests (the declared constraint);
   - `first-party:format-double` ('format'): a deterministic SYNTHETIC
     container — a bounded text header carrying the declared
     `target_format` + the source bytes. NOT a transcoder;
   - `first-party:crop-double` ('crop'): a deterministic SYNTHETIC
     crop frame — a bounded header encoding the declared rectangle
     (x, y, width, height) + the source bytes. NOT a pixel processor;
   - the integration suite adds its own `test:compilation-concat`
     double (byte concatenation) through the same public seam — the
     pluggability proof.
   Real first-party media-processing capabilities, AI-backed engines
   (execution kind `ai`) and Extension/App engine bridges arrive as
   future registered engines through the same port (lock rule 24:
   replaceable, never an alternate authority). The nine KINDS all ship
   as contract + doubles only.
2. **The engine registry is in-process module DATA**: engines cannot
   cross process boundaries, so the spawned HTTP API process (the
   production composition) carries the EMPTY registry — the HTTP-level
   transformation surface fails closed (409 no-engine) until real
   engines are wired; the full golden path is exercised module-level
   against the SAME real database/stack through the in-process
   application composed with the doubles (the notification-delivery
   precedent — disclosed as the current honest posture).
3. **The lifecycle semantics decision** (the dispatch chain
   "draft → materialized → derived", frozen here): `draft →
   materialized` is the single sanctioned same-version state move;
   `derived` is the BIRTH state of transformation outputs (born WITH
   their objects and their lineage — an existing version can never be
   mutated into an output; outputs are NEW versions). A derived
   version carries NO `/evidence` anchor (the provenance-shape CHECK):
   the recorded transformation IS its provenance — the derivation can
   never be quietly substituted by a claim.
4. **The execution-creation ordering**: the execution is created BEFORE
   the transformation row is inserted (the executions authority needs
   the pre-minted transformation id for the deterministic §8
   idempotency key + external-request link). On a row-insert failure
   the execution stays orphaned `created` — bounded harm (a runtime
   attempt that never runs; the executions authority tolerates that;
   the external-request ref makes the orphan self-describing).
5. **The module's runner is synchronous-in-band**: `executeTransformation`
   runs the engine inside the request/module call (no background
   worker plane — deliberately: no second engine, no dispatch loop).
   Long-running real engines will need the future async work pattern
   (execution transitions exist for it; the module-side runner is the
   honest synchronous contract for this program — disclosed).
6. **Cross-authority atomicity**: the module's OWN writes are
   transactional (the registration, the materialization, the
   completion); the composed authorities' writes (the execution
   transitions, the object-store puts, the rights lineage links) ride
   outside that transaction with their own idempotence/convergence —
   a partially-completed transformation is reconciled by replay
   (executeTransformation is idempotent-by-convergence) and a partial
   rights-link recording converges (duplicate pairs are the same
   immutable fact). The standard modular-monolith posture (063 itself
   ran the policy decision outside its transaction).
7. **The failure classification** on engine errors is `safe` (the
   module's writes are post-engine and transactional). A REAL engine
   with external side effects of its own must declare its own
   classification through its execution-kind choice / future contract
   extension — the doubles never side-effect.
8. **Shared files touched (the parallel-wave disclosure):** Workers A
   (MKT-057, /social-accounts subtree — no new module) and C (MKT-054,
   /growth-operator + migration 052-after-renumber) are in flight on
   the same base. This delivery touched: `spec/architecture.md` (§6
   line + sentence), `spec/module-dependency-matrix.md` (the new row +
   bullet + the 063 row completion + the 063 bullet's disclosure
