### 1.2 The fan-out execution (fail-closed PER DESTINATION, in §5 chain order)

Per destination, in fan-out order — one destination's outcome NEVER
blocks the others:

1. **THE 063 RIGHTS GATE FIRST** (`contentRights.evaluatePublicationGate`
   — the sole rights authority, COMPOSED never duplicated): only `allow`
   permits an autonomous publish; `review_required` → the destination is
   recorded `rights_review_required` (the blocked_pending_human_action
   surface — rights uncertainty routes to human action) and `blocked` →
   `rights_blocked` (including `no_rights_record`: a platform connection
   NEVER implies rights to redistribute content that originated
   elsewhere — an absent evaluation is blocked). NO attempt is made;
   zero provider traffic. The verdicts WITH reasons are recorded on the
   lineage tail, never re-evaluated.
2. **PER-PLATFORM CAPABILITY VALIDATION** (lock rules 19/29 — parity is
   never assumed): the destination account's REAL capabilities through
   `socialAccounts.resolveAccountCapabilityMatrix` (the declared adapter
   capability subset, the usable authorization, the per-family scope
   satisfaction against the CURRENT grant's VERBATIM scopes) plus the
   /integrations adapter registry (`listRegisteredAdapters` — the 056
   normalized adapter contract's platform pipe). Any failure
   (`platform_adapter_unregistered`, `authorization_unusable`,
   `publish_capability_undeclared`, `publish_operation_undeclared`,
   `publish_scope_unsatisfied`, `integration_adapter_unregistered`) →
   the destination is recorded `capability_rejected` WITH the rejection
   codes — never attempted blind.
3. **THE DISPATCH POLICY GATE** (`policies.evaluateAction` — the network
   dimension, operation `content.distribution.dispatch`, resource the
   destination platform): only an explicit allow permits; deny AND
   unknown both BLOCK (the decision rides the policy engine's own
   append-only ledger; the id is recorded on the lineage tail). This is
   the module's /policies consumption — the operator can pause
   distribution to a platform without touching rights. It composes the
   063 gate's own destination policy (a DIFFERENT key with a different
   purpose: `content.rights.publication.<platform>` inside the rights
   authority); BOTH must allow (lock rule 29).
4. **THE PUBLICATION ATTEMPT** (`socialAccounts.submitPublish` — the 056
   idempotency ledger, the ONLY physical publish path): the derived
   deterministic key + the destination-specific request. The outcome is
   the 056 ledger's own record, linked through the per-destination
   publication row and recorded verbatim on the lineage tail.
   `'submitted'` (interrupted) stays the honest UNKNOWN: the destination
   is `publishing` — pending reconciliation, never blindly replayed
   under the same key.

**Idempotency model:** a re-dispatch of a plan with recorded
publications REPLAYS from the 056 fence (`duplicate: true`, ZERO
provider calls — the same key never becomes a different operation; a
fresh publication of new content is a NEW plan) and re-evaluates
honestly for non-attempted destinations (the rights/capability/policy
state may have changed — e.g. a human clearance after
review_required). The plan lifecycle re-enters 'dispatching' and
completes 'dispatched'.

### 1.3 Boundaries (what this module deliberately does NOT do)

- **NO second execution engine**: the physical publish flows
  EXCLUSIVELY through the 056 adapter submitPublish contract; no
  provider HTTP client, no worker host, no dispatch loop, no runtime
  identity (the boundary tests prove the exact consumed surface set).
- **NO rights authority**: the 063 gate is composed, never duplicated —
  the module records verdicts, it never re-evaluates rights.
- **NO workflow/execution authority**: plans, attempts and outcomes are
  DATA toward the mission/operator layer (§13 composes this module; it
  never composes the operator).
- **NO policy authority**: /policies decisions ride the policy ledger;
  this module reads them and records their ids.
- **NO mission mutation**: the mission anchor is a read-only FK
  reference resolved through resolveGrowthMissionOwnership.
- **NO provider/platform knowledge**: platform ids are opaque adapter
  keys carried as data.
- **NO /ai-runtime dependency** (the frozen row lists none): fully
  deterministic.

## 4. Honest disclosures & known limitations

1. **The dispatch policy gate is a disclosed judgment call.** The frozen
   row lists /policies; the dispatch text says "You hold NO policy
   authority: /policies decisions ride the policy ledger; you read
   them." This delivery consumes /policies through `evaluateAction`
   (the network dimension, operation `content.distribution.dispatch`)
   as the per-destination DISPATCH gate — the same consumption posture
   as /social-accounts and /content-rights (fail-closed, decisions in
   the policy engine's own ledger, only allow permits). It does NOT
   duplicate the 063 gate's destination policy
   (`content.rights.publication.<platform>` — a different key inside a
   different authority): BOTH must allow (lock rule 29). An operator
   can therefore pause cross-platform distribution to a platform
   through policy alone. Disclosed as the reading of the row's
   /policies allowance.
2. **The re-dispatch convergence semantics.** A destination with a
   recorded publication replays from the 056 fence (duplicate: true)
   WITHOUT re-running the gates (the publication already happened — the
   recorded outcome stands; a same-key retry never becomes a different
   operation, the 056 fence discipline). A NEW publication of new
   content is a NEW plan. Non-attempted destinations (planned,
   gate/capability/policy-rejected) re-evaluate honestly on re-dispatch
   (the state may have changed — proven by the NAMED (e) human-clearance
   recovery). Disclosed as the idempotency model.
3. **The publication rows are the FIRST submit's immutable link.** The
   `duplicate` flag of a REPLAY rides the appended publication_attempt
   EVENTS (asserted in NAMED (c)); the link rows keep the submit-time
   facts (append-only, the live truth stays the 056 ledger).
4. **'publishing' is a reconciliation surface, not an engine.** A 056
   attempt left 'submitted' (interrupted) parks the destination at
   'publishing' — UNKNOWN, never blindly replayed. Reconciliation
   (polling the provider status) is the 056 surface's own
   (refreshPublishStatus); this module deliberately holds no polling
   loop (no worker plane). A future Work Item may compose a reconciler
   over the existing surfaces.
5. **Measurement references are opaque bounded strings** (recorded as
   data, never computed — attribution is distinct from causal
   inference). /evidence and /metrics are NOT allowances of this
   module's frozen row, so references do not resolve here; the
   mission/operator layer resolves them.
6. **The descriptor of the derived media assets omits the object
   digest** — the 056 §21 backstop's material-value hint matches raw
   64-char hex (a sha256 digest LOOKS like base64 material). The
   content-addressed digest stays in the 064 version record; the
   descriptor carries displayName/contentType/version only. Disclosed
   as an interop quirk of the two guards, not a semantic loss.

   sibling (YouTube adapter, based on the older 1ef58f8 baseline) and
   UX-002 (console/) run concurrently; the Tech Lead reconciles at
