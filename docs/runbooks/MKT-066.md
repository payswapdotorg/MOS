## 1. Contract summary

### 1.1 What this module IS

The **descriptive health evaluation authority**: it COMPOSES observable
provider/account records into per-account health verdicts — it never
invents, enforces or owns anything beyond them.

| Surface | Contract |
| --- | --- |

### 1.3 Baseline-relative anomaly detection ('ph-baseline-v1')

An anomaly is a deviation from the **account's OWN historical baseline**
— never an absolute threshold invented without one:

- the participating series are the frozen 'social.*'-namespace /metrics
  observations whose dimensions carry the account id under the
  `social_account_id` dimension key (the interop convention the social
  analytics normalizers write);
- a series flags only on a **SUSTAINED deviation**: the TWO most recent
  quality-passing observations BOTH under half the median of the
  account's own ≥3 prior observations (a single dip never flags;
  'suspect'-quality observations are excluded from the baseline — the
  /metrics data-quality posture);
- **cold-start** (fewer than 3 prior observations) produces the honest
  `insufficient_baseline` disclosure — no anomaly verdict is possible
  (an account with NO observable records at all produces the
  `no_observable_records` posture);
- the **cross-platform control comparison** (§11): same-name series of
  the client's accounts on OTHER platforms; an unflagged control
  sharpens the anomaly to medium confidence with the
  `cross_platform_control_divergence` reason; flagged controls keep the
  honest client-wide caveat ("a client-wide cause cannot be excluded");
- the **cadence rule** (the first-party automation signal): the most
  recent 24h publish-attempt count ≥ 3× the median daily count of the
  prior 6 days (median ≥ 1) — a WEAK signal by construction, always
  suspected_automation_risk at LOW confidence with the honest
  uncertainty.

### 1.4 Reason codes + confidence/uncertainty (the acceptance core)

Every verdict carries: its **closed-vocabulary reason codes** (21 codes,
ph-vocab-v1 — which observable records produced each constituent), a
**coarse confidence tier** derived deterministically from the evidence
(platform-confirmed records = high; sustained multi-record inference =
medium; thin/inferred-only or observability-gap verdicts = low — never a
probability invented from nothing), an **explicit uncertainty statement**
(baseline sizes and medians, control availability, the experiment
confounders, the unregistered-adapter observability gap), and its
**evidence basis** (the FK-anchored citation links + the structured
per-constituent basis entries: account/grant/connection records, publish
attempts, status polls, restriction signals, metric observations).

### 1.5 Compliant response recommendations (§11 as data)

The frozen maneuver vocabulary — §11 verbatim: change_content_mix,
change_publishing_frequency, pause_risky_strategy,
shift_to_another_connected_platform, adjust_transformations,
reduce_automation, request_human_interaction, platform_appeal_or_review,
preserve_goal_change_route — mapped deterministically per state (healthy
recommends nothing). The FORBIDDEN actions
(PLATFORM_HEALTH_FORBIDDEN_ACTIONS: anti_abuse_evasion, fake_engagement,
restriction_bypass, impersonation) are structurally absent from the
recommendation vocabulary and can never be emitted (lock rule 27; the
unit battery asserts no recommendation, description or rationale is or
suggests a forbidden action; the boundary tests pin the mapping table
contains exactly the frozen maneuvers).

### 1.6 What it is NOT (the bounded scope)

- NO hidden-moderation invention (lock rule 25): the evaluation input
  contract has NO signal/state/claim field — a provider notice with no
  observable record is STRUCTURALLY INEXPRESSIBLE as a verdict input.
- NO enforcement: the module describes; it never pauses, blocks or
  mutates an account, plan, mission or experiment (the MKT-070+
  planners, the Growth Operator platform-health seam and UX-007 decide).
- NO second authority: no account registry (055 sole), no publish ledger
  (056 sole), no metrics authority (/metrics sole), no evidence authority
  (/evidence sole), no experiment authority (/experiments sole).
- NO provider knowledge: platform identity is the account record's
  platform id carried as data; the rules never branch on a platform.
- NO /cross-platform-distribution dependency: the 065 distribution
  publications arrive as the per-account 056 publish-attempt records
  (the 056 idempotency ledger is the ONLY physical publish path — the
  065 module routes every destination publication through submitPublish,
  and its publication records anchor those attempt ids), so the

  the frozen row does not allow (disclosed; the row is the authority).

## 7. The MKT-065 HTTP dispatch-route defect fix (gated before MKT-075)

**The defect** (disclosed at the UX-004 station verification, reproduced
from main): `POST /api/clients/:clientId/cross-platform-distribution/
plans/:planId/dispatch` returned **422 "audit event rejected by the
append guard" AFTER the module had durably dispatched the plan** — the
route's audit emit passed the `outcomes` ARRAY in the audit details
(`outcomes: ctx.result.destinations.map((destination) =>
destination.destinationStatus)`) while the append guard
(audit-store's `assertValidAuditEvent`) requires scalar detail values
("audit details key 'outcomes' must be a JSON scalar"). The plan was
left dispatched despite the 422, and the repo's integration tests
dispatched through the module API, so the HTTP-route defect was never
exercised.

**The fix** (ONE expression changed in
src/api/cross-platform-distribution-routes.ts, disclosed line-by-line):
the outcomes array is serialized deterministically as the
**fan-out-ordered comma-joined status string** — the house serialization
precedent (notification-delivery's `receiptOutcomes` / field-agents'
`specializations` `join(',')`): position corresponds to fan-out order,
the string is lossless over the ordered outcome list, and the full
per-plan detail stays readable on the plan's own append-only lineage
tail. The `logger.info` structured-log line (which legitimately carries
the array — the logger is not audit-gated) is UNTOUCHED. Nothing else in
the route file changed; the module is NOT redesigned.

**The proof** (tests/integration/cross-platform-distribution-dispatch-route.test.ts
— the three NAMED route-level paths, dispatch through the HTTP route,
not the module API):

1. **happy** — the dispatch returns a truthful 200 (plan dispatched,
   both destinations published, publications recorded) and the audit row
   EXISTS with `details.outcomes = 'published,published'` (a JSON
   string — every detail value scalar);
2. **audit-failure truthfulness** — with the audit append forced to fail
   the way the house tests force such guards (a temporary DB rejection
   trigger on the audit trail for exactly this action+target), the
   response is a server error — NEVER a 200 that claims completion
   without its audit row — while the durable publication state stays
   truthful and readable (the GET route shows the dispatched plan with
   its publications; response and durable state cannot disagree about
   dispatch success); the retry after the trigger is removed converges
   (see 3);
3. **replay determinism** — re-dispatching through the route converges
   deterministically: the same publish-attempt ids replay from the 056
   fence with ZERO provider calls (asserted against the reference
   adapter's submit counter), the same destination outcomes, the plan
   lifecycle dispatched → dispatching → dispatched with an advanced
   version, and a FRESH audit row whose deterministic idempotency key
   carries the new plan version.

**HARNESS DISCLOSURE (the route-level battery):** the three tests run
against the REAL router + HTTP pipeline (buildApiRouter +
createHttpServer — the same route code the spawned entrypoint serves)
booted IN-PROCESS with the disclosed composition-seam adapters, because
the spawned production composition registers NO platform in BOTH the
integration-adapter registry (meta-ads, google-ads, generic-analytics,
crm, commerce-cms, creator-platform) and the social-adapter registry
(youtube, instagram, facebook-pages) on this base — the sets are
disjoint — so a full PUBLISHING dispatch through the spawned process is
not yet expressible on main (every destination would be
capability-rejected with `integration_adapter_unregistered`). This is an
honest environment limit of the current composition, not a test
shortcut: every route call is a real HTTP request through the real
pipeline (auth → owner → authorize → validate → execute → emit →
respond) against the real embedded-PostgreSQL state. The dispatch
response/dispatch-state truthfulness the fix proves is pipeline-level
and carries to the spawned topology unchanged.

## 9. Honest disclosures & known limitations

1. **The metric-series interop convention is frozen by this module but
   not yet populated by adapters**: the baseline calculation consumes
   /metrics observations of the frozen 'social.*' namespace carrying the
   account id under the `social_account_id` dimension key. The
   MKT-057..059 adapters' analytics reads are NOT yet normalized into
   /metrics by any composer (that is MKT-070+/075 work), so on this base
   the account series arrive only through the /metrics HTTP/module
   surface (exactly how the integration tests seed them). Until the
   normalizers exist, real accounts evaluate on their 055/056 records
   and the honest insufficient-baseline disclosure — the core's value
   does not depend on which adapters exist (the ACCEPTANCE CAVEAT).
2. **The status-poll composition is bounded**: the evaluation composes
   the status-poll history of the five most recent attempts carrying a
   provider publish reference (the newest three polls each) — the
   freshest provider state without unbounded fan-out. Older polls stay
   readable through the 056 surface; disclosed as the deliberate bound.
3. **The 065 publication-outcome surface**: the evaluator composes the
   per-account 056 publish-attempt records, NOT the 065 plan/destination
   rows (a /cross-platform-distribution import is not an allowance of
   the frozen row). Because the 056 ledger is the ONLY physical publish
   path, the account's attempt tail IS the complete observable
   publication-outcome surface (every 065 destination publication
   anchors a 056 attempt id on that account). If a future CR adds the
   direction, plan-scoped context (e.g. which mission drove an attempt)
   can enrich the basis — it cannot change the verdict inputs (§11's
   observable-records-only rule).
4. **The evaluation is a command, not a live view**: health is evaluated
   on demand and persisted append-only (the house research-run
   pattern). There is no background evaluator yet (a worker-plane
   scheduler is future work); consumers read the newest evaluation or
   run a fresh one through the POST route.
5. **The human_review_required triggers** are the two deterministic
   unresolvable-evidence cases: provider signals whose own labels say a
   review/appeal/pending process is underway, and conflicting
   authorization observations (the grant chain reads usable while the
   attempts record auth-expired failures). The state is NOT a general
   low-confidence escape hatch — suspected states carry their low
   confidence honestly instead (disclosed as the semantic choice).
6. **`bun run test:architecture` failed environmentally on this machine**
