## 1. What the module is

The discovery-mission RUNTIME for a Growth Mission of the frozen §3
`commerce_discovery` objective family. A discovery program rides the
mission spine (ONE program per mission, `commerce_discovery_missions`
FK-anchored to `growth_missions`) and owns exactly the
discovery-specific records:

- the versioned plan (`commerce_discovery_mission_versions`): the DECLARED
  bounded-spend budget fields + the deterministic cd-plan-v1 selection
  (niche ranking, candidate proposals as data, the demand-test design
  template, the composed economic gates) + the input snapshot/digest;
- the append-only history (`commerce_discovery_events`);
- the product/listing candidates
  (`commerce_discovery_candidates`) with FK-anchored provenance citations;
- the demand tests (`commerce_discovery_demand_tests`) — the experiment
  arm THROUGH the /experiments authority;
- the learning-loop outcomes (`commerce_discovery_outcomes`) — observed
  values DERIVED from the real MKT-071 commerce events;
- the economic-guardrail evaluations
  (`commerce_discovery_guardrail_evaluations`).

## 3. The guardrail design (the acceptance's core)

### The bounded-spend declarations (the MKT-054 budget convention)

Every version record carries, as DECLARED data (CHECK-fenced):

- `spend_currency` (3..8 letters — no FX authority exists; a demand test
  whose recorded spend is in another currency is honestly refused, never
  converted);
- `test_budget_minor_units` (integer minor units, 0..2e9; 0 = a
  zero-budget program that may still record candidates and observations);
- `max_demand_tests` (1..50);
- `min_order_count_for_viability` (1..1000 — the §15 economic gate).

Fail-closed seams:

- NO demand test launches without a current version;
- the launch pre-gate refuses when cumulative observed spend + the new
  test's spend would exceed the declared budget, or when the demand-test
  count reached the declared max (409 — "raise the declared bounds through
  a new version, never a silent continue");
- a `guardrail_blocked` or terminal program refuses all new spend.

### The evaluation + the breach states

`evaluateCommerceDiscoveryGuardrails` composes:

- the REAL observations: the demand-test spend sum + count from the
  program's own records, and the observed DISTINCT order count derived
  from the client's ingested order events of the declared store connection
  (READ-ONLY through /integrations);
- the policy context: the active network policy versions on the scope
  chain, CITED on the evaluation record (FK-anchored, scope-fenced);
- the deterministic cd-guardrails-v1 ruleset (pure, versioned):
  `spend_exceeds_test_budget`, `demand_tests_exceed_limit` → verdict
  `within_bounds` | `breached`.

A BREACH appends the evaluation record AND transitions the program to
`guardrail_blocked` (row-locked CAS + the transition event, in one
transaction). While blocked: launches refused, the learning loop still
records observations (they feed the resolution). The block is NEVER
silently lifted — `resolveCommerceDiscoveryGuardrailBlock` re-evaluates
under the CURRENT declared bounds (a budget-raising version may have been
recorded — itself an auditable declaration) and returns to `active` only
on an honestly within-bounds observation; a still-breached resolve is an
honest 409.

Terminal states (`concluded`, `stopped_by_user`) have no outgoing
transitions; the `guardrail_blocked ↔ active` pair is owned exclusively by
the evaluation/resolve commands (the generic status surface refuses those
targets).

## 4. The learning loop (order truth)

`recordCommerceDiscoveryOutcome` cites REAL commerce-event ids; each must
be one of the client's INGESTED order events of the declared store
connection (uniform 404 otherwise). The pure `deriveOutcomeCore`:

- counts DISTINCT non-cancelled orders (the LATEST event per provider
  order subject wins — order.updated/order.fulfilled supersede
  order.created; cancelled orders are disclosed separately);
- sums order values PER CURRENCY (no cross-currency aggregation, no
  conversion);
- evaluates the viability verdict against the current version's declared
  gate;
- derives the listing recommendation AS DATA
  (`recommend_listing` | `recommend_iteration` | `do_not_list`).

There is NO simulated-sales channel anywhere in the module (the
order-truth disclosure ships on every outcome view). Attribution is
distinct from causality (disclosed on every view).
