## 1. What the module is

The attribution SURVIVAL-CHAIN runtime the §16 contract names ("Every
social-to-product action can carry a mission-scoped attribution
reference"): ONE mission-scoped STABLE id per canonical creation input,
minted deterministically (SHA-256 identity digest over contract version
+ mission + mechanism + purpose + context; the id is its first 16 hex,
grammar `sca-<16hex>`), that then survives every downstream surface as
RECORDED DATA — never re-minted, never swapped:

- **the reference** (`social_attribution_references`): born `active`,
  the single guarded advance to `retired` (a retired reference accepts
  no new linkage; history stays readable). The honest `'unavailable'`
  mechanism is a FIRST-CLASS input — a platform that offers no
  attribution mechanism for the action is recorded as such, and the DB
  double fence later rejects any construction, attachment or crossing
  on it (never a fabricated link);
- **the link construction** (`social_attribution_link_constructions`):
  the deterministic pure `sca-link-v1` formula per mechanism — the
  constructed link + the match field it rides (the closed six-field
  vocabulary: utmContent, landingRoute, campaignId, creatorContentRef,
  nativeLinkId, attributionRef);
- **the attachments** (`social_attribution_attachments`): THE SURVIVAL
  CHAIN — every content transformation APPENDS a carried-identity row
  whose `carried_refs` MUST contain the ORIGINAL content identity plus
  every derived one (the `sca_carried_refs_valid` CHECK: an attachment
  that dropped the original is INEXPRESSIBLE);
- **the provider-boundary crossings**
  (`social_attribution_provider_crossings`): born `dispatched` with the
  EXACT field recorded, the single guarded advance to `echoed`
  (provider echoed the reference back) or `dropped` (the provider
  dropped it — honestly recorded, never fabricated into an echo);
- **the conversion events**
  (`social_attribution_conversion_events`): the objective's three
  outcome surfaces (`store_visit`, `product_interaction`, `order`) from
  the two closed sources — `order_webhook` (the REAL order landing
  through the MKT-071 commerce webhook boundary with the attribution
  passthrough riding VERBATIM) and `first_party_event` (the
  mechanism-specific first-party matching, e.g. utmContent);
- **the outcomes** (`social_attribution_outcomes`): THE JOIN — the
  co-occurrence match VERIFIED by the deterministic `sca-match-v1`
  matcher (never a caller-asserted match: no verified match → the
  honest 409), carrying THE PINNED CO-OCCURRENCE NOTE
  `co-occurrence evidence only — never causal proof` CHECK-fenced at
  the DB level, plus the evidence/metrics flowback citations.

Module surface: `public.ts` (the ONE public entry — the TEST_MODULE_
INTERNAL_IMPORT rule: the pure cores + pure input guards re-exported)
+ `internal/validation.ts` (the pure guards), `internal/link-core.ts`
(the deterministic construction/matching cores),
`internal/attribution-store.ts` (the six-table persistence),
`internal/attribution-module.ts` (the orchestration).

## 3. The survival chain (the acceptance's first core)

`constructAttributionLink` → `recordAttributionAttachment` (APPEND per
transformation, the original identity REQUIRED among carried refs) →
`recordProviderBoundaryCrossing` (the exact field) → the REAL order
lands through the MKT-071 commerce webhook boundary (the attribution
passthrough rides VERBATIM — the reference is whatever the provider's
own attribution field carries back, no re-mint) →
`recordAttributionOutcome` verifies the co-occurrence through the
UNIVERSAL `attributionRef` carrier field + the mechanism-specific
match field. The idempotent convergence is the fence pair: the
identity-digest unique (same canonical inputs → the SAME reference
row) + the input-digest unique (same construction inputs → the SAME
construction row) — no re-minting, no id swap, ever.

## 4. The causal separation (the acceptance's second core)

- THE CAUSAL-SEPARATION DISCIPLINE (structural): the comment-stripped
  module code carries NO causal vocabulary — no lift, no contribution,
  no incrementality, no "caused". The experiment-analysis authorities
  own causal estimation; this module records co-occurrence only;
- THE CO-OCCURRENCE NOTE CHECK FENCE (DB): every outcome row carries
  the pinned note literally — a causal-claiming row is INEXPRESSIBLE
  (error 23514, proven by probe over an otherwise-valid FK chain);
- the no-verified-match 409: the co-occurrence is evidenced by the
  matcher or the outcome row stays unexpressible — never a
  caller-asserted match.

## 5. Migration 069 — the fences

Six OWN tables only (no authority table, no catalog/order/listing/
price/inventory table anywhere — lock rules 32/33). CHECK-fenced
closed vocabularies (the mechanisms + the constructible subset, the
statuses, the crossing statuses, the conversion kinds/sources, the
carrier kinds, the match fields, the version strings sca-contract-v1 /
sca-vocab-v1 / sca-link-v1 / sca-match-v1, the stable-id grammar).
Nineteen triggers: the four append-only families reject UPDATE/DELETE;
the references carry the single guarded active → retired advance; the
crossings the single guarded dispatched → echoed/dropped advance. The
`SCOPE-CONSISTENCY` fences (construction/attachment/crossing/outcome
same-reference + same-tenant). Every FK anchor points ONLY at the
tenant tables + same-module rows (the mission/commerce citations are
OPAQUE recorded data). THE ORDER-TRUTH FENCE: an `order` conversion
REQUIRES the real order-webhook source + the commerce-event citation
(a first-party kind carries none). The `unavailable` double fence.
The `sca_carried_refs_valid` survival-chain helper.
