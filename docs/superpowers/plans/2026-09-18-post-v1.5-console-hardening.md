# MOS Post-v1.5 Product Console & Deployment Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`[ ]`) syntax for tracking.

**Goal:** Bring the user-facing MOS console under the `payswapdotorg/MOS` repository, reorganize the product around the agency's daily operating workflow, and leave the repository with a verifiable three-worker implementation handoff.

**Architecture:** MOS v1.5 remains frozen. The console is a presentation layer over the existing v1.5 authorities and must not create client, workflow, execution, evidence, decision, profit, app, deployment, or AI-routing authorities. The current live `mos-product` deployment is an external CLI-sourced Vercel artifact; source recovery is therefore a hard P0 before any UI implementation can be accepted as repository truth.

**Tech Stack:** Existing MOS modular monolith (TypeScript/Node/PostgreSQL) plus the recovered Next.js MOS console, Vercel deployment, Neon/PostgreSQL, Redis and object storage through existing provider abstractions.

**Spec:** `docs/product/PRODUCT-CONSOLE-V1.5.md`

## Global Constraints

- MOS architecture remains **v1.5 FROZEN**.
- MKT-001..MKT-052 are accepted/merged; do not reopen them for presentation concerns.
- Repository `main` is the canonical integration branch.
- The complete console source must live under `payswapdotorg/MOS` before the console can be declared repository-complete.
- UI is presentation over authoritative APIs; frontend authorization checks are advisory only.
- Client/Workspace isolation is enforced server-side before dependent traversal or external access.
- The Operating Graph, Decision Ledger, Profit Intelligence, Client Memory and AI Operator are derived/coordination surfaces and never replace their underlying authorities.
- App UI is presentation-only and invokes server capabilities for mutations.
- Deployment remains the only deployment lifecycle authority.
- Maximum active implementation workers: 3.
- One Work Item per Worker unless the Tech Lead explicitly authorizes a corrective split.
- No worker may mark a Work Item complete from its own report alone.
- Production claims require reproducible evidence and exact commands.
