## Forbidden dependency directions

- `/ai-runtime` must not import a concrete provider SDK outside its adapter implementation.
- `/workflows` must not depend on a model/provider implementation.
- `/executions` must not select a business strategy or decide business success.
- `/evidence` must not mutate workflow/execution state.
- `/reporting` must never mutate authoritative domain state.
- `/operating-graph` is a derived coordination model over canonical authorities (read-only composition): it must never mutate authoritative domain state, must store only source references (canonical ids, kinds, versions and the scope chain — never shadowed authoritative shape), and must never become a second authority for any composed module.
- `/decisions` is the v1.5 append-oriented Decision Ledger authority (spec/architecture-v1.5.md §4; spec/change-request-005.md change #2). It consumes the listed public contracts READ-ONLY for write-time reference validation and canonical ownership resolution; `/policies` is the reserved direction for the MKT-045 consequential-action flow (deliberately unused by the ledger itself — recording a decision is unconditional, architecture-v1.5.md §7). The ledger never mutates historical execution, evidence, outcome or learning records (architecture-lock-v1.5.md rule #5).
- `/app-installs` is the v1.5 App installation authority (spec/mos-app-ecosystem-v1.5.md "Install and invoke", "Bounded app state", "Upgrade and rollback"; architecture-lock-v1.5.md rules #10/#11). It consumes the `/apps` registry public contract READ-ONLY (exact App Version resolution + the MKT-047 compatibility query — the registry is never mutated from here) and the `/policies` public contract for the fail-closed install/upgrade/rollback gate and the per-scope server-derived grant evaluations (every evaluation recorded by the engine); `/workspaces` and `/extensions` arrive through declared STRUCTURAL PORTS wired at the composition root (canonical workspace ownership; the workspace's authorized extension versions as the compatibility inputs). Installation is workspace-scoped and policy-gated; granted scopes are always SERVER-DERIVED (never caller-supplied); the install ledger is append-only with the single sanctioned selection-supersession transition — historical invocation records retain their original exact App Version identity (architecture-lock-v1.5.md rules #10/#11).
- `/profit-intelligence` is the v1.5 derived Profit Intelligence read model (spec/architecture-v1.5.md §5; architecture-lock-v1.5.md rule #6). It consumes the listed public contracts READ-ONLY through the /reporting live-aggregation precedent: every material figure is computed at read time with source references, the frozen calculation version and the explicit assumption set, and the module owns NO durable state (no profit_intelligence_* tables, no persisted projection). It can recommend but must never mutate contracts, billing or any financial/accounting authority — no mutation method over any authority may exist on its contract.
- `/ai-operator` is the v1.5 AI Operator attention-queue read model (spec/architecture-v1.5.md §7). It consumes the listed public contracts READ-ONLY through the /profit-intelligence derived-read-model precedent: attention items are live-derived at read time with a frozen category vocabulary and rank calculation version, source references to canonical record ids, structured rationale and the EXISTING consequential-action contract reference the item would flow through — the module owns NO durable state (no ai_operator_* tables, no persisted queue) and exposes ZERO mutation methods: it ranks action candidates only, never executes or creates them (consequential actions continue through the existing policy/approval contracts; scope-leakage and margin-pressure items consume the /profit-intelligence public figures and never recompute them).
- `/sales-continuity` is the v1.5 Sales-to-Delivery Continuity orchestrator (spec/architecture-v1.5.md §8). It consumes /decisions READ-ONLY (the proposal record + canonical ownership), orchestrates the /playbooks and /deployments EXISTING public creation/status commands (the only writes it can cause anywhere — never a second playbook/deployment store, never a write to their tables, never the MKT-040 validate/activate gate), resolves /clients + /workspaces ownership through its declared structural ports, and consumes the /evidence public contract's shared §21 material-key guard (READ-ONLY, the /decisions precedent) over the carried snapshot. Its own durable state is exactly the append-only continuity ledger (source references + version identity + carried snapshot + linkage) with forward-only completion; the carried identity is never rewritten — a new proposal version carries fresh identity.
- `/client-memory` is the v1.5 Client Operating Memory derived read model (spec/architecture-v1.5.md §6: a governed projection over canonical client, goal, playbook, deployment, evidence, experiment, outcome, decision and learning records; retrieval/index technology is non-authoritative). It consumes the listed public contracts READ-ONLY through the /reporting + /profit-intelligence live-derivation precedent: every memory view is composed at read time with canonical record citations only (never a shadowed authoritative shape) under the frozen, versioned projection vocabulary (cm-proj-v1) with its explicit selection rules, and the module owns NO durable state (no client_memory_* tables, no persisted projection, no retrieval index — nothing to rebuild). It must never expose a mutation method over ANY authority and may never become a second tenant or data authority.
- `/extensions` must not mutate `/workflows` except through an authorized workflow command/port.
- `/app-marketplace` is the v1.5 App marketplace, trust and certification surface (spec/mos-app-ecosystem-v1.5.md "Trust levels" + "Manifest" + "Economics"). It consumes the `/apps` registry public contract READ-ONLY for every catalog fact (the listing, version history and exact-version resolution — the marketplace NEVER becomes a second registry: it owns no app catalog table, only the append-only trust_events governance ledger and the app_reviews display-metadata records). Trust transitions are append-only events with operator provenance — never registry rewrites (the registry's certification column stays frozen at birth); trust is METADATA and a policy input that never grants authority by itself. The MKT-048 install gate consumes the marketplace-derived trust state through a STRUCTURAL PORT declared in `/app-installs`'s public entry and wired at the composition root (the `/policies`→`/credentials` port precedent — deliberately off-matrix, disclosed); reviews are display metadata no policy consumes. Marketplace attribution stays separate from the core financial authority (metering/attribution is later Work Item territory).
- `/app-metering` is the v1.5 App metering and commercial attribution authority (spec/mos-app-ecosystem-v1.5.md "Economics": "MOS may meter installations, invocation count, compute/runtime, data volume and premium capabilities. Marketplace attribution is separate from the core financial authority."). It consumes the `/apps` registry public contract READ-ONLY (exact App Version resolution for the ingestion manifest guards + the lineage listings for the publisher view), the `/app-installs` public contract READ-ONLY (the install-ledger selection rows and lifecycle event tail are the COLLECTION SOURCES; the current selections are the ingestion context and the invocation-attribution linkage inputs — the ledger is never written from here), the `/extensions` public contract READ-ONLY (the invocation ledger rows are the invocation COLLECTION SOURCE and the ingestion provenance validation), and `/workspaces` through a declared STRUCTURAL PORT (canonical workspace ownership, the /app-installs precedent). Its durable state is exactly the append-only meter event tail plus the rebuildable rollup projection (migration 044 — the at-most-once source fence, the payload-shape and unit CHECKs, the scope-chain and canonical-identity triggers, and append-only UPDATE/DELETE rejection); the collection, usage-observation ingestion and rollup recompute are MODULE-LEVEL operations for server-side callers (the operating-graph rebuild precedent) and the HTTP surface is the GET-only attribution family. The module exposes ZERO billing/charging mutation methods of any kind — no invoices, no payments, no balance mutations, no prices: meter records carry quantities, never money (architecture-lock v1.5 #6's financial-authority posture; the Economics separation).
- `/first-party-apps` is the v1.5 Incumbent Capability App Program composition home (spec/effective-backlog-v1.5.md MKT-051; spec/mos-app-ecosystem-v1.5.md "What Apps can do" / "Non-goals"; spec/architecture-v1.5.md §9). It consumes the `/apps` registry and the `/app-installs` ledger READ-ONLY (the pinned manifest of the workspace's CURRENT selection — exact App Version identity; the granted scopes that constrain presentation), and the incumbent authorities' public contracts READ-ONLY through the /reporting + /profit-intelligence live-aggregation precedent (with /workspaces for the workspace enumeration the /reporting contract's scope-as-data input requires): every pack surface model is composed at read time from the authorities' own views with canonical source references, never recomputed or shadowed. Pack code holds ZERO mutation verbs over ANY authority (the strict MKT-051 discipline): action menus DECLARE actions whose invocation contracts reference the EXISTING authority command routes, and every mutation an operator then makes flows through those routes under the platform's own authorization — never through pack logic. Bounded app state is IN-MEMORY, namespaced under the pack's own manifest-declared `app:<key>:<local>` namespaces (the migration-037 denylist respected), with explicit export/delete semantics and lineage to canonical record ids; the module owns NO durable state, takes NO migration and holds NO database dependency (packs are registry data + presentation code over existing authorities).
- `/growth-missions` is the v1.6 Growth Mission and Objective Model authority (spec/effective-backlog-v1.6.md MKT-053; spec/architecture-v1.6.md §1/§2/§3; spec/architecture-lock-v1.6.md rules 16/17/41). It consumes `/agencies` and `/goals` through declared STRUCTURAL PORTS, both READ-ONLY (the agency row for the fail-closed agency-scope resolution; canonical goal resolution for the mission→goal mapping — the Goal authority stays the sole measurable business-intent authority and goal progress is never re-stated, re-computed or owned here). Its durable state is exactly the agency-scoped mission records plus the append-only version tail (the declared objective is immutable — corrections are NEW version records), the append-only history tail (state transitions with actor + provenance + reason) and the goal-mapping rows (migration 045 — CHECK-fenced family/state vocabularies and append-only UPDATE/DELETE rejection triggers); it is a durable orchestration LAYER over existing Goals, never a replacement authority, and holds NO controller, scheduler or replanner — the Growth Operator is MKT-054 (architecture-lock-v1.6.md rules 16/17).
- `/social-accounts` is the v1.6 Social Account and OAuth Connection Model authority (spec/architecture-v1.6.md §4; spec/effective-backlog-v1.6.md MKT-055; architecture-lock-v1.6.md rules 18/19/28). It consumes the `/integrations` public contract READ-ONLY for the canonical integration connection reference + ownership chain (a social account attaches only through an EXISTING authorized — `connected` — integration; the connection, never this module, owns the client chain), the `/credentials` public contract as the vault authority for the grant's OWN least-privilege token references (kind `social_account_oauth` — created, resolved in-process after a fail-closed allow, and disabled through the vault; NEVER shared with product/source/store credentials, and NO token material ever enters the module's tables — the migration-046 grant rows carry the vault reference only), `/policies` for the fail-closed network/secrets gates in front of every provider-touching flow step (social-account.complete/refresh/revoke + social-account.credential), and `/workspaces` through a declared STRUCTURAL PORT for the optional workspace narrowing of the attachment. The OAuth grant lifecycle is append-oriented (pending → authorized → expired/revoked/refreshed/superseded; refresh and reauthorize append NEW grant records + history events — the recorded authorization facts are immutable), the EXACT granted scope list is recorded VERBATIM plus the platform-normalized capability tags (a faithful RECORD, never an assumption of parity), one connection binds one platform identity with idempotent reconnect and fail-closed conflicting-binding rejection, and disconnect/revocation — operator-initiated and externally-signalled — is terminal and fail-closed (every authorization-bearing read refuses; replaced grants' vault references are disabled — no zombie grants). The module defines the provider-neutral OAuth FLOW PORT but ships NO flow implementation: flows arrive as data (the adapter-registry precedent) with the MKT-056+ adapter deliveries; until then the production registry is EMPTY and flow steps are refused fail-closed (no platform-specific knowledge lives in the module — the platform identity is the adapter key carried as data, architecture-lock-v1.6 rule 18).
- `/notification-delivery` is the v1.6 Notification Delivery Plane authority (spec/effective-backlog-v1.6.md MKT-068; spec/architecture-v1.6.md §14; spec/module-dependency-matrix-v1.6.md boundary rule 9). It consumes the `/notifications` BOUNDARY identity READ-ONLY (the MKT-001 boundary-only stub — the delivery plane fills the delivery surface that boundary reserved, and the boundary itself keeps no business logic), the `/policies` public contract for the fail-closed per-channel gates (the notification-channel policy keys `notification.channel.<channel>` — a channel not sanctioned for the urgency/event type fails closed into an honest refused receipt, never a silent drop) and the `/credentials` vault READ-ONLY through the email adapter (provider credential by vault REFERENCE id, resolved in-process in the notification's authorized-execution scope — never a raw secret in the module). Its durable state is exactly the notification records (the §14 field set), the event-occurrence dedup fence (at-most-one notification per (source kind, source id, event type, occurrence key) — a replayed occurrence surfaces honest duplicate-skipped receipts on the original), the append-only delivery-attempt receipt tail (delivered/failed/refused/duplicate-skipped; retries are NEW rows) and the in-app read-state projection with its append-only read transition (migration 047 — CHECK-fenced vocabularies and append-only UPDATE/DELETE rejection triggers). Delivery is pluggable per channel through the platform-neutral DeliveryAdapter contract (in-app + email MVP; WhatsApp/Telegram/SMS/Signal are declared-but-unimplemented capability keys — registering one is refused fail-closed until their Work Items arrive). It delivers messages ONLY and never becomes canonical task/action state (boundary rule 9): the delivery status is the adapter-plane lifecycle (pending → dispatched), never a business/task state, and no done/acknowledged/acted-on verb or column exists anywhere. The disclosed off-matrix structural-port wiring: the email recipient resolution composes the `/agencies` membership and `/users` identity authorities at the composition root (recipients resolve from the notification's own scope chain — never a request field, never guessed).
- No module imports another module's database repository implementation directly unless the matrix explicitly names that authority boundary and the imported symbol is part of its public contract.

## Composition root

Provider SDKs, concrete queue/storage clients, sandbox drivers, browser drivers and external integration adapters are wired at the composition root. Domain/application modules depend on provider-neutral contracts.
